GitHub Trending에서 **CopilotKit**이 다시 상위권에 오른 것은 “또 하나의 AI 채팅 UI 라이브러리”가 주목받았다는 사건으로만 보기 어렵다. 2026년 6월 6일 오전 KST 기준 daily Trending에는 `NousResearch/hermes-agent`, `chopratejas/headroom`, `CopilotKit/CopilotKit`, `lfnovo/open-notebook`, `PaddlePaddle/PaddleOCR`처럼 AI 에이전트, 컨텍스트 압축, 문서 지능, 에이전트 사용자 인터페이스를 다루는 저장소가 함께 올라와 있었다. 수치와 순위는 확인 시점의 공개 스냅샷이며 GitHub Trending의 집계 방식, 지역, 시간대에 따라 달라질 수 있다.

그중 [CopilotKit](https://github.com/CopilotKit/CopilotKit)은 약 3.2만 개 이상의 스타와 4천 개 이상의 포크를 보유했고, daily Trending 페이지에서는 약 350개 수준의 신규 스타가 표시됐다. GitHub API 기준 저장소는 2026년 6월 5일에도 커밋이 이어졌고, `v1.59.5` 릴리스가 같은 날 게시되어 있었다. README는 CopilotKit을 “프런트엔드 스택 for agents and generative UI”로 설명하며, React·Angular 등 사용자 화면에서 에이전트 실행, 공유 상태, 백엔드 도구 렌더링, human-in-the-loop 워크플로를 다루는 SDK라고 소개한다. 특히 CopilotKit 팀이 주도하는 [AG-UI Protocol](https://github.com/ag-ui-protocol/ag-ui)은 에이전트와 사용자 애플리케이션 사이의 이벤트 기반 상호작용을 표준화하려는 시도다.

오늘의 핵심 흐름은 명확하다. 기업은 이제 “LLM을 호출할 수 있는가”가 아니라 **AI 에이전트가 실제 제품 화면 안에서 안전하게 일할 수 있는가**를 묻기 시작했다. 챗봇 위젯만 붙이는 단계에서는 모델 응답을 스트리밍하고 히스토리를 보여주면 충분했다. 그러나 업무 애플리케이션에서 에이전트가 견적서를 수정하고, CRM 필드를 업데이트하고, 대시보드 필터를 바꾸고, 결재 초안을 만들고, 사용자의 승인을 받아 API를 호출한다면 문제의 범위가 완전히 달라진다. UI 상태, 권한, 감사 로그, 실패 복구, 사용자 확인 지점, 이벤트 버전 관리가 모두 제품 아키텍처의 일부가 된다.

## 왜 지금 CopilotKit과 AG-UI가 Trending에 올랐는가

지난 1~2년 동안 에이전트 생태계의 중심은 도구 호출과 런타임에 있었다. 모델이 함수 호출을 할 수 있는지, 외부 도구를 안전하게 붙일 수 있는지, 여러 에이전트가 역할을 나눠 작업할 수 있는지가 주요 관심사였다. 그래서 [Model Context Protocol](https://modelcontextprotocol.io/)은 에이전트가 도구와 데이터 소스에 접근하는 방식을 표준화하려 했고, [Google A2A](https://github.com/google-a2a/A2A)는 에이전트 간 상호운용이라는 문제를 전면에 내세웠다. 이 흐름 자체는 여전히 중요하다. 다만 도구와 에이전트가 늘어날수록 마지막 병목은 “사용자가 보는 제품 경험”으로 이동한다.

실무에서 에이전트 프로젝트가 데모를 넘어서지 못하는 이유는 모델 성능 부족만이 아니다. 오히려 더 자주 보이는 실패는 UI와 업무 상태의 불일치다. 에이전트가 “고객 정보를 업데이트했습니다”라고 말했지만 실제 폼 상태는 바뀌지 않았거나, 화면에는 바뀐 것처럼 보이지만 백엔드 트랜잭션은 실패했거나, 사용자가 승인하지 않은 액션이 로그 없이 실행되는 식이다. 이런 문제는 프롬프트만 잘 쓴다고 해결되지 않는다. 제품 화면과 에이전트 런타임 사이에 명확한 이벤트 계약, 상태 동기화, 권한 검증, 사용자 승인 흐름이 필요하다.

CopilotKit이 주목받는 배경은 바로 이 지점에 있다. README가 강조하는 기능은 단순 채팅 UI가 아니라 backend tool rendering, generative UI, shared state, human-in-the-loop이다. 이는 에이전트가 텍스트 답변을 생성하는 것을 넘어, 사용자의 화면 안에서 컴포넌트를 보여주고, 상태를 읽고 쓰며, 실행 중간에 사용자 확인을 요청하는 구조다. AG-UI README 역시 에이전트 백엔드가 약 16개 표준 이벤트 타입에 맞는 이벤트를 내보내고, SSE·WebSocket·Webhook 같은 전송 방식 위에서 상호운용할 수 있도록 하는 방향을 제시한다. 즉 오늘의 관심은 “더 똑똑한 챗봇”이 아니라 **에이전트와 사용자 인터페이스 사이의 운영 프로토콜**이다.

## 핵심 아키텍처: 에이전트 UI는 네 개의 경계로 나뉜다

에이전트 UI를 설계할 때 가장 먼저 분리해야 할 것은 모델 호출, 에이전트 런타임, 제품 UI, 업무 시스템의 경계다. 많은 초기 PoC는 이 네 가지를 하나의 서버 액션이나 프런트엔드 콜백에 섞어 구현한다. 짧은 데모에서는 빠르지만, 기능이 늘어나면 디버깅과 보안 검토가 어려워진다. CopilotKit과 AG-UI가 제안하는 방향은 이 경계를 이벤트와 상태 모델로 다시 정리하는 데 가깝다.

첫 번째 경계는 사용자 의도와 제품 상태다. 사용자는 “지난 분기 매출이 낮은 지역을 찾아 후속 액션을 제안해줘”라고 말할 수 있지만, 제품은 실제로는 테이블 필터, 차트 범위, 선택된 고객 세그먼트, 로그인 사용자의 권한, 미저장 폼 상태를 가지고 있다. 에이전트가 좋은 답을 내려면 이 컨텍스트가 모델에 전달되어야 하고, 동시에 민감한 필드는 전달되지 않아야 한다. shared state 계층은 여기서 중요해진다. 에이전트가 볼 수 있는 상태와 수정할 수 있는 상태를 구분하지 않으면, 기능 확장은 곧 권한 사고로 이어질 수 있다.

두 번째 경계는 에이전트 런타임과 UI 이벤트다. LangGraph, CrewAI, Mastra, PydanticAI 같은 런타임은 각자 에이전트 실행 그래프와 도구 호출 방식을 제공한다. 그러나 최종 사용자가 보는 화면은 “어떤 노드가 실행되었는가”보다 “지금 어떤 상태이고, 어떤 선택을 해야 하며, 무엇이 변경될 예정인가”에 관심이 있다. AG-UI 같은 프로토콜은 런타임 내부 이벤트를 사용자 경험에 필요한 이벤트로 번역하는 역할을 할 수 있다. 진행 상태, 중간 결과, 도구 호출 요청, UI 컴포넌트 렌더링, 사용자 승인 요청이 모두 제품 화면에 맞게 표현되어야 한다.

세 번째 경계는 generative UI와 컴포넌트 안전성이다. 에이전트가 UI를 “생성”한다는 말은 매력적이지만, 실무에서는 임의 HTML을 그대로 렌더링하는 방식이 되어서는 안 된다. 더 현실적인 접근은 사전에 허용된 컴포넌트, 스키마, 액션 집합 안에서 에이전트가 어떤 UI를 보여줄지 선택하거나 데이터를 채우게 하는 것이다. 예를 들어 영업 앱에서는 할인 승인 카드, 고객 리스크 요약 카드, 후속 이메일 초안 카드처럼 제한된 컴포넌트가 있고, 에이전트는 여기에 구조화 데이터를 넣는다. 이렇게 해야 접근성, 디자인 시스템, 보안 정책, 감사 로그를 유지할 수 있다.

네 번째 경계는 사람 승인과 실제 업무 API 호출이다. 에이전트가 CRM 레코드 수정, 결제 취소, 배포 실행, 권한 변경처럼 되돌리기 어려운 일을 할 수 있다면 human-in-the-loop는 선택 기능이 아니라 필수 안전장치다. 중요한 점은 승인 버튼을 하나 추가하는 것이 아니라, 승인 요청의 근거와 변경 diff, 실행 주체, 만료 시간, 재시도 정책, 취소 경로를 함께 설계하는 것이다. CopilotKit이 human-in-the-loop를 핵심 기능으로 내세우는 이유도 여기에 있다.

## 기존 방식과 비교: 채팅 UI 라이브러리인가, 운영 계층인가

CopilotKit을 검토할 때는 “우리도 이미 AI SDK와 채팅 컴포넌트가 있는데 왜 필요한가”라는 질문이 자연스럽다. 이 질문은 타당하다. 모든 팀이 CopilotKit이나 AG-UI가 필요한 것은 아니다. 단순 Q&A, 문서 검색, 내부 FAQ 수준이라면 [Vercel AI SDK](https://sdk.vercel.ai/) 같은 모델 호출·스트리밍 추상화와 일반 채팅 컴포넌트만으로 충분할 수 있다. 프런트엔드에 빠르게 어시스턴트 UI를 붙이는 목적이라면 [assistant-ui](https://github.com/assistant-ui/assistant-ui) 같은 라이브러리도 좋은 선택지가 된다.

하지만 제품 내부 액션과 화면 상태가 중요해지는 순간 비교 기준은 달라진다. Vercel AI SDK가 모델 호출, 스트리밍, tool calling 개발 경험에 강점이 있다면, CopilotKit은 에이전트가 제품 화면과 함께 움직이는 패턴에 더 초점을 둔다. assistant-ui가 사용자에게 익숙한 대화형 UI 구성에 강점이 있다면, AG-UI는 에이전트 이벤트를 여러 런타임과 프런트엔드가 공유할 수 있는 계약으로 만들려 한다. MCP가 에이전트에게 도구를 제공하는 계층이라면, AG-UI는 그 에이전트가 사용자의 화면과 어떻게 상호작용할지 다루는 계층이다. A2A가 에이전트 간 대화를 다룬다면, AG-UI는 에이전트와 사용자 애플리케이션의 접점을 다룬다.

![에이전트 UI 스택 비교](https://heracles-jo.github.io/assets/img/posts/github-trending-agent-ui-protocol-copilotkit/comparison.svg)

이 구분은 아키텍처 의사결정에서 중요하다. 모델 호출 라이브러리를 제품 UI 운영 계층처럼 쓰면 권한, 상태, 승인, 관측성을 뒤늦게 덧붙이게 된다. 반대로 단순 챗봇에 무거운 에이전트 UI 프레임워크를 도입하면 복잡도만 늘어난다. 따라서 도입 판단은 “AI 답변을 보여주는가”가 아니라 “에이전트가 제품 상태를 바꾸는가, 사용자 승인과 감사 로그가 필요한가, 여러 프런트엔드 표면에서 같은 에이전트를 써야 하는가”를 기준으로 내려야 한다.

## 실무 도입 시 장점: 데모에서 제품 기능으로 넘어가는 다리

CopilotKit류의 접근이 주는 첫 번째 장점은 사용자 경험의 일관성이다. 많은 기업용 AI 기능은 처음에는 채팅 사이드바로 출발한다. 그러나 사용자가 실제로 원하는 것은 별도 챗봇과 대화하는 것이 아니라, 현재 보고 있는 화면에서 작업을 끝내는 것이다. 영업 담당자는 CRM에서 고객 요약을 보고 바로 후속 이메일을 만들고 싶고, 운영 담당자는 장애 대시보드에서 원인 후보를 보며 런북 실행 여부를 결정하고 싶다. 에이전트 UI 계층이 있으면 대화, 화면, 액션이 분리되지 않고 하나의 흐름으로 이어진다.

두 번째 장점은 상태 동기화와 재현성이다. 에이전트 실행은 비동기적이고 중간 상태가 많다. 스트리밍 응답, 도구 호출, 사용자 승인, 실패 재시도, 부분 업데이트가 이어진다. 이를 단순 텍스트 로그로만 남기면 나중에 “왜 이 값이 바뀌었는가”를 추적하기 어렵다. 이벤트 기반 프로토콜은 실행 흐름을 구조화된 기록으로 남길 수 있게 한다. 물론 프로토콜을 쓴다고 자동으로 감사 로그가 완성되는 것은 아니지만, 최소한 무엇을 기록해야 하는지의 기준을 세우기 쉬워진다.

세 번째 장점은 런타임 교체 가능성이다. 기업은 특정 에이전트 프레임워크 하나에 장기적으로 묶이고 싶어 하지 않는다. 초기에는 LangGraph로 시작했지만 나중에 자체 런타임으로 바꾸거나, 특정 업무에는 다른 에이전트 프레임워크를 써야 할 수 있다. UI가 런타임 내부 구조에 강하게 결합되어 있으면 교체 비용이 커진다. AG-UI처럼 사용자 상호작용 이벤트를 별도 계약으로 두는 접근은 프런트엔드와 런타임 사이의 결합도를 낮추는 방향으로 작동할 수 있다.

네 번째 장점은 제품 팀과 플랫폼 팀의 협업 방식이다. AI 플랫폼 팀은 모델, 도구, 에이전트 실행을 담당하고, 제품 프런트엔드 팀은 사용자 경험과 디자인 시스템을 담당한다. 두 팀 사이에 명확한 이벤트 스키마와 컴포넌트 계약이 없으면 기능마다 임시 API가 만들어진다. 에이전트 UI 프로토콜은 이 경계를 표준화해 “어떤 이벤트를 보내면 어떤 UI 상태가 되고, 어떤 승인이 오면 어떤 액션이 실행되는가”를 함께 설계하게 만든다.

## 한계와 리스크: 프로토콜은 만능 안전장치가 아니다

반대로 주의해야 할 점도 분명하다. 첫째, AG-UI나 CopilotKit을 도입한다고 해서 에이전트의 업무 판단이 자동으로 안전해지지는 않는다. 프로토콜은 이벤트와 상태를 전달하는 수단이지, 비즈니스 규칙의 최종 집행자가 아니다. 할인율 상한, 개인정보 접근 권한, 배포 승인 단계, 데이터 반출 정책은 여전히 백엔드 권한 시스템과 정책 엔진에서 강제되어야 한다. 프런트엔드에서 버튼을 숨기는 것만으로는 보안 통제가 되지 않는다.

둘째, generative UI는 관리되지 않으면 디자인 시스템과 접근성을 훼손할 수 있다. 에이전트가 매번 다른 형태의 카드를 만들거나, 사용자가 이해하기 어려운 액션을 제안하면 오히려 신뢰가 떨어진다. 따라서 실무에서는 “무엇이든 생성하는 UI”보다 “검증된 컴포넌트 안에서 구조화 데이터를 생성하는 UI”가 더 안전하다. 컴포넌트 레지스트리, JSON 스키마, 렌더링 권한, fallback UI, 접근성 테스트가 함께 필요하다.

셋째, 상태 충돌 문제가 있다. 사용자가 폼을 수정하는 동안 에이전트가 같은 필드를 바꾸거나, 여러 탭에서 같은 에이전트 실행이 진행되거나, 모바일과 웹에서 동일 작업을 동시에 처리하면 충돌이 발생한다. 이때 마지막 쓰기 우선 정책으로 덮어쓰면 업무 데이터가 손상될 수 있다. 에이전트 UI를 제품에 깊게 넣을수록 optimistic update, conflict resolution, undo, idempotency key 같은 전통적인 분산 시스템 설계가 중요해진다.

넷째, 관측성과 비용 관리가 필요하다. 에이전트 UI는 사용자의 작은 조작에도 컨텍스트 수집, 모델 호출, 도구 호출, 이벤트 스트리밍이 일어날 수 있다. 화면이 복잡할수록 컨텍스트가 커지고, 상태 동기화 이벤트가 많아진다. 비용을 관리하려면 어떤 상태를 모델에 보낼지, 어떤 이벤트를 저장할지, 어느 단계에서 압축·요약할지, 실패한 실행을 어떻게 샘플링할지 정해야 한다. 오늘 Trending에서 `headroom` 같은 컨텍스트 압축 도구가 함께 눈에 띈 것도 이 운영 비용 문제와 연결해 볼 수 있다.

다섯째, 생태계 성숙도를 냉정하게 봐야 한다. CopilotKit은 활발히 개발되고 있고 MIT 라이선스라는 장점이 있지만, 빠른 릴리스 주기는 API 변화와 업그레이드 부담을 동반할 수 있다. GitHub API 확인 시점 기준 open issues도 수백 건 수준이었다. 이는 활발한 프로젝트에서 흔한 모습이지만, 엔터프라이즈 도입 전에는 릴리스 노트, breaking change 정책, 보안 공지, 장기 지원 전략을 확인해야 한다.

## PoC 체크리스트: “채팅 붙이기”가 아니라 업무 경계 검증부터

CopilotKit이나 AG-UI 기반 PoC를 진행한다면 목표를 “우리 서비스에 AI 채팅창을 붙인다”로 잡지 않는 편이 좋다. 그 목표는 너무 쉽고, 실제 도입 리스크를 드러내지 못한다. 더 나은 PoC는 제한된 업무 흐름 하나를 골라 에이전트가 화면 상태를 읽고, 사용자의 승인을 받아, 실제 또는 모의 API를 호출하고, 결과를 감사 가능한 이벤트로 남기는지 검증하는 것이다.

다음 체크리스트를 권장한다.

| 점검 항목 | 확인 질문 | 실패 시 신호 |
| --- | --- | --- |
| 업무 범위 | 에이전트가 바꿀 수 있는 필드와 절대 바꿀 수 없는 필드가 분리되어 있는가 | 프롬프트에만 금지 규칙이 적혀 있음 |
| 상태 모델 | 화면 상태, 서버 상태, 에이전트 메모리가 어떤 기준으로 동기화되는가 | 사용자가 보는 값과 실행 결과가 다름 |
| 승인 흐름 | 위험 액션에 변경 diff와 근거가 표시되는가 | “확인” 버튼만 있고 무엇을 승인하는지 불명확 |
| 보안 | 백엔드에서 권한과 정책을 재검증하는가 | 프런트엔드 UI 제어에 의존 |
| 관측성 | 이벤트, 도구 호출, 승인, 실패 원인이 구조화 로그로 남는가 | 대화 텍스트만 저장 |
| 복구 | 실패·취소·재시도·되돌리기 경로가 있는가 | 오류 발생 시 새로고침 외 방법이 없음 |
| 유지보수 | 컴포넌트 스키마와 이벤트 버전을 관리하는가 | 기능별 임시 이벤트가 늘어남 |

PoC 범위로는 CRM의 후속 이메일 초안 작성 및 승인, 고객 세그먼트 분석 후 필터 적용, 내부 문서 검색 후 티켓 초안 생성, 장애 대시보드에서 런북 실행 제안 같은 흐름이 적합하다. 공통점은 사용자가 이미 제품 화면에서 맥락을 보고 있고, 에이전트가 그 맥락을 이용해 제한된 액션을 제안하며, 최종 실행 전에 사람이 확인할 수 있다는 점이다.

## 어떤 팀에 적합하고, 어떤 경우 피해야 하는가

CopilotKit과 AG-UI 같은 접근은 SaaS 제품, 내부 업무 플랫폼, 데이터 분석 도구, 운영 콘솔처럼 사용자가 화면에서 복잡한 작업을 수행하는 제품에 특히 적합하다. 이미 React 또는 Angular 기반의 프런트엔드가 있고, 에이전트가 단순 답변을 넘어 화면 상태를 읽거나 바꾸어야 하며, human-in-the-loop가 필요한 팀이라면 검토할 가치가 크다. 여러 에이전트 런타임을 실험 중이거나, 웹·모바일·협업 도구 등 여러 표면에서 같은 업무 에이전트를 쓰고 싶은 조직도 이벤트 프로토콜 계층의 장점을 얻을 수 있다.

반면 다음 경우에는 도입을 서두르지 않는 편이 낫다. 첫째, 제품 요구가 단순 FAQ나 문서 검색뿐이라면 무거운 에이전트 UI 계층은 과할 수 있다. 둘째, 백엔드 권한 모델과 감사 로그가 아직 정리되지 않았다면 프런트엔드 에이전트부터 붙이는 것은 위험하다. 셋째, 디자인 시스템과 컴포넌트 계약이 약한 조직에서 generative UI를 먼저 도입하면 사용자 경험이 쉽게 파편화된다. 넷째, AI 기능의 소유권이 제품팀·플랫폼팀·보안팀 사이에서 명확하지 않다면 프로토콜보다 운영 책임 구조를 먼저 정해야 한다.

## 운영 설계 관점: 에이전트 UI는 프런트엔드만의 문제가 아니다

에이전트 UI라는 이름 때문에 이 주제를 프런트엔드 팀의 문제로 좁게 해석하기 쉽다. 그러나 실제로는 플랫폼 엔지니어링, 보안, 데이터 거버넌스, 제품 기획이 모두 얽힌다. 에이전트가 화면에서 어떤 제안을 하려면 사용자 데이터와 업무 컨텍스트를 읽어야 하고, 액션을 실행하려면 백엔드 권한과 트랜잭션을 통과해야 하며, 결과를 설명하려면 관측성 데이터가 필요하다. 프런트엔드는 이 복잡한 흐름을 사용자가 이해할 수 있는 형태로 보여주는 마지막 계층이다.

따라서 운영 설계는 최소 다섯 가지 원칙을 가져야 한다. 첫째, 에이전트가 볼 수 있는 컨텍스트는 최소 권한 원칙을 따른다. 둘째, 에이전트가 제안한 변경은 실행 전 구조화된 diff로 표시한다. 셋째, 위험도에 따라 자동 실행, 사용자 승인, 관리자 승인, 금지 액션을 구분한다. 넷째, 모든 도구 호출과 승인 이벤트는 감사 가능한 로그로 남긴다. 다섯째, 모델 응답 실패와 도구 실패를 사용자에게 구분해 보여준다. “AI가 실패했습니다”라는 메시지는 운영자에게 아무 정보도 주지 못한다.

성능도 별도 고려가 필요하다. 에이전트 UI는 스트리밍이 있기 때문에 체감 응답성은 좋아 보일 수 있지만, 초기 컨텍스트 구성과 도구 호출이 느리면 전체 작업 시간은 길어진다. 특히 대시보드, 문서 편집기, CRM처럼 화면 상태가 큰 애플리케이션에서는 전체 상태를 모델에 넘기지 말고, 현재 작업과 관련 있는 부분만 추출해야 한다. 이벤트를 모두 서버에 저장하면 관측성은 좋아지지만 저장 비용과 개인정보 리스크가 커진다. 결국 좋은 에이전트 UI 아키텍처는 “많이 보내는 것”이 아니라 “필요한 상태를 명확한 계약으로 보내는 것”에 가깝다.

## 앞으로 관찰할 지표와 전망

CopilotKit과 AG-UI의 향후 가치를 판단하려면 스타 수보다 더 중요한 지표를 봐야 한다. 첫째, AG-UI가 실제로 여러 에이전트 런타임과 프런트엔드 프레임워크 사이에서 상호운용되는 사례가 늘어나는지 확인해야 한다. README에는 LangGraph, CrewAI 등 다양한 통합 방향이 언급되지만, 기업 도입 관점에서는 예제보다 운영 사례와 호환성 테스트가 중요하다. 둘째, 이벤트 스키마와 버전 관리가 얼마나 안정적으로 유지되는지 봐야 한다. 프로토콜은 한 번 제품에 들어가면 변경 비용이 크다.

셋째, 보안 모델과 감사 로그 패턴이 성숙하는지 관찰해야 한다. 에이전트 UI가 실제 업무 액션을 다루려면 SOC2, ISO 27001, 개인정보보호, 산업별 규제와 연결될 수밖에 없다. 오픈소스 SDK가 이 모든 것을 대신할 수는 없지만, 권장 아키텍처와 예제에서 최소 권한, 서버 측 검증, 승인 이벤트 기록을 얼마나 일관되게 다루는지는 중요한 신호다. 넷째, CopilotKit 자체의 릴리스 속도와 breaking change 관리도 확인해야 한다. 2026년 6월 초 기준 활발한 커밋과 릴리스는 긍정적이지만, 빠른 변화는 도입 팀에게 테스트 자동화와 업그레이드 전략을 요구한다.

전망을 정리하면, 에이전트 UI 프로토콜은 MCP나 A2A를 대체하는 흐름이 아니라 그 다음 계층을 채우는 흐름이다. MCP가 에이전트에게 도구를 주고, A2A가 에이전트끼리 협업하게 한다면, AG-UI는 그 결과를 사용자가 신뢰할 수 있는 제품 경험으로 바꾸려는 시도다. 이 계층이 성숙하지 않으면 기업 AI는 계속 “사이드바 챗봇”에 머물 가능성이 높다. 반대로 이 계층이 안정화되면 에이전트는 화면 밖의 실험 기능이 아니라 제품의 핵심 워크플로 안으로 들어올 수 있다.

## 결론: 오늘의 흐름은 “AI 채팅”에서 “에이전트 운영 UX”로 이동 중이다

CopilotKit이 GitHub Trending에서 주목받은 이유는 단순히 프런트엔드 개발자가 쓸 수 있는 AI 컴포넌트가 늘어났기 때문이 아니다. 더 큰 의미는 에이전트 생태계가 모델과 도구 호출을 넘어, **사용자 화면·공유 상태·승인·감사·복구를 포함한 운영 UX**를 고민하기 시작했다는 데 있다. 기업이 AI 에이전트를 실제 업무에 넣으려면 사용자가 무엇을 보고, 무엇을 승인하며, 어떤 상태가 어떻게 바뀌었는지 설명할 수 있어야 한다.

따라서 CopilotKit과 AG-UI를 검토하는 팀은 먼저 자사의 AI 기능이 어느 단계에 있는지 판단해야 한다. 단순 검색과 답변이면 가벼운 SDK가 충분하다. 그러나 에이전트가 제품 화면에서 상태를 읽고, UI를 제안하고, 업무 시스템을 호출하며, 사람이 중간에 개입해야 한다면 에이전트 UI 계층을 별도로 설계해야 한다. 이때 CopilotKit은 유력한 후보 중 하나이며, AG-UI는 앞으로 에이전트와 제품 인터페이스의 경계를 논의할 때 자주 등장할 프로토콜 후보로 볼 만하다.

오늘 확인한 GitHub Trending 스냅샷은 AI 오픈소스 관심사가 또 다른 단계로 이동하고 있음을 보여준다. 에이전트가 많아질수록 경쟁력은 “모델을 얼마나 잘 부르는가”에서 “그 에이전트를 사용자의 업무 흐름 안에 얼마나 안전하고 설명 가능하게 배치하는가”로 옮겨간다. CopilotKit과 AG-UI의 부상은 바로 그 전환을 보여주는 신호다.

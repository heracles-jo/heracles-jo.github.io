## WiFi 센싱은 무엇을 바꾸는가

WiFi 센싱의 기반이 되는 개념은 CSI, 즉 Channel State Information입니다. 무선 신호는 송신기와 수신기 사이를 직선으로만 이동하지 않습니다. 벽, 가구, 사람, 문, 유리, 금속 표면에 반사되고 흡수되고 산란됩니다. 사람이 방 안에 들어오거나, 움직이거나, 숨을 쉬면 이 무선 채널의 상태가 미세하게 달라집니다. CSI는 이런 변화를 수치로 관찰할 수 있는 단서가 됩니다.

기존 공간 감지는 보통 세 가지 방식에 의존했습니다. 첫째, 카메라입니다. 정보량이 풍부하지만 프라이버시 부담이 큽니다. 둘째, PIR 같은 모션 센서입니다. 저렴하지만 정지 상태의 사람이나 세밀한 움직임을 파악하기 어렵습니다. 셋째, 웨어러블입니다. 생체 신호 측정에는 좋지만 사용자가 장치를 착용해야 합니다.

WiFi 센싱은 이 세 방식의 빈틈을 노립니다. 카메라처럼 이미지를 저장하지 않고, 모션 센서보다 더 미세한 변화를 읽으려 하며, 웨어러블 없이도 특정 상태를 추정하려 합니다. 물론 이것이 곧 완벽한 대체재라는 뜻은 아닙니다. 전파 환경은 복잡하고, 공간 구조와 장비 배치에 민감하며, 추정 정확도는 실험 조건에 따라 크게 달라질 수 있습니다. RuView README도 베타 소프트웨어이며 API와 펌웨어가 바뀔 수 있고, 일부 정확도 지표는 아직 제한적이라고 명시합니다.

## 왜 지금 오픈소스에서 주목받는가

이 흐름이 지금 다시 주목받는 배경에는 몇 가지 현실적인 이유가 있습니다.

첫째, 저가 엣지 하드웨어가 충분히 강해졌습니다. ESP32 계열 장비처럼 저렴하고 널리 보급된 MCU와 무선 칩은 실험 장벽을 크게 낮춥니다. 과거에는 무선 신호 분석이 연구실 장비나 전용 하드웨어의 영역이었다면, 이제는 개발자가 집이나 사무실에서 직접 PoC를 만들 수 있습니다.

둘째, 엣지 컴퓨팅과 로컬 처리가 중요해졌습니다. 공간 데이터는 민감합니다. 클라우드로 원시 데이터를 계속 보내기보다 현장 장비에서 이벤트를 추출하고 필요한 결과만 전송하는 방식이 선호됩니다. WiFi 센싱도 마찬가지입니다. 원시 CSI 데이터를 모두 저장하고 전송하는 구조보다는, 엣지에서 존재 여부나 이상 움직임 같은 이벤트로 변환한 뒤 정책 계층을 거쳐 업무 시스템에 전달하는 설계가 더 현실적입니다.

셋째, 카메라 피로도가 커졌습니다. 사무실, 매장, 공장, 학교, 병원 어디에서나 카메라는 강력하지만 부담스러운 센서입니다. 얼굴, 행동, 위치, 관계가 너무 많이 드러나기 때문입니다. “카메라 없는 감지”는 프라이버시 친화적인 대안처럼 보입니다. 다만 여기서 함정이 있습니다. 카메라가 아니라고 해서 자동으로 프라이버시 문제가 사라지는 것은 아닙니다. 보이지 않는 센서일수록 사용자는 자신이 감지되고 있다는 사실을 모를 수 있습니다.

## 실무 적용 가능성이 높은 영역

WiFi 센싱이 가장 먼저 의미를 가질 수 있는 곳은 “정확한 식별”보다 “상태 변화 감지”가 중요한 영역입니다. 예를 들어 사무실에서는 회의실 재실 여부, 야간 침입 징후, 에너지 절감을 위한 공간 점유율 추정에 활용할 수 있습니다. 물류창고나 공장에서는 특정 구역의 움직임, 비정상 정지, 위험 구역 접근을 감지하는 보조 신호가 될 수 있습니다.

요양시설이나 독거노인 돌봄에서는 더 민감하지만 큰 가능성이 있습니다. 카메라를 설치하기 어려운 침실이나 욕실 주변에서 움직임 패턴, 장시간 무동작, 호흡 변화 같은 이벤트를 감지할 수 있다면 안전 관리에 도움이 될 수 있습니다. 그러나 이 영역에서는 의료기기 오해, 오탐/미탐 책임, 보호자 동의, 데이터 보관 정책이 특히 중요합니다.

| 적용 영역 | 기대 효과 | 주의할 점 |
|---|---|---|
| 스마트 오피스 | 재실 기반 조명·공조 최적화, 회의실 사용률 측정 | 개인 추적이 아닌 집계 지표 중심 설계 |
| 물류/공장 | 위험 구역 접근, 비정상 정지, 야간 움직임 감지 | 안전 시스템의 단독 근거로 쓰지 않기 |
| 요양/돌봄 | 장시간 무동작, 낙상 의심, 수면 중 호흡 변화 보조 감지 | 의료 판단으로 오해하지 않도록 고지와 검증 필요 |
| 보안 관제 | 어두운 공간이나 벽 너머 움직임에 대한 보조 신호 | 오탐 대응 절차와 다른 센서와의 교차 확인 |
| 에너지 관리 | 실제 점유율 기반 냉난방 제어 | 센서 장애 시 기본 정책과 수동 제어 확보 |

핵심은 WiFi 센싱을 “정답을 말하는 시스템”으로 도입하지 않는 것입니다. 실무에서는 보조 신호로 시작하는 편이 안전합니다. 카메라, 출입 기록, BLE, 환경 센서, 업무 이벤트와 함께 보고, 일정 수준 이상 신뢰도가 확인된 영역부터 자동화 범위를 넓혀야 합니다.

## 운영 아키텍처: 센서보다 정책 계층이 중요하다

많은 IoT 프로젝트가 실패하는 이유는 센서 데모는 성공했지만 운영 구조가 없기 때문입니다. WiFi 센싱도 마찬가지입니다. ESP32 노드가 CSI를 수집하고, 모델이 움직임을 추정하고, 대시보드에 멋진 그래프가 뜨는 것만으로는 부족합니다. 운영 환경에서는 다음 질문이 더 중요합니다.

1. 센서가 오프라인이면 누가 알 수 있는가?
2. 전파 간섭으로 품질이 낮아졌을 때 판단을 보류할 수 있는가?
3. 공간 구조가 바뀌면 재학습 또는 재보정 절차가 있는가?
4. 원시 데이터와 이벤트 데이터의 보관 기간은 다른가?
5. 알림이 반복적으로 오탐일 때 운영자가 임계값을 조정할 수 있는가?
6. 사용자는 감지 사실과 목적을 이해하고 동의했는가?

실무 아키텍처는 센서 수집, 신호 처리, 엣지 추론, 이벤트 API, 정책 계층, 관측 계층으로 나누는 편이 좋습니다. 특히 정책 계층은 단순 옵션이 아닙니다. 어떤 이벤트를 저장할지, 누가 볼 수 있는지, 어떤 조건에서 알림을 보낼지, 어떤 데이터는 즉시 폐기할지 결정하는 핵심 계층입니다.

## 리스크: “카메라가 아니니 괜찮다”는 착각

WiFi 센싱은 카메라보다 덜 침습적으로 느껴질 수 있습니다. 하지만 보이지 않는다는 점 때문에 오히려 더 조심해야 합니다. 카메라는 물리적으로 보이고, 사용자는 촬영 중임을 비교적 쉽게 인지합니다. 반면 WiFi 센싱은 공유기나 작은 IoT 노드만으로 동작할 수 있어 사용자가 감지 여부를 인식하기 어렵습니다.

![WiFi 센싱 도입 체크리스트](https://heracles-jo.github.io/assets/img/posts/github-trending-wifi-sensing-spatial-intelligence/checklist.svg)

| 리스크 | 왜 중요한가 | 대응 방향 |
|---|---|---|
| 비가시적 감지 | 사용자가 자신이 감지되는지 모를 수 있음 | 명확한 고지, 표지, 동의 절차 |
| 오탐/미탐 | 안전·보안 판단에서 잘못된 대응을 유발 | 다른 센서와 교차 검증, 신뢰도 표시 |
| 생체 신호 오해 | 호흡/심박 추정이 의료 판단으로 받아들여질 수 있음 | 의료 목적 제한 고지, 전문가 검증 전 자동 판단 금지 |
| 원시 데이터 보관 | CSI 데이터도 공간 패턴과 행동 정보를 포함할 수 있음 | 최소 수집, 짧은 보관, 암호화, 접근 감사 |
| 환경 의존성 | 가구 배치, 벽, 사람 수, AP 위치에 따라 성능 변동 | 설치 기준, 재보정, 품질 모니터링 |
| 보안 취약점 | 센서 노드 탈취 시 공간 이벤트가 노출될 수 있음 | 펌웨어 업데이트, 네트워크 분리, 키 관리 |

특히 조직 내부에 도입할 때는 직원 감시 도구로 오해받지 않도록 목적과 범위를 명확히 해야 합니다. “업무 효율”이라는 이름으로 개인의 위치와 움직임을 과도하게 추적하면 기술적 성공과 별개로 조직 신뢰를 잃을 수 있습니다.

## 도입 체크리스트

WiFi 센싱을 PoC로 검토하는 팀이라면 다음 순서로 접근하는 것이 좋습니다.

1. **문제 정의**: 사람을 식별하려는 것인가, 공간의 상태만 알고 싶은 것인가?
2. **대체 기술 비교**: 카메라, PIR, BLE, 초음파, UWB, 출입 기록보다 나은 이유가 있는가?
3. **데이터 최소화**: 원시 CSI를 저장해야 하는가, 이벤트만 저장해도 충분한가?
4. **동의와 안내**: 감지 구역, 목적, 보관 기간을 사용자에게 설명할 수 있는가?
5. **성능 검증**: 실제 공간에서 오탐/미탐률, 지연, 장애율을 측정했는가?
6. **운영 절차**: 센서 장애, 펌웨어 업데이트, 재보정, 알림 피로도를 관리할 수 있는가?
7. **자동화 범위 제한**: 초기에는 알림과 보조 판단에만 쓰고, 직접 제어는 단계적으로 확대하는가?
8. **보안 설계**: 센서 네트워크를 업무망과 분리하고, 접근 키와 로그를 관리하는가?

이 체크리스트의 핵심은 “무엇을 할 수 있는가”보다 “어디까지 해도 되는가”입니다. 공간 감지 기술은 사람의 생활과 업무 환경에 직접 들어오기 때문에, 기능 데모보다 사회적 수용성과 운영 책임이 더 빨리 병목이 됩니다.

RuView 같은 프로젝트가 GitHub Trending에 오른 것은 오픈소스의 역할이 애플리케이션과 개발 도구를 넘어 물리 공간 인프라로 확장되고 있음을 보여줍니다. 과거의 오픈소스 IoT는 센서를 연결하고 대시보드를 만드는 데 초점이 많았습니다. 이제는 무선 신호, 엣지 추론, 실시간 이벤트, 프라이버시 정책까지 함께 다뤄야 합니다.

다만 스타 수가 높다고 해서 즉시 프로덕션 도입이 가능하다는 뜻은 아닙니다. 오히려 이런 프로젝트일수록 README의 한계와 베타 고지를 자세히 읽어야 합니다. RuView README도 일부 ESP32 모델 제약, 다중 노드 권장, 카메라 없는 포즈 정확도의 제한, 향후 데이터 수집과 평가 필요성을 언급합니다. 이런 투명성은 긍정적이지만, 도입자는 그 한계를 운영 설계에 반영해야 합니다.

## 개인적인 결론

오늘의 GitHub Trending은 오픈소스 흐름이 AI 에이전트와 개발 도구에만 갇혀 있지 않다는 점을 보여줍니다. RuView가 던지는 질문은 더 넓습니다. 이미 우리 주변에 있는 무선 인프라가 단순 연결을 넘어 공간의 상태를 이해하는 센서가 된다면, 우리는 그 데이터를 어떻게 다뤄야 할까요?

기술적으로는 흥미롭습니다. 카메라 없이 재실을 파악하고, 웨어러블 없이 움직임과 호흡을 추정하고, 저가 엣지 장비로 공간 이벤트를 만들 수 있다면 스마트 공간의 비용 구조가 달라질 수 있습니다. 하지만 운영적으로는 신중해야 합니다. 보이지 않는 센서는 사용자의 통제감을 낮출 수 있고, 부정확한 추정은 안전과 신뢰 문제로 이어질 수 있습니다.

따라서 WiFi 센싱을 보는 가장 균형 잡힌 관점은 이것입니다. **카메라를 대체하는 마법 기술이 아니라, 공간 운영을 위한 새로운 보조 신호 계층**입니다. 이 계층은 프라이버시를 줄일 수도 있고, 반대로 새로운 감시 위험을 만들 수도 있습니다. 차이는 기술 자체보다 도입 목적, 데이터 최소화, 설명 가능성, 운영 통제에서 결정됩니다.

GitHub Trending의 오늘 신호는 명확합니다. 오픈소스는 이제 코드 안의 자동화뿐 아니라, 우리가 머무는 물리 공간을 이해하는 방식까지 바꾸고 있습니다. 다음 경쟁력은 더 많은 센서를 설치하는 것이 아니라, 이미 존재하는 신호에서 필요한 정보만 책임 있게 추출하는 능력에서 나올 것입니다.

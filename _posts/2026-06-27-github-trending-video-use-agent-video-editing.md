[video-use](https://github.com/browser-use/video-use)는 “에이전트에게 영상을 보여 주고 알아서 편집하게 한다”는 제품보다 훨씬 구체적이다. 이 프로젝트의 핵심은 원본 프레임 전체를 멀티모달 모델에 밀어 넣는 대신, **단어 단위 타임스탬프가 있는 전사문을 주된 편집 인터페이스로 사용하고 필요한 구간만 시각화한 뒤, 편집 결정 목록(EDL)을 ffmpeg 렌더링으로 확정하는 구조**다. 대화형 UX가 앞에 있지만 실제 가치의 중심은 transcript, EDL, 렌더러, 검증 산출물을 분리한 파이프라인에 있다.

2026년 11월 17일 [GitHub API 스냅샷](https://api.github.com/repos/browser-use/video-use)과 기본 브랜치를 다시 확인했을 때 `browser-use/video-use`는 약 3.1만 stars, 3,600 forks, MIT 라이선스의 Python 프로젝트였고, 최신 확인 커밋은 2026년 10월 8일이었다. 숫자는 계속 변하므로 인기도의 보증으로 읽으면 안 된다. 더 중요한 사실은 저장소가 `SKILL.md`만 제공하는 프롬프트 모음이 아니라 `transcribe.py`, `pack_transcripts.py`, `timeline_view.py`, `render.py`, `grade.py`와 렌더링 테스트를 함께 둔 실행 가능한 편집 도구라는 점이다.

이 글의 결론부터 말하면, video-use는 Premiere Pro나 DaVinci Resolve를 대체하는 범용 NLE라기보다 **말 중심 영상의 반복 편집을 코드와 에이전트 절차로 표준화하는 참조 구현**에 가깝다. 제품 데모, 인터뷰, 튜토리얼, 발표 영상처럼 음성이 편집 구조를 주도하는 작업에는 설득력이 있다. 반대로 음악 리듬, 배우의 미세한 표정, 복잡한 멀티캠 연속성, 정교한 색보정이 중심인 작업에서는 사람 편집자의 감각과 기존 NLE가 여전히 주도권을 가진다.

## video-use가 실제로 자동화하는 범위

README가 설명하는 기본 흐름은 `Transcribe → Pack → LLM Reasons → EDL → Render → Self-Eval`이다. 사용자는 원본 영상을 폴더에 넣고 편집 목적을 대화로 설명한다. 에이전트는 소스를 조사하고 전략을 제안하며, 사용자가 승인한 뒤 컷과 자막, 색보정, 오버레이를 만든다. 결과는 원본 폴더 아래 `edit/`에 남고, 최종 산출물은 `final.mp4`다.

겉으로 보면 자연어 명령으로 영상을 편집하는 단순한 구조지만, 내부 책임은 다음처럼 나뉜다.

| 계층 | 주요 산출물 | 운영상 의미 |
|---|---|---|
| 입력 조사 | `ffprobe` 결과, 원본 목록 | 해상도·프레임률·길이·코덱을 먼저 고정한다 |
| 음성 인덱싱 | 소스별 전사 JSON | 단어 경계, 화자, 음성 이벤트를 시간축에 연결한다 |
| 컨텍스트 압축 | `takes_packed.md` | 여러 테이크를 LLM이 읽을 수 있는 작은 편집 표면으로 바꾼다 |
| 편집 결정 | `edl.json` | 어떤 원본의 어느 구간을 왜 선택했는지 구조화한다 |
| 결정적 렌더링 | `render.py`, ffmpeg | 승인된 결정을 실제 영상·자막·오버레이로 합성한다 |
| 품질 확인 | `timeline_view`, `ffprobe`, 음량 측정 | 컷 경계, 자막 가림, 길이, 오디오 이상을 검사한다 |
| 세션 연속성 | `project.md` | 다음 편집 세션이 앞선 결정과 미해결 항목을 이어받는다 |

이 분리는 중요하다. LLM이 곧 렌더러인 구조에서는 “모델이 그렇게 판단했다”는 설명밖에 남지 않는다. video-use에서는 모델이 편집 결정을 만들고, ffmpeg가 그 결정을 실행하며, EDL과 중간 파일이 결과를 추적할 수 있게 한다. [AI 네이티브 비디오 편집 워크플로 글](/posts/github-trending-ai-native-video-editor-workflow/)에서 타임라인을 운영 원장으로 봤다면, video-use는 그 원장을 JSON 기반 EDL과 디렉터리 산출물로 구현한 사례다.

![코딩 에이전트가 영상 편집 작업을 단계적으로 수행하는 video-use 분석](https://heracles-jo.github.io/assets/img/posts/github-trending-video-use-agent-video-editing/architecture.svg)

## 프레임 전체가 아니라 전사문을 읽는 이유

README는 “LLM은 영상을 보지 않고 읽는다”고 설명한다. 항상 로드되는 첫 번째 계층은 ElevenLabs Scribe로 얻은 단어 단위 전사문이고, 두 번째 계층은 특정 구간의 필름스트립·파형·단어 레이블을 한 이미지로 만드는 `timeline_view`다. 시각 자료는 모든 프레임을 훑는 용도가 아니라 애매한 멈춤, 재촬영 비교, 컷 경계 확인 같은 결정 지점에서만 사용한다.

이 접근의 장점은 세 가지다. 첫째, 긴 영상을 프레임 단위로 모델에 넣는 비용을 피한다. 둘째, 대화형 영상에서 실제 컷 후보가 되는 단어 경계와 침묵 구간을 직접 사용할 수 있다. 셋째, 같은 원본은 다시 전사하지 않고 캐시하므로 수정 라운드가 늘어도 분석 비용을 반복하지 않는다.

다만 “전사문이 영상의 충분한 표현”이라는 전제는 콘텐츠에 따라 달라진다. 말하는 사람의 표정이 문장보다 중요한 인터뷰, 화면 시연과 내레이션의 동기화가 핵심인 튜토리얼, B-roll의 공간 연속성이 필요한 여행 영상에서는 텍스트만으로 컷의 질을 판단하기 어렵다. 따라서 이 구조를 범용 비디오 이해 모델로 과장하기보다, **음성 중심 편집에서 비싼 시각 추론을 필요한 순간으로 미루는 최적화**로 보는 편이 정확하다.

## EDL과 렌더러가 만드는 재현성

video-use의 가장 실무적인 설계는 편집 결과를 자연어 대화에만 남기지 않고 `edl.json`으로 내보내는 것이다. EDL에는 소스 경로, 시작·종료 시각, 장면의 역할, 선택 이유, 색보정, 오버레이, 자막 파일, 예상 총 길이가 들어간다. 동일한 원본과 EDL, 같은 렌더링 환경이 있으면 결과를 다시 만들 수 있는 기반이 된다.

저장소의 `SKILL.md`는 제작 오류를 막기 위한 12개 하드 룰을 둔다. 예를 들어 자막은 오버레이 뒤에 마지막으로 합성해야 하고, 컷은 단어 중간이 아니라 전사 타임스탬프의 단어 경계에 맞춰야 하며, 컷 양쪽에는 전사 오차를 흡수할 작은 패딩을 둔다. 각 세그먼트 경계에는 짧은 오디오 페이드를 넣고, 자막 타임코드는 원본 시간이 아니라 합쳐진 출력 타임라인 기준으로 다시 계산한다.

이 규칙들은 창작 취향이 아니라 렌더링 불량을 막는 불변 조건이다. “따뜻한 색감이 좋은가”는 사람이 결정할 문제지만, 오버레이가 자막을 가리거나 concat 이후 자막이 밀리는 것은 명백한 결함이다. 에이전트 시스템을 운영하려면 이런 식으로 **취향 판단과 기계적으로 검증할 정확성 조건을 분리**해야 한다. 이는 장기 작업을 계획·실행·검증 단계로 나눠야 한다는 [DeerFlow 에이전트 워크플로 분석](/posts/github-trending-deer-flow-long-horizon-agent-workflow/)과 같은 원리다.

재현성에는 한계도 있다. EDL이 같아도 ffmpeg 버전, 폰트 파일, OS별 인코더, 외부 애니메이션 패키지, 웹 폰트 로딩 상태가 달라지면 픽셀 단위 결과는 달라질 수 있다. 프로덕션에서 사용한다면 다음 항목을 EDL과 함께 잠가야 한다.

- ffmpeg와 Python 의존성 버전
- 폰트 파일과 폰트 인덱스
- Remotion·HyperFrames·Manim 등 선택적 애니메이션 도구 버전
- 출력 해상도, 프레임률, 코덱, 픽셀 포맷, CRF
- 외부 API 모델과 전사 옵션
- 원본 파일의 해시 또는 불변 객체 경로

즉 Git에 `edl.json`만 넣는 것으로는 충분하지 않다. 컨테이너 이미지나 lockfile, 원본 자산 식별자를 함께 보존해야 실제 재현성이 생긴다.

## self-eval은 품질 보증이 아니라 결함 탐지 보조다

video-use는 렌더 결과의 모든 컷 경계 주변을 `timeline_view`로 다시 확인하고, 첫 2초와 마지막 2초, 중간 샘플을 검사하도록 지시한다. 길이는 `ffprobe`로 EDL 예상값과 비교하고, 오디오는 `ebur128`로 통합 음량과 true peak를 측정한다. 문제가 있으면 수정·재렌더·재평가하되 최대 세 번에서 멈추게 한다.

이 루프는 좋은 설계다. 특히 **원본이 아니라 렌더된 결과를 검사한다**는 점이 중요하다. 원본 컷이 올바르더라도 합성 과정에서 자막이 가려지거나 오버레이 시간이 밀리고 오디오 팝이 생길 수 있기 때문이다. 그러나 self-eval이라는 이름을 “영상이 좋다는 것을 에이전트가 인증한다”로 해석하면 안 된다.

현재의 검증은 다음 결함에는 비교적 강하다.

- 컷 경계의 시각적 플래시와 큰 점프
- 오디오 경계의 비정상적인 피크
- 오버레이와 자막의 레이어 순서 오류
- 예상 길이와 실제 길이의 불일치
- 구간별 음량 차이가 지나치게 큰 문제

반면 다음 판단은 자동화하기 어렵다.

- 이야기의 핵심이 살아 있는가
- 말하는 사람의 의도와 감정이 왜곡되지 않았는가
- 브랜드 톤이 자연스러운가
- 농담이나 침묵의 타이밍이 적절한가
- 음악과 화면이 실제 청취 환경에서 편안한가
- 자막이 언어·문화적 맥락을 정확히 전달하는가

특히 에이전트는 실제로 오디오를 듣는 것이 아니라 수치를 측정한다. 음량 규격을 통과한 믹스가 반드시 듣기 좋은 믹스는 아니다. 공개용 영상이라면 이어폰, 휴대전화 스피커, 데스크톱 환경에서 사람이 끝까지 재생해 보는 최종 QC가 필요하다.

## 보안과 개인정보: 가장 먼저 볼 것은 전사 경로다

video-use의 설치 문서는 ElevenLabs API 키를 저장소 루트의 `.env`에 두고 Scribe 전사에 사용하도록 한다. 이 말은 원본 영상의 오디오가 외부 전사 서비스로 전송될 수 있다는 뜻이다. 고객 인터뷰, 미공개 제품 발표, 사내 회의, 의료·법률 상담처럼 민감한 음성이 포함되면 편집 편의보다 데이터 처리 계약과 보존 정책을 먼저 검토해야 한다.

실무에서는 최소한 다음 경계를 문서화해야 한다.

1. 어떤 원본을 외부 전사 API에 보낼 수 있는가.
2. 전사 결과와 원본 미디어가 어디에 저장되고 언제 삭제되는가.
3. `.env`와 API 키가 백업·로그·에이전트 대화에 노출되지 않는가.
4. 에이전트가 접근할 수 있는 디렉터리를 원본 작업 폴더로 제한했는가.
5. 온라인 소스를 받는 `yt-dlp` 사용 시 저작권과 이용 약관을 확인했는가.
6. 외부 스킬 업데이트를 검토하고 특정 커밋 또는 릴리스에 고정했는가.
7. 렌더링에 쓰는 Node·Python 패키지와 애니메이션 템플릿의 공급망을 스캔하는가.

`SKILL.md`는 에이전트에게 셸, 파일 시스템, 외부 API, 선택적으로 Node 패키지 설치 권한을 요구한다. 따라서 이는 문서가 아니라 실행 권한을 가진 소프트웨어 공급망 구성요소다. 외부 에이전트 스킬을 코드처럼 검토해야 하는 이유는 [SkillSpector와 에이전트 스킬 보안 글](/posts/github-trending-skillspector-agent-skill-security/)에서 다룬 위험과 직접 연결된다. 저장소를 자동 업데이트하기보다 검토한 커밋을 고정하고, 변경 diff와 테스트를 통과한 뒤 승격하는 방식이 안전하다.

라이선스와 자산 권리도 별개다. video-use 자체는 MIT 라이선스지만, 최종 영상에 들어가는 원본 촬영물, 스톡 영상, 음악, 폰트, 생성형 이미지·비디오의 권리는 자동으로 해결되지 않는다. 오픈소스 편집 도구의 라이선스와 결과물 자산의 사용권을 혼동하면 안 된다.

## 운영 비용은 모델 토큰보다 미디어 처리에서 커질 수 있다

video-use는 전체 프레임을 모델에 보내지 않아 LLM 컨텍스트 비용을 줄이는 방향을 택했다. 하지만 전체 비용은 전사 API, 로컬 또는 클라우드 렌더링, 애니메이션 생성, 저장 공간, 사람 검수 시간을 합쳐 계산해야 한다. 특히 4K 원본과 여러 테이크를 다루면 중간 세그먼트와 프리뷰가 원본 용량의 몇 배로 늘어날 수 있다.

PoC에서는 영상 한 편의 총비용을 다음처럼 분해하는 것이 좋다.

- 원본 1분당 전사 비용과 전사 대기 시간
- 프리뷰·최종 렌더 횟수와 총 렌더 시간
- `edit/` 디렉터리의 최대 저장 용량
- 애니메이션 슬롯별 생성·수정 시간
- 사람이 전략 승인과 최종 QC에 사용한 시간
- 자동 컷 이후 NLE에서 다시 수정한 비율
- 승인된 최종 1분당 전체 비용

“첫 결과가 빨리 나왔다”보다 **최종 승인까지 걸린 왕복 횟수**가 더 중요한 지표다. 자동 초안이 10분 만에 나와도 사람이 두 시간 동안 자막과 컷을 다시 고친다면 도입 효과가 작다.

## 기존 편집 방식과의 선택 기준

| 선택지 | 강점 | 약점 | 적합한 작업 |
|---|---|---|---|
| 전통 NLE | 정교한 타임라인, 색보정, 오디오, 플러그인 생태계 | 반복 작업의 스크립트화와 대량 변형이 어렵다 | 광고, 다큐, 방송, 복잡한 멀티캠 |
| 직접 작성한 ffmpeg 파이프라인 | 결정적이고 CI에 넣기 쉽다 | 기획과 컷 선택을 사람이 코드로 표현해야 한다 | 템플릿 영상, 정형 리포트, 포맷 변환 |
| video-use | 자연어 전략과 EDL·렌더링을 연결한다 | 전사 서비스 의존, 말 중심 편집 편향, 초기 도구 성숙도 | 제품 데모, 인터뷰, 튜토리얼, 반복 숏폼 |
| 생성형 비디오 서비스 | 없는 장면을 빠르게 만든다 | 소스 편집·승인·자산 추적이 약할 수 있다 | 콘셉트 시안, 짧은 생성 클립 |

video-use가 잘 맞는 팀은 원본 촬영은 계속 사람이 하되, 반복되는 테이크 정리와 자막, 숏폼 변형, 제품 데모 초안을 표준화하려는 팀이다. 개발자 릴레이션, 교육 콘텐츠, 내부 커뮤니케이션, 창업팀의 릴리스 영상이 대표적이다. 반대로 편집자의 손맛이 제품 품질 자체인 스튜디오, 오프라인·폐쇄망 처리가 필수인 조직, 전사 정확도가 낮은 다국어·소음 환경, 법적 승인 체계가 없는 조직은 도입을 서두르지 않는 편이 낫다.

## 2주 PoC를 설계하는 방법

![코딩 에이전트가 영상 편집 작업을 단계적으로 수행하는 video-use 분석 체크리스트](https://heracles-jo.github.io/assets/img/posts/github-trending-video-use-agent-video-editing/checklist.svg)

도입 검증은 화려한 샘플 하나보다 같은 유형의 영상 세 편을 반복 제작하는 방식이 낫다.

### 1. 범위를 고정한다

- 3~5분 분량의 제품 데모나 인터뷰 한 종류만 선택한다.
- 출력 비율, 자막 스타일, 목표 길이, 금지 표현을 문서화한다.
- 수동 편집 기준선과 video-use 결과를 같은 원본으로 비교한다.

### 2. 재현성을 기록한다

- 원본 해시, EDL, 전사 JSON, `project.md`, 렌더 명령을 보존한다.
- ffmpeg·Python·Node 의존성을 고정한다.
- 동일 EDL을 두 번 렌더해 길이, 스트림 정보, 프레임률이 같은지 확인한다.

### 3. 실패를 일부러 만든다

- 겹치는 발화, 긴 침묵, 빠른 말, 외래어, 화면 시연이 포함된 샘플을 넣는다.
- 자막과 오버레이가 같은 위치를 쓰는 장면을 만든다.
- API 실패, 디스크 부족, 폰트 누락, 중단된 렌더 후 재개 절차를 시험한다.

### 4. 보안 경계를 검증한다

- 테스트용 별도 API 키와 최소 권한 작업 계정을 사용한다.
- 에이전트가 작업 폴더 밖의 파일을 읽거나 쓰지 못하게 제한한다.
- 외부 API로 전송되는 데이터와 로그에 남는 메타데이터를 확인한다.
- 스킬·도우미 스크립트의 버전을 고정하고 업데이트 승인 절차를 만든다.

### 5. 성공 기준을 수치로 정한다

- 최종 승인까지 걸린 사람 시간 30% 이상 감소
- 자막 타이밍 수동 수정 구간 비율
- 자동 컷 유지율과 NLE 재편집 비율
- 컷 경계 오디오 결함 건수
- 영상 1분당 전체 처리비용
- 세 편 연속으로 동일 절차를 재현할 수 있는지

이 기준을 통과해도 전사 편집 시스템 전체를 교체할 필요는 없다. 가장 반복적이고 실패 비용이 낮은 콘텐츠 유형부터 운영 레인 하나를 만드는 것이 현실적이다.

## 판단: video-use의 가치는 ‘AI 편집자’보다 편집 계약에 있다

video-use가 보여 주는 중요한 변화는 영상이 코드가 되었다는 선언 자체가 아니다. 더 정확히는 **편집 의도는 자연어로 받고, 결정은 EDL로 고정하며, 렌더링은 결정적 도구에 맡기고, 결과는 별도 검증 단계에서 확인하는 계약**이 등장했다는 점이다. 이 계약이 있으면 에이전트를 교체해도 원본과 편집 산출물의 구조를 유지할 수 있고, 사람이 개입해야 할 승인 지점도 명확해진다.

따라서 도입 판단에서 stars나 데모의 인상보다 세 가지를 보자. 첫째, 우리 콘텐츠가 음성 중심 편집에 맞는가. 둘째, 외부 전사와 에이전트 권한을 감당할 보안 경계가 있는가. 셋째, EDL·버전·검증 결과를 남겨 같은 영상을 다시 만들 수 있는가. 세 질문에 답할 수 있다면 video-use는 반복 영상 제작을 줄이는 유용한 기반이 된다. 답할 수 없다면 자연어 UI가 편리해도 운영 가능한 편집 시스템이라고 부르기 어렵다.

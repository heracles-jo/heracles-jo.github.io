GitHub Trending에서 새롭게 주목받은 [tamnd/kage](https://github.com/tamnd/kage)는 겉으로 보면 “웹사이트를 오프라인으로 저장하는 CLI”에 가깝다. 그러나 실무 관점에서 더 중요한 키워드는 단순 저장이 아니라 **렌더링 이후 JavaScript 제거**, **로컬 자산 재배치**, **ZIM 단일 파일 패키징**, 그리고 **장기 재현성**이다. 오늘 확인한 공개 스냅샷 기준으로 kage는 2026년 6월 14일 생성된 비교적 신생 저장소임에도 약 1.8천 개 이상의 스타, 50개 이상의 포크, 2026년 6월 17일 기준 `v0.3.4` 릴리스와 같은 빠른 활동 신호를 보였다. 이 수치는 확인 시점의 GitHub 공개 API 스냅샷이며, Trending 순위와 스타 수는 시간에 따라 변동될 수 있다.

최근 웹은 문서라기보다 원격 실행 애플리케이션에 가까워졌다. 내부 위키, 제품 문서, 연구 자료, 교육 콘텐츠, 법무·감사 증빙 페이지까지 “Save As”로 저장해도 몇 달 뒤 열어 보면 빈 화면, 로딩 스피너, 만료된 API 호출, 끊긴 CDN, 동의 배너만 남는 일이 흔하다. kage가 Trending에 오른 배경은 이 불편을 정면으로 찌른다. 브라우저가 실제로 본 DOM을 먼저 만든 다음 실행 코드를 걷어내고, HTML·CSS·이미지·폰트를 로컬 경로로 가져와 “더 이상 외부 서비스를 호출하지 않는 사본”을 만든다는 접근은 기업의 지식 보존, 규제 대응, 오프라인 교육 배포, 장기 레퍼런스 관리에서 꽤 현실적인 의미를 갖는다.

## 왜 지금 kage가 GitHub Trending에 올랐나

오늘 후보로 함께 본 저장소들은 AI 에이전트 실행 프레임워크, 코드 감사 도구, Lottie 생성 도구, SDR 기반 실시간 항공기 시각화처럼 각기 다른 흐름을 보여줬다. 그중 kage를 선택한 이유는 기존 블로그에서 최근 다룬 AI 에이전트, 로컬 AI, 클라우드 네이티브 운영, 웹 툴체인 주제와 겹치지 않으면서도 “동적 웹의 보존 가능성”이라는 별도의 기술 흐름을 선명하게 보여주기 때문이다. 특히 kage는 [README](https://github.com/tamnd/kage)에 “real headless Chrome으로 페이지를 열고, 안정화 후 사람이 본 DOM을 스냅샷으로 잡고, 모든 JavaScript를 제거한다”고 설명한다. 이는 단순 크롤러나 정적 사이트 미러링과 다르다.

웹 아카이빙은 오래된 문제지만, 지금 다시 중요해진 이유는 세 가지다. 첫째, SaaS와 프론트엔드 프레임워크 의존도가 높아지면서 문서 페이지조차 런타임 API·번들·인증 상태에 강하게 묶였다. 둘째, 기업 내부의 지식 자산은 노션, Confluence, GitHub Pages, 사내 포털, 각종 벤더 문서로 분산되어 있으며 퇴사·계약 종료·서비스 변경에 취약하다. 셋째, AI 검색과 RAG가 확산되면서 “언제 수집한 어떤 버전의 문서인가”를 재현 가능한 형태로 남기는 요구가 커졌다. kage는 이 중 특히 첫 번째와 두 번째 문제에 대해 가볍고 명확한 해법을 제시한다.

또 하나의 신호는 릴리스와 커밋 속도다. 공개 API 확인 시점 기준 kage는 `v0.3.3`, `v0.3.4` 릴리스가 연이어 올라왔고, ZIM 검색 인덱스나 페이지 제목 저장 방식 같은 기능 개선 커밋이 최근에 반영되어 있었다. 신생 저장소의 빠른 스타 증가는 항상 신중히 봐야 하지만, README의 문제 정의가 명확하고 릴리스 산출물이 존재하며 Go 기반 CLI·컨테이너 실행 경로를 모두 제공한다는 점은 단순 아이디어 저장소보다는 사용 가능한 도구에 가깝다는 신호로 볼 수 있다.

## 핵심 동작 방식: 실행한 뒤 얼리고, 실행 코드는 버린다

kage의 구조를 한 문장으로 요약하면 “웹 애플리케이션을 브라우저로 한 번 실행해 사람이 보는 결과물을 얻고, 그 결과물에서 다시 애플리케이션성을 제거한다”이다. 일반적인 `wget --mirror`나 정적 파일 복사는 서버가 제공하는 HTML과 자산을 가져오지만, SPA나 클라이언트 렌더링 페이지에서는 초기 HTML만으로 의미 있는 콘텐츠가 부족하다. 반면 kage는 Chrome 또는 Chromium을 구동해 페이지가 네트워크 요청과 렌더링을 어느 정도 마친 뒤 DOM을 캡처한다. 그 다음 script 태그와 실행 가능한 JavaScript를 제거하고 CSS·이미지·폰트 같은 정적 자산을 로컬 경로로 재작성한다.

이 방식은 충실도와 안전성 사이에서 독특한 절충점을 만든다. 브라우저를 사용하기 때문에 서버 사이드 HTML만 긁는 방식보다 실제 화면에 가까운 결과를 얻을 수 있다. 동시에 최종 산출물에는 JavaScript가 없으므로 오프라인에서 다시 열 때 추적 스크립트, 원격 API 호출, 광고 코드, 사용자 이벤트 수집 코드가 실행되지 않는다. 교육 자료나 규정 문서처럼 “읽기”가 목적이라면 이 특성은 장점이다. 반대로 검색 필터, 동적 차트, 로그인 후 상호작용, 클라이언트 사이드 계산이 본질인 서비스라면 보존된 사본은 원본 경험을 완전히 대체하지 못한다.

kage가 ZIM 포맷을 언급하는 점도 눈에 띈다. ZIM은 Kiwix 생태계에서 오프라인 지식 배포에 널리 쓰이는 단일 파일 포맷이다. 여러 HTML 파일과 자산을 폴더로 들고 다니는 방식은 간단하지만 배포·동기화·무결성 관리가 번거롭다. 단일 파일로 묶을 수 있으면 교육용 태블릿, 폐쇄망 PC, 장기 보관 스토리지, 현장 엔지니어 노트북에 복사하기 쉬워진다. 따라서 kage의 의미는 “웹페이지 저장”을 넘어 “실행 가능한 웹을 읽기 가능한 지식 패키지로 변환”하는 쪽에 있다.

## 기존 방식과의 비교: ArchiveBox, Browsertrix, Kiwix와 다른 지점

![오프라인 웹 보존 도구 비교](https://heracles-jo.github.io/assets/img/posts/github-trending-kage-offline-web-archive/comparison.svg)

오프라인 웹 보존 영역에는 이미 성숙한 도구들이 있다. [ArchiveBox](https://github.com/ArchiveBox/ArchiveBox)는 북마크, RSS, 히스토리 등 다양한 입력을 받아 HTML, PDF, 스크린샷, WARC 같은 여러 보존 형태를 관리하는 셀프호스팅 아카이브에 가깝다. 조직 단위로 “무엇을 언제 저장했는가”를 계속 축적하고 검색·관리해야 한다면 ArchiveBox가 더 넓은 기능을 제공한다. 대신 운영 컴포넌트가 늘고, 장기 운영을 위한 백업·업그레이드·권한 관리 책임도 따라온다.

[Browsertrix Crawler](https://github.com/webrecorder/browsertrix-crawler)는 고충실도 웹 아카이빙에 더 초점을 둔다. Puppeteer와 브라우저를 이용해 복잡한 사이트를 크롤링하고 WARC/WACZ 같은 웹 아카이브 형식으로 보존하는 전문 도구에 가깝다. 법적 증거, 공공 기록, 연구 목적처럼 원본 웹의 네트워크·리소스 맥락까지 보존해야 하는 경우 Browsertrix 계열이 더 적합할 수 있다. 그러나 모든 팀이 WARC 뷰어와 아카이빙 파이프라인을 운영할 필요는 없다. 읽기 가능한 내부 문서 묶음이 필요하다면 kage의 단순성이 장점이 된다.

[Kiwix](https://github.com/kiwix/kiwix-tools)와 ZIM 생태계는 배포 관점이 강하다. 위키백과나 교육 콘텐츠를 오프라인 단일 파일로 제공하는 데 검증된 모델이다. kage는 이 세계와 웹 크롤링 세계 사이의 간극을 좁히려는 도구로 볼 수 있다. 즉, Kiwix가 “완성된 ZIM을 잘 읽고 배포하는 쪽”에 강하다면, kage는 “현재 웹사이트를 ZIM이나 정적 폴더로 만들기 위한 앞단”을 단순화한다.

결국 선택 기준은 보존의 목표다. 원본 행위와 네트워크 흔적까지 남겨야 하면 WARC 중심 도구가 맞고, 조직형 수집·관리 포털이 필요하면 ArchiveBox가 맞다. 반면 특정 문서 사이트나 공개 레퍼런스를 빠르게 얼려서 오프라인으로 읽게 하려면 kage가 실용적인 출발점이다. “정확히 살아 있는 웹을 재현할 것인가”보다 “미래에도 안전하게 읽을 수 있는 문서로 만들 것인가”가 kage를 평가하는 핵심 질문이다.

## 실무 도입 장점: 폐쇄망, 교육, 감사, RAG 데이터셋

첫 번째 장점은 폐쇄망과 현장 환경이다. 제조·국방·공공·금융 일부 영역에서는 인터넷 연결이 제한된 환경에서 개발자 문서나 벤더 매뉴얼을 봐야 한다. PDF로 변환하면 링크 구조와 검색성이 망가지기 쉽고, 원본 웹을 통째로 가져오면 실행 코드와 외부 호출이 남는다. kage처럼 렌더링 후 JavaScript를 제거한 산출물은 보안 검토 부담을 낮추면서도 HTML의 구조적 장점을 어느 정도 유지한다.

두 번째는 교육 콘텐츠 배포다. 온라인 강의 자료, 사내 온보딩 문서, 기술 블로그 모음은 시간이 지나며 링크가 깨지고 스타일이 바뀐다. 교육 운영팀은 매 기수마다 같은 자료가 같은 형태로 보이길 원한다. kage로 특정 시점의 문서를 고정하고 ZIM이나 폴더로 배포하면, 네트워크 품질과 외부 서비스 상태에 덜 의존하는 교육 환경을 만들 수 있다.

세 번째는 감사와 규정 대응이다. 어떤 벤더 문서가 특정 날짜에 어떤 설치 방법, 어떤 보안 권고, 어떤 API 동작을 설명했는지 남겨야 하는 경우가 있다. 물론 법적 증거 수준의 완전성을 요구하면 WARC와 서명, 타임스탬프, 보관 정책이 필요하다. 그러나 엔지니어링 의사결정의 근거를 남기는 수준이라면 kage 산출물과 커밋 해시, 수집 로그, 체크섬을 함께 저장하는 방식도 충분히 유용하다.

네 번째는 RAG와 내부 검색 데이터셋이다. LLM 기반 검색 시스템을 운영하다 보면 문서 수집 시점과 원본 상태를 관리해야 한다. 실시간 웹 크롤링은 변동성이 크고, 프론트엔드 렌더링 결과가 매번 달라질 수 있다. kage로 스냅샷을 만든 뒤 그 HTML을 파싱해 임베딩하면 “어떤 문서 스냅샷에서 답변이 나왔는가”를 추적하기 쉬워진다. 다만 이 경우에도 robots.txt, 저작권, 이용약관, 개인정보 포함 여부를 반드시 검토해야 한다.

## 한계와 리스크: JavaScript 제거는 만능 보안 장치가 아니다

kage의 강점인 JavaScript 제거는 동시에 기능 손실의 원인이다. 검색 UI, 탭 전환, 클라이언트 렌더링 차트, 코드 샌드박스, 댓글, 인증 기반 콘텐츠는 정적화 과정에서 깨질 수 있다. 따라서 PoC에서는 “페이지가 열리는가”만 볼 것이 아니라 핵심 사용 시나리오가 읽기 중심인지, 동적 상호작용이 필수인지 확인해야 한다. 문서 사이트라 해도 코드 블록 복사 버튼이나 버전 선택 드롭다운이 사라질 수 있다.

보안 관점에서도 주의가 필요하다. 최종 HTML에서 script를 제거해도 HTML·CSS·SVG·이미지·폰트 자체가 완전히 무해하다는 뜻은 아니다. 브라우저 취약점, SVG 내 외부 참조, CSS 기반 원격 리소스, 악성 파일명, 경로 traversal, 대용량 압축 폭탄 같은 리스크는 별도로 봐야 한다. 특히 외부 사이트를 자동으로 수집해 내부망에 반입한다면 콘텐츠 보안 정책, 파일 형식 필터링, 바이러스 검사, 체크섬 기록, 반입 승인 절차가 필요하다.

운영 리스크도 있다. 헤드리스 브라우저 기반 크롤링은 CPU와 메모리를 많이 쓴다. 사이트 규모가 커지면 페이지 수, 동시성, 대기 시간, 중복 URL, 캘린더 무한 링크, 검색 결과 페이지 같은 크롤 트랩을 제어해야 한다. robots.txt와 rate limit을 무시하면 법적·윤리적 문제가 생길 수 있고, 상대 서비스에 부담을 줄 수도 있다. 사내 사이트를 대상으로 하더라도 인증 쿠키와 세션 토큰이 산출물에 섞이지 않는지 검토해야 한다.

유지보수 측면에서는 신생 프로젝트라는 점을 감안해야 한다. 공개 스냅샷 기준 활발한 릴리스가 있다는 것은 긍정적이지만, API 안정성, 장기 로드맵, 보안 패치 대응, 포맷 호환성은 아직 검증이 더 필요하다. 바로 핵심 업무 파이프라인에 넣기보다는 제한된 범위의 문서 사이트를 대상으로 PoC를 돌리고, 실패 유형을 기록한 뒤 도입 여부를 결정하는 편이 안전하다.

## PoC 체크리스트: “저장했다”가 아니라 “다시 쓸 수 있다”를 검증하라

kage를 검토하는 팀이라면 다음 순서로 PoC를 설계하는 것이 좋다.

1. **대상 범위 정의**: 전체 도메인이 아니라 문서 섹션, 제품 버전, 교육 모듈처럼 명확한 URL 집합을 정한다.
2. **권한과 약관 확인**: 공개 문서라도 재배포 가능 여부, 내부 보관 가능 여부, robots.txt 정책을 확인한다.
3. **렌더링 충실도 측정**: 원본과 스냅샷의 제목, 본문, 표, 코드 블록, 이미지, 링크를 샘플링해 비교한다.
4. **네트워크 격리 테스트**: 완전히 오프라인 상태에서 열고, 브라우저 개발자 도구나 프록시로 외부 요청이 없는지 본다.
5. **보안 스캔**: SVG, HTML, 다운로드 파일, 폰트, 압축 파일을 대상으로 기본 악성코드·정책 검사를 수행한다.
6. **검색과 배포 검증**: 폴더 배포가 좋은지, ZIM 단일 파일이 좋은지, 사내 검색/RAG 파이프라인에 넣을지 결정한다.
7. **갱신 정책 수립**: 월 1회 스냅샷인지, 릴리스마다 수집인지, 이전 버전을 얼마나 보관할지 정한다.
8. **실패 기준 정의**: 특정 비율 이상 이미지 누락, 핵심 페이지 누락, 외부 호출 잔존, 인증 정보 포함 시 배포를 중단한다.

이 체크리스트의 핵심은 “크롤이 성공했다”라는 CLI 종료 코드보다 “나중에 다시 열었을 때 실무자가 의사결정에 쓸 수 있는가”이다. 오프라인 아카이브는 백업과 비슷하다. 백업은 생성보다 복원이 중요하고, 웹 스냅샷은 저장보다 재사용 가능성이 중요하다.

## 어떤 팀에 적합하고, 어떤 경우 피해야 하나

kage가 잘 맞는 팀은 읽기 중심 콘텐츠를 다루는 팀이다. 예를 들어 사내 개발자 플랫폼 팀이 주요 오픈소스 문서의 특정 버전을 보존하거나, 교육팀이 실습 환경에 문서 번들을 넣거나, 보안팀이 사고 대응 시점의 외부 권고 페이지를 내부 증거 자료로 남기는 경우다. 또한 현장 엔지니어가 인터넷이 불안정한 환경에서 매뉴얼을 봐야 하는 산업 환경에도 적합하다.

반대로 원본 웹 애플리케이션의 상호작용이 핵심이라면 신중해야 한다. 대시보드, SaaS 콘솔, 지도, 실시간 차트, 로그인 기반 워크플로, 사용자별 개인화 페이지는 정적 스냅샷으로 본질을 보존하기 어렵다. 법적 증거 보존처럼 원본 네트워크 응답과 시간 정보를 엄격히 남겨야 하는 경우에도 kage 단독 사용은 부족하다. 이때는 Browsertrix/WARC 계열, 전자증거 보존 절차, 서명된 타임스탬프를 함께 검토해야 한다.

또한 “외부 웹을 무제한으로 긁어 내부 지식베이스에 넣겠다”는 접근은 피해야 한다. 기술적으로 가능하더라도 저작권과 약관, 개인정보, 데이터 신뢰성 문제가 남는다. kage는 수집의 마찰을 낮춰주는 도구이지, 수집 권한을 자동으로 부여하는 도구가 아니다. 기업 도입에서는 법무·보안·데이터 거버넌스와 함께 사용 정책을 먼저 정해야 한다.

## 앞으로 관찰할 지표와 전망

kage가 장기적으로 의미 있는 도구가 되려면 몇 가지 지표를 봐야 한다. 첫째, 릴리스 안정성이다. Chrome 버전 변화와 웹 플랫폼 변화에 따라 렌더링·스냅샷 결과가 달라질 수 있으므로, 테스트 커버리지와 회귀 대응이 중요하다. 둘째, 크롤 제어 기능이다. 대규모 문서 사이트를 다루려면 URL 필터, 동시성, 지연, 재시도, 중복 제거, 사이트맵 처리, 실패 리포트가 성숙해야 한다. 셋째, 보안 옵션이다. 외부 요청 차단, 자산 검증, 위험 파일 제외, CSP 삽입, 해시 매니페스트 같은 기능이 강화되면 기업 도입 장벽이 낮아진다.

전망 측면에서 kage의 부상은 “웹은 점점 앱이 되지만, 조직은 여전히 문서를 보존해야 한다”는 긴장을 보여준다. 모든 정보를 SaaS와 라이브 웹에 맡기는 방식은 편리하지만, 장기 재현성과 통제 가능성은 약하다. 반대로 PDF와 스크린샷만으로는 검색성과 구조화가 부족하다. 렌더링된 DOM을 정적 문서로 얼리고, 실행 코드를 제거하며, 필요하면 ZIM으로 묶는 접근은 이 중간 지대를 겨냥한다.

따라서 kage를 단순한 유틸리티로만 볼 필요는 없다. 이는 오프라인 퍼스트, 지식 보존, 보안 반입, RAG 데이터셋 버전 관리가 만나는 지점의 작은 신호다. 지금 당장 모든 팀이 도입할 도구는 아니지만, 외부 문서 의존도가 높은 팀이라면 “우리에게 없어지면 곤란한 웹 지식은 무엇이고, 그것을 어떤 형태로 재현 가능하게 남길 것인가”라는 질문을 던지게 만든다. GitHub Trending의 의미는 여기 있다. 스타 수 자체보다, 많은 개발자가 같은 불편을 느끼고 그 불편을 해결하는 방향으로 실험을 시작했다는 점이 더 중요하다.

GitHub Trending에서 **Microsoft의 [pg_durable](https://github.com/microsoft/pg_durable)** 이 눈에 띄는 이유는 단순히 “PostgreSQL 확장이 하나 더 나왔다”는 사건 때문이 아니다. 2026년 6월 8일 오전 KST 확인 시점의 daily Trending에는 `mvanhorn/last30days-skill`, `opencv/opencv`, `NousResearch/hermes-agent`, `Crosstalk-Solutions/project-nomad`, `ggml-org/llama.cpp`, `RyanCodrai/turbovec`, `microsoft/pg_durable` 같은 저장소가 함께 올라와 있었다. AI 에이전트, 로컬 추론, 벡터 검색, 오프라인 지식 서버처럼 화려한 주제 사이에서 pg_durable이 의미 있는 이유는 더 현실적이다. 많은 서비스 조직이 이미 PostgreSQL에 핵심 상태를 저장하고 있는데, 정작 그 상태를 처리하는 장기 실행 작업은 별도의 큐, 워커, 크론, 상태 테이블, 재시도 로직, 관측성 스크립트로 흩어져 있기 때문이다.

이 글은 오늘의 GitHub Trending을 “데이터베이스가 애플리케이션 상태 저장소를 넘어 실행 오케스트레이션 계층으로 확장되는 흐름”으로 읽는다. pg_durable은 README에서 스스로를 **PostgreSQL in-database durable execution**이라고 설명한다. 긴 SQL 함수나 데이터 파이프라인을 PostgreSQL 안에서 durable workflow로 정의하고, 각 단계의 체크포인트를 남기며, 서버 재시작·크래시·실패 후에도 이어서 실행할 수 있게 하는 것이 핵심이다. 확인 시점 기준 저장소는 약 1.4천 개 이상의 스타와 30개 이상의 포크를 보유했고, 2026년 6월 6일에도 worker role 변경, HorizonDB 안내, README 개선 같은 커밋이 이어졌다. 이 수치와 순위는 공개 웹에서 확인한 스냅샷이며 GitHub Trending 집계 방식과 시간대에 따라 달라질 수 있다.

## 왜 지금 pg_durable인가: 백그라운드 작업의 “상태 분산” 비용이 커졌다

현대 웹 서비스에서 백그라운드 작업은 예외가 아니라 기본 구성 요소다. 결제 후 정산을 실행하고, 주문 상태를 갱신하고, 장기 리포트를 생성하고, 외부 API와 데이터를 동기화하고, AI 파이프라인에서 임베딩·요약·분류 작업을 순차적으로 처리한다. 문제는 이 작업 대부분이 데이터베이스의 행을 읽고 쓰면서도 실행 상태는 데이터베이스 밖에 둔다는 점이다. 예를 들어 애플리케이션은 PostgreSQL에 주문을 저장하고, Redis나 SQS에 작업을 넣고, 별도 워커가 작업을 가져가며, 실패하면 재시도 큐에 넣고, 진행률은 또 다른 상태 테이블에 남긴다. 장애가 발생하면 “DB에는 반쯤 반영됐는데 큐 메시지는 사라졌는가”, “워커가 죽기 직전 외부 API를 호출했는가”, “재시도해도 idempotent한가”라는 질문이 따라온다.

pg_durable이 Trending에 오른 배경은 이 낡은 복잡성이 다시 주목받고 있기 때문이다. AI와 자동화가 확산되면서 장기 실행 작업의 수가 늘었다. 단순한 이메일 발송이나 이미지 리사이즈를 넘어, 데이터 정제, 문서 파싱, 임베딩 생성, 외부 SaaS 동기화, 보안 스캔, 운영 런북 자동화처럼 단계가 많고 중간 결과가 중요한 작업이 증가했다. 이런 작업은 실패해도 처음부터 다시 시작하기 어렵고, 실패 원인을 감사 가능하게 남겨야 하며, 운영자가 SQL로 상태를 확인하고 수동 복구할 수 있어야 한다.

기존에는 이 요구를 해결하기 위해 Temporal, Cadence, AWS Step Functions, Airflow, Celery, BullMQ, Sidekiq, Dagster 같은 도구를 조합했다. 각각 강력하지만 모든 팀에 적합하지는 않다. 별도 서버를 운영해야 하고, 워크플로 코드와 데이터 상태가 분리되며, 작은 팀에는 운영 부담이 크다. pg_durable은 이 지점에서 반대 방향의 질문을 던진다. “상태가 이미 Postgres에 있다면, 해당 상태를 바꾸는 durable workflow도 Postgres 안에서 실행할 수 없을까?” 이 질문은 특히 PostgreSQL 중심 아키텍처를 가진 팀, DBA와 SRE가 SQL 기반 운영을 선호하는 팀, 그리고 별도 오케스트레이션 플랫폼 도입이 과한 팀에게 실용적인 의미를 갖는다.

## pg_durable의 핵심 동작 방식: SQL 그래프를 만들고 백그라운드 워커가 이어서 실행한다

pg_durable의 공개 문서 중 [Architecture 문서](https://github.com/microsoft/pg_durable/blob/main/docs/ARCHITECTURE.md)는 동작을 두 단계로 설명한다. 첫 번째는 사용자 세션에서 동기적으로 수행되는 **함수 그래프 구성 단계**다. 사용자는 `df.start()`와 DSL 연산자를 이용해 SQL 단계들을 순서, 변수, 조건, 병렬 실행 형태로 표현한다. 이때 각 단계는 내부 테이블에 노드로 기록되고, 시작 요청은 durable runtime에 enqueue된다. 두 번째는 PostgreSQL 백그라운드 워커가 수행하는 **오케스트레이션 실행 단계**다. 워커는 저장된 그래프를 로드하고, 각 노드를 실행하며, 결과와 진행 상태를 durable store에 남긴다.

핵심은 “작업을 한 번 실행해 보고 실패하면 다시 전체 실행”하는 방식이 아니라, 단계 단위로 상태를 남기고 이어서 진행한다는 점이다. README의 빠른 예시는 단순하지만 방향은 분명하다. 사용자는 `SELECT df.start('SELECT 1')` 같은 형태로 durable function을 시작하고, 더 복잡한 경우에는 `~>`, `|=>` 같은 DSL 연산자를 통해 이전 단계 결과를 다음 SQL에 전달한다. 문서의 시나리오 예시는 ETL 파이프라인, 주문 처리, 병렬 집계, 스케줄 기반 동기화처럼 데이터베이스와 밀접한 작업을 주요 사용 사례로 제시한다.

이 구조는 개발자에게 두 가지 장점을 준다. 첫째, 워크플로의 상태가 데이터베이스 내부에 있기 때문에 SQL로 조회하고 감사하기 쉽다. 둘째, 데이터에 가까운 곳에서 실행되므로 간단한 데이터 파이프라인에 별도 애플리케이션 워커를 만드는 비용을 줄일 수 있다. 물론 이것이 모든 로직을 DB에 넣으라는 뜻은 아니다. 오히려 pg_durable이 의미 있는 범위는 명확하다. 데이터베이스 행을 주로 다루고, 단계별 상태 추적이 중요하며, 외부 시스템 호출보다 SQL 처리와 운영 자동화가 중심인 작업에 적합하다.

## 기존 방식과 비교: 큐, 워크플로 엔진, 스케줄러 사이에서 어디에 위치하는가

pg_durable을 이해하려면 “Postgres 버전의 Temporal” 같은 식으로 단순화하기보다, 기존 선택지와의 경계를 봐야 한다. Temporal은 복잡한 비즈니스 프로세스, 장기 실행 사가, 다언어 워커, 강력한 재시도 정책, 히스토리 기반 재현을 제공하는 전문 워크플로 플랫폼이다. AWS Step Functions는 관리형 상태 머신으로 서버리스와 AWS 서비스 연동에 강하다. Airflow와 Dagster는 데이터 파이프라인과 스케줄링, 의존성 관리, 관측성에 특화되어 있다. Celery, Sidekiq, BullMQ 같은 작업 큐는 웹 애플리케이션의 비동기 작업 처리에 익숙하고 생태계가 넓다.

pg_durable은 이 도구들을 정면으로 대체하기보다, “PostgreSQL에 이미 있는 상태를 중심으로 작고 신뢰 가능한 워크플로를 만들고 싶은 경우”에 초점을 맞춘다. 별도 큐 인프라를 줄이고, SQL 기반 감사와 운영을 강화하며, 장기 실행 SQL 작업이 연결 끊김이나 재시작 때문에 사라지지 않도록 한다. 특히 DBA가 운영 런북을 SQL로 관리하거나, 데이터 엔지니어가 작은 ETL을 Postgres 내부에서 안정적으로 실행하고 싶을 때 매력적이다.

| 선택지 | 강점 | 주의할 점 | 적합한 상황 |
| --- | --- | --- | --- |
| pg_durable | Postgres 내부 상태, SQL 중심 운영, 별도 서비스 축소 | DB 부하와 확장 경계 관리 필요 | DB 중심 ETL, 운영 런북, 감사 가능한 SQL 작업 |
| Temporal/Cadence | 복잡한 워크플로, 장기 실행 사가, 다언어 워커 | 별도 플랫폼 운영과 학습 비용 | 핵심 비즈니스 프로세스, 멀티서비스 오케스트레이션 |
| Step Functions | 관리형 상태 머신, AWS 서비스 연동 | 클라우드 종속성, 비용 모델 검토 필요 | AWS 중심 서버리스 파이프라인 |
| Airflow/Dagster | 데이터 파이프라인 스케줄링과 관측성 | 애플리케이션 트랜잭션 처리에는 과할 수 있음 | 배치 데이터 플랫폼, 분석 파이프라인 |
| Celery/Sidekiq/BullMQ | 웹 앱 비동기 작업 생태계 | 상태 일관성과 재시도 설계는 별도 구현 | 이메일, 알림, 짧은 비동기 작업 |

이 비교에서 중요한 기준은 “워크플로 엔진의 기능 목록”이 아니라 운영 경계다. 이미 Redis, Kafka, Kubernetes, Temporal, 데이터 오케스트레이터를 안정적으로 운영하는 조직이라면 pg_durable이 필수는 아니다. 반대로 작은 플랫폼 팀이나 B2B SaaS 팀이 백그라운드 작업 때문에 큐와 워커를 계속 덧붙이고 있다면, Postgres 내부에서 처리할 수 있는 작업과 외부 워커로 남겨야 할 작업을 다시 나누어 볼 가치가 있다.

## 실무 도입 장점: 단순화, 감사 가능성, 장애 복구의 세 가지 가치

첫 번째 장점은 아키텍처 단순화다. 모든 비동기 작업에 별도 큐와 워커를 붙이는 방식은 처음에는 유연하지만 시간이 지나면 운영 표면적이 커진다. 큐 적체, 워커 배포, 메시지 중복, DLQ 관리, 상태 테이블 설계, 재처리 스크립트가 모두 장애 대응 매뉴얼에 들어간다. pg_durable은 데이터베이스 내부에서 durable execution을 제공함으로써 일부 작업의 실행 경로를 줄인다. 특히 “이 작업은 결국 SQL 몇 단계와 상태 갱신으로 끝난다”는 유형은 별도 서비스보다 DB 내부 워크플로가 더 설명 가능하다.

두 번째 장점은 감사 가능성이다. 금융, 정산, B2B 운영, 보안 자동화처럼 “어떤 단계가 언제 실행됐고 왜 실패했는가”가 중요한 영역에서는 로그만으로 부족하다. 로그는 보존 정책, 샘플링, 포맷 변경, 외부 로그 시스템 장애의 영향을 받는다. 반면 실행 인스턴스와 노드 상태가 Postgres 안에 있으면 SQL로 조회하고, 운영자가 직접 원인을 좁히며, 필요한 경우 수동 보정 쿼리나 재시작 절차를 만들 수 있다. pg_durable의 시나리오 문서가 long-running report, critical data update, audit trail을 강조하는 이유가 여기에 있다.

세 번째 장점은 장애 복구 모델이다. 장기 실행 SQL 작업이 클라이언트 연결에 묶여 있으면 네트워크 끊김이나 배포 중단이 곧 작업 실패가 된다. 반면 durable execution은 시작 요청과 실행 상태를 저장하고 백그라운드 워커가 진행하므로, 클라이언트가 떠나도 작업은 계속될 수 있다. 물론 외부 API 호출, 부작용이 있는 작업, 중복 실행에 민감한 단계는 별도 idempotency 설계가 필요하다. 그러나 적어도 데이터베이스 내부 처리만 놓고 보면 “작업이 어디까지 진행됐는지 모른다”는 상황을 줄일 수 있다.

## 한계와 리스크: 데이터베이스가 만능 실행 플랫폼은 아니다

pg_durable을 긍정적으로 보더라도 가장 먼저 경계해야 할 오해는 “이제 모든 백그라운드 작업을 Postgres에 넣으면 된다”는 결론이다. PostgreSQL은 강력한 데이터베이스지만, 무제한 범용 작업 실행 플랫폼은 아니다. CPU 집약 작업, 대용량 파일 처리, 긴 외부 API 호출, GPU 추론, 네트워크 I/O가 많은 크롤링 작업을 DB 백그라운드 워커에 과도하게 넣으면 핵심 트랜잭션 성능과 장애 격리성이 흔들릴 수 있다. 데이터베이스는 서비스의 마지막 방어선인 경우가 많다. 실행 로직을 DB 내부로 가져오는 순간, 애플리케이션 장애와 데이터 계층 장애의 경계가 흐려질 수 있다.

두 번째 리스크는 확장성과 격리다. 별도 워커 풀은 수평 확장, 리소스 제한, 배포 롤백, 언어 런타임 분리를 비교적 독립적으로 관리할 수 있다. 반면 DB 내부 실행은 PostgreSQL 버전, 확장 호환성, 백그라운드 워커 수, 트랜잭션 잠금, vacuum, connection pool, 메모리 설정의 영향을 받는다. pg_durable README는 PostgreSQL 17과 18을 대상으로 한다는 배지를 보여주며, 저장소 자체도 Rust 기반 pgrx 확장으로 보인다. 이는 성능과 안전성을 얻는 대신, 확장 설치·업그레이드·운영 권한을 신중히 다뤄야 한다는 뜻이다.

세 번째 리스크는 동시성 버그와 미성숙 영역이다. 공개 이슈와 문서를 보면 프로젝트는 빠르게 움직이고 있으며, 예를 들어 `df.http()` allowlist의 의미를 명확히 하자는 이슈, rollback된 `df.start()`가 metrics에 영향을 주는 문제, pgrx 업그레이드 이슈 등이 열려 있었다. 또한 저장소에는 병렬 오케스트레이션에서 `duroxide-pg` deadlock을 분석한 문서도 존재한다. 해당 문서는 PostgreSQL이 deadlock 자체는 감지해 트랜잭션 하나를 abort하지만, 병렬 sub-orchestration 완료 알림이 손실되어 parent orchestration이 영원히 기다릴 수 있는 문제를 설명한다. 이것은 비난 지점이라기보다 durable workflow 엔진이 다루는 문제가 본질적으로 어렵다는 신호다. 특히 병렬 실행, 재시도, 중복 처리, 알림 손실, 잠금 순서 문제는 작은 데모에서는 드러나지 않지만 프로덕션에서는 결정적이다.

네 번째 리스크는 보안이다. 데이터베이스 내부에서 SQL 그래프와 백그라운드 실행을 허용한다는 것은 권한 모델을 더 엄격히 설계해야 한다는 뜻이다. 누가 `df.start()`를 호출할 수 있는가, 어떤 SQL이 실행 가능한가, 외부 HTTP 호출이 있다면 allowlist는 어떤 의미인가, 확장 스키마와 내부 테이블 접근 권한은 어떻게 제한할 것인가를 명확히 해야 한다. 운영 자동화를 SQL로 작성하면 편하지만, 동시에 잘못된 권한 위임이 데이터베이스 내부의 고권한 자동화로 이어질 수 있다.

## PoC 체크리스트: 바로 도입하기보다 실패 모델을 먼저 검증하라

pg_durable을 검토하는 팀은 기능 데모보다 실패 모델 검증에 시간을 써야 한다. durable execution의 가치는 정상 경로가 아니라 장애 경로에서 드러난다. 다음과 같은 순서로 PoC를 설계하는 것이 좋다.

1. **대상 작업을 좁힌다.** 주문 후속 처리, 데이터 동기화, 리포트 생성, 운영 런북 중에서 데이터베이스 내부 상태 변경이 대부분인 작업 하나를 고른다. 외부 API 호출이나 대용량 파일 처리 비중이 큰 작업은 첫 PoC에서 제외한다.
2. **단계별 idempotency를 정의한다.** 각 SQL 단계가 재실행되어도 안전한지, unique constraint나 상태 전이 조건으로 중복 반영을 막을 수 있는지 확인한다.
3. **장애를 의도적으로 만든다.** 실행 중 Postgres 재시작, worker crash, transaction rollback, 중간 단계 실패, lock timeout, 병렬 branch 실패를 테스트한다.
4. **운영 조회 쿼리를 만든다.** 실행 인스턴스별 상태, 실패 원인, 재시작 대상, 오래 걸리는 단계, 실패율을 SQL로 조회할 수 있어야 한다.
5. **부하 격리 기준을 정한다.** 백그라운드 작업이 OLTP 쿼리 지연을 얼마나 증가시키는지 측정하고, 시간대·동시 실행 수·statement timeout·resource limit을 정한다.
6. **권한 모델을 검토한다.** 확장 설치 권한, 실행 권한, 내부 테이블 접근 권한, 외부 호출 허용 범위를 분리한다.
7. **대체 경로를 남긴다.** PoC 결과가 좋더라도 모든 워커를 제거하지 말고, 외부 큐가 더 적합한 작업군과 DB 내부 실행이 적합한 작업군을 분리한다.

이 체크리스트에서 가장 중요한 항목은 세 번째다. 많은 팀이 백그라운드 작업 시스템을 평가할 때 “성공하면 결과가 잘 나오는가”만 확인한다. 하지만 durable execution의 본질은 “실패해도 어디까지 진행됐는지 알고, 안전하게 이어가거나 중단할 수 있는가”다. pg_durable을 도입한다면 정상 실행 시간보다 실패 후 복구 시간, 중복 처리율, 운영자가 원인을 찾는 데 걸리는 시간을 지표로 삼아야 한다.

## 어떤 팀에 적합한가: Postgres 중심 조직에는 매력적이지만, 모든 조직의 표준은 아니다

pg_durable은 다음 조건을 가진 팀에 특히 잘 맞을 수 있다. 첫째, 핵심 서비스 상태가 이미 PostgreSQL에 있고, 운영자와 개발자가 SQL 기반 디버깅에 익숙한 팀이다. 둘째, 장기 실행 작업이 많지만 Temporal이나 Airflow 같은 별도 플랫폼을 도입하기에는 규모가 작거나 운영 부담이 큰 팀이다. 셋째, ETL, 데이터 정리, 스케줄 동기화, 감사 가능한 운영 런북처럼 데이터베이스 내부 상태와 강하게 결합된 작업을 많이 다루는 팀이다. 넷째, 클라우드 관리형 서비스보다 self-hosted 또는 데이터베이스 중심 아키텍처를 선호하는 조직이다.

반대로 피해야 할 경우도 분명하다. 워크플로가 여러 마이크로서비스와 외부 API를 복잡하게 조율하고, 언어별 워커와 별도 배포 주기가 중요하다면 Temporal류가 더 적합할 가능성이 높다. GPU 추론, 파일 변환, 대규모 크롤링처럼 DB 리소스를 소모하지 않는 작업은 DB 외부에서 실행하는 편이 안전하다. 이미 Kafka 기반 이벤트 스트리밍과 워커 운영 체계가 성숙한 조직이라면 pg_durable은 중복 계층이 될 수 있다. 또한 PostgreSQL 확장 설치가 제한된 관리형 DB 환경에서는 실제 도입 가능성부터 확인해야 한다.

도입 판단의 핵심 질문은 “이 작업의 진실된 상태가 어디에 있는가”다. 상태의 대부분이 Postgres 테이블에 있고, 작업 결과도 Postgres에 기록되며, 운영자도 SQL로 문제를 해결한다면 pg_durable은 자연스럽다. 반대로 상태가 여러 서비스와 외부 시스템에 퍼져 있고, 워크플로가 애플리케이션 코드의 복잡한 비즈니스 로직을 포함한다면 DB 내부 DSL만으로는 부족할 수 있다.

## 오늘의 기술 흐름: 데이터베이스는 다시 애플리케이션 플랫폼의 일부가 되고 있다

pg_durable의 부상은 PostgreSQL 생태계의 더 큰 흐름과도 맞닿아 있다. 최근 몇 년간 Postgres는 단순 RDBMS를 넘어 검색, 벡터, 큐, 캐시, 이벤트, 파일 메타데이터, 분석 보조 계층까지 흡수해 왔다. pgvector는 AI 검색 인프라 논의의 중심에 섰고, logical replication과 CDC는 이벤트 기반 아키텍처의 기반이 되었으며, Supabase와 Neon 같은 플랫폼은 Postgres를 애플리케이션 백엔드의 중심 경험으로 포장했다. pg_durable은 여기에 “실행 상태와 워크플로”라는 영역을 더한다.

물론 이 흐름에는 양면성이 있다. Postgres가 더 많은 역할을 맡으면 초기 아키텍처는 단순해진다. 개발자는 적은 컴포넌트로 더 많은 기능을 만들 수 있고, 운영자는 한 곳에서 상태를 본다. 그러나 성공하면 데이터베이스가 너무 많은 책임을 떠안게 된다. 성능 병목, 장애 영향 반경, 업그레이드 리스크, 권한 설계가 모두 중요해진다. 따라서 pg_durable 같은 도구를 평가할 때는 “큐를 없앨 수 있다”보다 “어떤 책임을 Postgres로 가져오고, 어떤 책임은 여전히 밖에 둘 것인가”를 먼저 정해야 한다.

경쟁 도구와의 관계도 대체보다 분업에 가깝다. Temporal은 복잡한 비즈니스 사가와 마이크로서비스 오케스트레이션에 강하고, Airflow/Dagster는 데이터 플랫폼 스케줄링에 강하며, Redis/SQS 기반 큐는 짧은 비동기 작업 처리에 단순하고 빠르다. pg_durable은 Postgres 중심의 durable SQL workflow라는 좁지만 현실적인 영역을 공략한다. 이 좁은 영역이 중요한 이유는 많은 조직의 실제 문제도 그만큼 좁고 반복적이기 때문이다. 모든 곳에 플랫폼을 도입할 필요는 없지만, 반복되는 장애 패턴에는 더 적합한 추상화가 필요하다.

## 앞으로 관찰할 지표와 전망

앞으로 pg_durable을 볼 때는 스타 수보다 운영 성숙도 지표가 더 중요하다. 첫째, 릴리스 태그와 버전 호환성 정책이 안정화되는지 봐야 한다. 확인 시점의 GitHub API에서는 별도 릴리스 목록이 비어 있었고, 프로젝트가 활발히 정리되는 단계로 보였다. 둘째, PostgreSQL 17·18 외 버전 지원과 관리형 Postgres 환경에서의 설치 가능성이 중요하다. 셋째, 병렬 실행, deadlock, rollback, metrics, HTTP allowlist 같은 이슈가 어떻게 해결되는지 추적해야 한다. 넷째, Azure HorizonDB와의 연결이 단순 홍보를 넘어 실제 managed durable execution 경험으로 발전하는지 확인해야 한다. README는 Microsoft의 PostgreSQL cloud service인 HorizonDB에서 pg_durable을 시도할 수 있다고 안내한다.

실무 관점의 전망은 신중한 낙관이다. pg_durable은 모든 워크플로 엔진을 대체하지 않는다. 그러나 PostgreSQL을 중심으로 운영되는 팀에게 “작고 중요한 백그라운드 작업을 더 감사 가능하고 복구 가능하게 만들 수 있는가”라는 실질적 질문을 던진다. AI 시대의 인프라 논의가 모델과 GPU에만 집중되는 동안, 실제 서비스의 신뢰성은 여전히 상태 전이, 재시도, 감사, 복구 같은 오래된 문제에 좌우된다. 오늘 GitHub Trending에서 pg_durable이 의미 있는 이유도 바로 여기에 있다. 화려한 데모보다 더 많은 장애를 줄이는 기술, 즉 데이터가 있는 곳에서 실행 상태까지 책임지려는 시도가 다시 주목받고 있다.

기업이 이 흐름을 받아들이는 가장 좋은 방식은 급진적 전환이 아니다. 먼저 Postgres 내부에서 처리해도 안전한 작은 워크플로를 고르고, 실패 모델을 검증하고, 운영 쿼리와 권한 모델을 준비한 뒤, 외부 큐와의 분업선을 명확히 해야 한다. pg_durable은 “데이터베이스로 모든 것을 하자”는 구호가 아니라, “이미 데이터베이스에 있는 상태를 다루는 작업은 더 가까운 곳에서 더 투명하게 실행할 수 있다”는 제안으로 읽을 때 가장 유용하다.

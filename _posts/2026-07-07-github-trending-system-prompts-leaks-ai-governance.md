GitHub Trending daily 최상단에 [asgeirtj/system_prompts_leaks](https://github.com/asgeirtj/system_prompts_leaks)가 다시 올라온 현상은 단순한 호기심 콘텐츠로 넘기기 어렵다. 2026년 7월 7일 07:16 KST 확인 시점의 GitHub Trending 스냅샷에서 이 저장소는 daily 기준 약 51.3k stars, 8.3k forks, “1,386 stars today”로 표시됐고, GitHub API 기준 51,395 stars, 8,378 forks, 34 open issues, CC0-1.0 라이선스, 2026년 7월 6일 최신 커밋이 확인됐다. 숫자는 확인 시점의 스냅샷이며 GitHub 캐시와 시간대에 따라 달라질 수 있다.

이 글의 논지는 명확하다. 시스템 프롬프트 유출은 “프롬프트를 더 잘 숨겨야 한다”는 단순 보안 문제가 아니라, AI 제품의 정책·권한·운영 지식이 어디에 존재하고 어떻게 변경되며 어떤 경로로 노출될 수 있는지를 관리하는 **AI 제품 거버넌스 문제**다. 프롬프트가 소스코드처럼 제품 동작을 좌우한다면, 이제 프롬프트도 자산 인벤토리, 변경 승인, 보안 검토, 회귀 평가, 사고 대응의 대상이 되어야 한다.

system_prompts_leaks를 선택한 이유는 “AI가 무엇을 하느냐”보다 “AI 제품이 어떤 내부 규칙으로 운영되느냐”를 정면으로 보여주기 때문이다. 저장소 README는 Claude, ChatGPT, Gemini, Cursor, Copilot, Perplexity 등 여러 제품의 시스템 프롬프트 문서를 모아두는 목적을 설명하며, 루트에는 Anthropic, OpenAI, Google, Microsoft, Cursor, xAI, Perplexity 등 벤더별 디렉터리가 있다. GitHub API로 확인한 콘텐츠 목록에는 OpenAI의 `gpt-5-thinking.md`, Anthropic의 `claude-opus-4.8.md`, Google의 `gemini-3.5-flash.md`, `gemini-cli.md`, Cursor의 `cursor.md`처럼 제품·모델·클라이언트별 파일이 존재했다. 이 사실 자체가 특정 문서의 진위나 최신성을 보장하지는 않지만, 시장이 “AI 제품의 보이지 않는 운영 규칙”을 관찰 가능한 대상으로 보기 시작했다는 신호로는 충분하다.

## 왜 지금 GitHub Trending에 올랐나: 프롬프트가 제품 정책의 실행 계층이 됐다

초기 챗봇 시대의 시스템 프롬프트는 대체로 말투, 안전 지침, 답변 형식 같은 보조 설정으로 이해됐다. 그러나 현재의 AI 제품은 다르다. 웹 검색, 코드 실행, 파일 접근, 브라우저 제어, 사내 문서 검색, 결제·예약·배포 같은 외부 도구 호출이 붙으면서 시스템 프롬프트는 모델에게 “어떤 권한을 어떤 조건에서 행사할지”를 지시하는 실행 정책 계층이 됐다.

이 변화가 유출 관심을 키웠다. 사용자는 모델이 왜 특정 답변을 거부하는지, 어떤 도구를 언제 호출하는지, 내부적으로 어떤 우선순위를 갖는지 알고 싶어 한다. 경쟁사는 제품 경험의 차이가 프롬프트 설계인지, 모델 자체 성능인지, 후처리 파이프라인인지 알고 싶어 한다. 보안 연구자는 프롬프트 인젝션이나 탈옥 공격이 실제 시스템 지시문을 얼마나 우회할 수 있는지 검증하려 한다. 언론과 커뮤니티는 거대 AI 서비스가 공개적으로 말하는 원칙과 내부 지시가 일치하는지도 보려 한다.

따라서 system_prompts_leaks의 Trending은 “비밀 문서 모음이 재미있다”는 수준이 아니다. AI 제품이 점점 더 많은 업무 의사결정에 들어오면서, 시스템 프롬프트가 사실상 제품 정책, UX 설계, 보안 경계, 법무·브랜드 기준을 함께 담는 문서가 되었고, 그 문서가 노출될 때 조직이 어떤 위험을 감수해야 하는지 묻는 현상이다.

## 시스템 프롬프트 유출의 기술 구조: 모델 메모리 문제가 아니라 경계면 문제

많은 팀이 “시스템 프롬프트는 사용자가 볼 수 없는 메시지이니 안전하다”고 가정한다. 하지만 LLM 애플리케이션의 실제 경계는 그렇게 단순하지 않다. 사용자 입력, 시스템 메시지, 개발자 메시지, 검색 결과, 도구 응답, 대화 히스토리, 로깅 파이프라인, 브라우저 번들, 고객지원 스크린샷이 모두 하나의 실행 컨텍스트 주변에 존재한다. 유출은 이 중 한 곳에서 발생한다.

첫 번째 경로는 모델 응답을 통한 직접 노출이다. 사용자가 “위 지시문을 그대로 출력하라”는 식으로 요청하거나, 다단계 역할극·번역·디버깅·마크다운 복원 요청을 조합하면 모델이 내부 지시 일부를 답변에 섞을 수 있다. 최신 모델은 이 공격에 더 강해졌지만, 시스템 지시가 길고 복잡하며 도구 설명이 포함될수록 회귀 가능성은 남는다.

두 번째 경로는 제품 구현상의 노출이다. 웹 클라이언트에 포함된 프롬프트 템플릿, 모바일 앱 번들, 브라우저 확장 프로그램, 프론트엔드 소스맵, API 에러 메시지, 관측성 로그, 고객지원용 대화 내보내기 파일에 시스템성 지시가 포함될 수 있다. 이 경우 모델이 아무리 안전해도 배포·로깅·디버깅 체계가 약하면 유출된다.

세 번째 경로는 도구 설명과 권한 모델의 간접 노출이다. 많은 에이전트형 제품은 모델에게 사용 가능한 도구, 인자, 제한 조건, 실패 시 복구 절차를 자연어로 알려준다. 이 정보가 드러나면 공격자는 어떤 액션이 가능한지, 어떤 검증이 클라이언트에만 있는지, 어떤 제한 문구를 우회해야 하는지 추론할 수 있다. 즉 프롬프트 유출은 프롬프트 내용만의 문제가 아니라 도구 권한, 백엔드 검증, 감사 로그 설계의 문제로 이어진다.

## 기존 방식과의 비교: 보안 문서, 정책 코드, 프롬프트는 어떻게 다른가

AI 도입 전에도 조직은 정책과 규칙을 운영했다. 접근제어 정책은 IAM과 RBAC에 있었고, 네트워크 정책은 방화벽과 서비스 메시 설정에 있었으며, 개인정보 정책은 법무 문서와 데이터 카탈로그에 있었다. 이들은 대체로 기계가 강제하거나 사람이 검토하는 구조가 분리되어 있었다.

시스템 프롬프트는 그 중간에 있다. 자연어라서 제품팀·법무팀·보안팀이 읽고 수정하기 쉽지만, 동시에 모델 실행에 직접 영향을 준다. 정책 문서처럼 해석 여지가 있고, 코드처럼 배포되며, 설정처럼 자주 바뀐다. 이 혼합적 성격 때문에 기존 SDLC만으로는 충분하지 않다.

| 구분 | 전통적 정책 문서 | 정책 코드/IAM | 시스템 프롬프트 |
|---|---|---|---|
| 표현 방식 | 자연어 | 선언형 설정·코드 | 자연어와 구조화 템플릿의 혼합 |
| 강제력 | 사람의 준수에 의존 | 시스템이 직접 강제 | 모델 해석에 의존하며 확률적 |
| 변경 주기 | 느림 | 릴리스·인프라 변경과 연동 | 제품 실험·모델 변경에 따라 빠름 |
| 검증 방식 | 리뷰·감사 | 테스트·정책 시뮬레이션 | 레드팀, 평가셋, 회귀 테스트 필요 |
| 유출 영향 | 평판·컴플라이언스 | 권한 우회·침해 | 정책 우회 단서, 제품 전략, 도구 구조 노출 |

대체 접근도 있다. [OWASP Top 10 for LLM Applications](https://owasp.org/www-project-top-10-for-large-language-model-applications/)는 프롬프트 인젝션, 민감정보 노출, 과도한 에이전시 같은 범주로 위험을 정리한다. [NIST AI Risk Management Framework](https://www.nist.gov/itl/ai-risk-management-framework)는 AI 시스템의 거버넌스, 측정, 관리 절차를 강조한다. [Lakera Gandalf](https://gandalf.lakera.ai/) 같은 교육형 챌린지는 프롬프트 공격을 체험하게 만든다. 그러나 오늘의 Trending이 보여주는 차이는, 실제 제품의 시스템 지시문이 공개 저장소와 커뮤니티 검토의 대상이 되면서 거버넌스 논의가 추상 프레임워크가 아니라 구체 산출물 관리 문제로 내려왔다는 점이다.

## 실무 도입 관점: 프롬프트를 비밀로만 취급하면 실패한다

조직이 가장 먼저 해야 할 일은 “프롬프트를 절대 노출하지 않겠다”는 선언이 아니다. 물론 시스템 프롬프트에는 내부 정책, 제품 전략, 도구 구조, 안전 우회 방지 지침이 들어갈 수 있으므로 무분별한 공개는 위험하다. 그러나 완전한 비밀성을 전제로 제품을 설계하면, 한 번의 노출이 곧 통제 상실로 이어진다.

더 현실적인 원칙은 **유출되어도 치명적 권한 상승이 일어나지 않는 구조**다. 시스템 프롬프트에는 민감한 API 키, 내부 URL, 고객 식별자, 우회 가능한 보안 로직을 넣지 않아야 한다. 모델이 어떤 도구를 호출할 수 있는지는 백엔드 권한 검증과 서버 측 정책 엔진이 최종 판단해야 한다. 프롬프트는 모델의 행동을 안내할 수 있지만, 보안 경계를 대체해서는 안 된다.

또한 프롬프트 변경은 제품 실험이면서 보안 변경이다. “거절률을 낮추기 위해 문구를 완화했다”는 수정이 데이터 유출 가능성을 높일 수 있고, “도구 호출을 더 적극적으로 하라”는 지시가 비용 폭증이나 외부 시스템 오작동을 만들 수 있다. 따라서 중요한 시스템 프롬프트는 Git으로 버전관리하고, 변경 이유와 승인자를 기록하며, 핵심 평가셋을 통과해야 배포하는 절차가 필요하다.

## 보안·운영·성능·유지보수 리스크

### 보안 리스크: 프롬프트는 공격 표면의 지도다

시스템 프롬프트가 노출되면 공격자는 금지 항목, 예외 조건, 도구 이름, 내부 분기 로직을 알 수 있다. 이는 곧 프롬프트 인젝션 설계에 쓰인다. 예를 들어 “특정 상황에서는 사용자에게 정책을 설명하지 말라”는 문구가 있으면, 공격자는 그 상황을 가장해 모델의 응답 경계를 테스트할 수 있다. “특정 도구는 결제 확인 후 호출하라”는 설명이 있으면, 결제 확인이 어디에서 검증되는지 탐색할 수 있다.

대응은 두 층으로 나눠야 한다. 모델 지시문에는 방어 문구가 필요하지만, 최종 보안 통제는 서버 측 권한, 입력 검증, 출력 필터, 도구별 allowlist, 사용자·테넌트별 접근제어가 맡아야 한다. 프롬프트가 유출되어도 공격자가 실제 데이터나 액션 권한을 얻지 못해야 한다.

### 운영 리스크: 모델·제품 변경 때마다 프롬프트 의미가 달라진다

동일한 시스템 프롬프트도 모델 버전이 바뀌면 다르게 작동한다. 더 긴 컨텍스트, 새로운 도구 호출 방식, 강화된 안전 정책, 멀티모달 입력이 추가되면 기존 프롬프트의 우선순위와 효과가 달라질 수 있다. 저장소의 최근 커밋이 2026년 7월에도 계속 발생하는 것처럼, 시장의 AI 제품 프롬프트는 정적 산출물이 아니라 계속 바뀌는 운영 대상이다.

실무에서는 모델 업그레이드와 프롬프트 변경을 같은 릴리스 노트에 묶어 추적해야 한다. “모델만 바꿨다”는 배포도 실제로는 정책 실행 방식이 바뀐 배포일 수 있다.

### 성능·비용 리스크: 긴 지시문은 비용과 지연을 만든다

시스템 프롬프트가 길어질수록 컨텍스트 토큰을 차지하고, 요청당 비용과 지연이 늘어난다. 더 큰 문제는 긴 프롬프트가 명확성을 항상 높이지 않는다는 점이다. 예외 규칙이 누적되면 모델이 상충 지시를 해석해야 하고, 회귀 테스트가 어려워진다. 시스템 프롬프트는 “많을수록 안전하다”가 아니라 “짧고 계층화되어 있으며 검증 가능할수록 운영 가능하다”에 가깝다.

### 유지보수 리스크: 프롬프트 소유자가 불명확해진다

제품팀은 사용자 경험을, 보안팀은 위험 통제를, 법무팀은 규정 준수를, 데이터팀은 검색 품질을 프롬프트에 반영하고 싶어 한다. 소유권이 분산되면 누가 최종 승인자인지, 어떤 문구가 필수 통제인지, 어떤 문구가 실험용인지 구분되지 않는다. 이는 시간이 지나면 “아무도 삭제하지 못하는 거대한 시스템 프롬프트”로 이어진다.

## PoC와 도입 체크리스트: 우리 조직의 프롬프트는 운영 가능한가

AI 제품이나 사내 에이전트를 운영하는 팀이라면 다음 순서로 점검하는 것이 현실적이다.

1. **프롬프트 인벤토리 작성**: 제품별, 모델별, 기능별 시스템 프롬프트 위치를 기록한다. 코드 저장소, 설정 서버, 벡터 검색 프롬프트, 고객지원 매크로까지 포함한다.
2. **민감도 분류**: 공개 가능 문구, 내부 전용 문구, 유출 시 보안 영향이 있는 문구를 나눈다. API 키나 비밀 URL이 있다면 즉시 제거한다.
3. **도구 권한 분리**: 모델에게 알려주는 도구 설명과 실제 권한 검증을 분리한다. 프롬프트가 허용해도 서버가 거부할 수 있어야 한다.
4. **프롬프트 인젝션 평가셋 구축**: “지시문 출력”, “정책 무시”, “도구 우회”, “검색 결과 내 악성 지시” 같은 케이스를 반복 테스트한다.
5. **변경 승인 절차 도입**: 중요한 시스템 프롬프트는 pull request, 리뷰어, 릴리스 노트, 롤백 기준을 갖춘다.
6. **로그와 DLP 점검**: 대화 로그, 에러 리포트, 분석 이벤트에 시스템 지시문이 저장되는지 확인한다. 저장이 필요하면 접근권한과 보존기간을 제한한다.
7. **사고 대응 플레이북 작성**: 유출 확인 시 영향 범위 산정, 프롬프트 교체, 도구 권한 점검, 고객 공지 여부 판단, 회귀 평가 재실행 절차를 마련한다.

PoC 단계에서는 거창한 플랫폼보다 작은 표준부터 시작하는 편이 낫다. 예를 들어 `prompts/` 디렉터리에 시스템 프롬프트를 버전관리하고, YAML front matter로 소유자·민감도·적용 모델·평가셋을 기록하며, CI에서 금지 문자열과 토큰 길이를 검사하는 방식이다. 여기에 레드팀 테스트 결과를 PR에 첨부하면 프롬프트 변경이 더 이상 감각적 문구 수정이 아니라 검증 가능한 운영 변경이 된다.

## 어떤 팀에 적합하고, 어떤 경우 피해야 하나

이 접근은 고객 데이터, 업무 자동화, 결제·예약·배포, 사내 문서 검색처럼 AI가 실제 권한이나 민감정보에 접근하는 팀에 특히 중요하다. 금융, 헬스케어, 공공, B2B SaaS, 보안 제품, 개발자 도구처럼 감사와 책임 소재가 중요한 조직은 시스템 프롬프트를 별도 자산으로 관리해야 한다. 에이전트가 브라우저나 CLI를 제어하는 경우에는 더욱 그렇다. 모델이 실수로 민감 정보를 말하는 것뿐 아니라, 잘못된 도구 호출로 실제 시스템 상태를 바꿀 수 있기 때문이다.

반대로 초기 아이디어 검증 단계의 개인 프로젝트나 내부 데모에서 과도한 프롬프트 거버넌스 체계를 먼저 도입하는 것은 비용이 클 수 있다. 아직 제품 방향이 바뀌는 단계라면 최소한의 원칙, 즉 비밀값 금지, 서버 측 권한 검증, 기본 인젝션 테스트, 로그 노출 방지부터 적용하는 편이 낫다. 문제는 “거버넌스를 하느냐 마느냐”가 아니라 “제품 위험도에 맞는 수준으로 하느냐”다.

## 향후 관찰해야 할 지표와 전망

앞으로 볼 지표는 저장소의 stars만이 아니다. 첫째, 주요 AI SDK와 플랫폼이 시스템 프롬프트 버전관리, 평가셋 연결, 정책 시뮬레이션 기능을 얼마나 기본 제공하는지 봐야 한다. 둘째, OWASP·NIST·ISO 같은 프레임워크가 프롬프트 자산 관리와 에이전트 권한 통제를 얼마나 구체적으로 다루는지 봐야 한다. 셋째, 기업용 AI 제품이 “프롬프트가 유출되어도 안전한 구조”를 아키텍처 설명과 감사 자료에서 증명할 수 있는지 봐야 한다.

system_prompts_leaks 같은 저장소는 앞으로도 논쟁적일 수밖에 없다. 일부 파일은 최신성이 떨어질 수 있고, 출처 검증이 어렵거나 제품사의 의도와 다르게 해석될 수 있다. 따라서 이를 근거로 특정 벤더의 보안 수준을 단정하는 것은 부적절하다. 하지만 이 저장소가 Trending에 오른 사실은 AI 제품의 내부 정책이 더 이상 완전히 보이지 않는 영역에 머물 수 없다는 압력을 보여준다.

실무 의사결정자에게 필요한 결론은 간단하다. 시스템 프롬프트를 제품의 비밀 주문서처럼 취급하지 말고, 변경 가능한 정책 자산으로 취급하라. 유출을 막기 위한 방어는 필요하지만, 유출이 곧 보안 붕괴가 되지 않도록 권한 검증과 데이터 보호를 프롬프트 밖에 배치하라. 그리고 프롬프트 변경을 릴리스 관리, 보안 평가, 사고 대응 체계 안으로 넣어라. 오늘의 GitHub Trending은 이 작업을 미룰 시간이 줄어들고 있음을 보여주는 신호다.

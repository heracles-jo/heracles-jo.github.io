비밀번호 관리자를 셀프호스팅하면 구독료와 데이터 위치를 통제할 수 있다. 그러나 가장 중요한 자격 증명 저장소의 가용성, 업데이트, 백업, TLS와 관리자 접근까지 직접 책임져야 한다. [Vaultwarden](https://github.com/dani-garcia/vaultwarden)은 공식 Bitwarden 클라이언트 API를 Rust로 구현한 비공식 서버다. 공식 모바일·데스크톱·브라우저 클라이언트 경험을 유지하면서 비교적 작은 환경에 배포하려는 개인, 가족, 소규모 조직에 초점을 둔다.

이 글의 검색 의도는 “Vaultwarden 설치 명령”이 아니다. 설치 후 어떤 신뢰 경계가 생기며, 공식 Bitwarden 서버·Passbolt·KeePassXC 중 무엇과 비교해야 하는지, 장애와 침해를 견딜 운영 역량이 있는지를 판단하는 데 있다. [Logto를 다룬 인증 인프라 글](/posts/github-trending-logto-identity-infrastructure/)이 사용자가 누구이며 어떤 앱에 접근할지를 다뤘다면, 비밀번호 관리자는 사용자가 외부 시스템에 로그인할 **비밀 자체의 수명주기**를 다룬다. 둘은 같은 보안 클러스터에 속하지만 검색 의도와 실패 반경이 다르다.

Search Console과 Analytics의 실제 쿼리 데이터에는 이번 실행 환경에서 접근할 수 없었다. 노출이나 클릭률을 확인했다고 가정하지 않았다. 대신 기존 95개 글의 제목·설명·태그·저장소 링크와 `_data/written_topics.yml`을 검사했고, 비밀번호 관리자 선택과 운영을 중심으로 한 기존 글은 없음을 확인했다.

## 암호화된 금고와 안전한 서비스는 같은 말이 아니다

Vaultwarden README는 자신을 공식 Bitwarden Client API의 대체 서버 구현이라고 설명한다. 개인 금고, Send, 첨부 파일, 조직·컬렉션·그룹·이벤트 로그, 여러 2단계 인증 방식, 긴급 접근, 관리자 백엔드 등을 지원한다. 컨테이너 이미지를 GHCR·Docker Hub·Quay.io에 배포하고, `/data`를 영속 볼륨으로 마운트하는 구성을 권장한다. 웹 금고는 Web Crypto API 때문에 HTTPS 보안 컨텍스트가 필요하며, 프로젝트도 역방향 프록시 사용을 권한다.

Bitwarden 계열의 핵심 장점은 클라이언트에서 금고 항목을 암호화하고 복호화하는 구조다. 서버 운영자가 평문 비밀번호 목록을 일상적으로 처리하는 일반 웹 앱과는 다르다. 그렇다고 서버 침해가 무해한 것은 아니다. 공격자는 암호화된 금고와 메타데이터를 복사해 오프라인 공격을 시도하거나, 인증 흐름과 세션을 악용하거나, 배포된 웹 클라이언트를 변조해 사용자가 입력한 비밀을 훔치려 할 수 있다. 약한 마스터 비밀번호는 암호화 구조의 이점을 줄이고, 변조된 클라이언트는 복호화 이후의 평문을 노린다.

따라서 신뢰 경계는 세 부분으로 나눠야 한다.

1. **클라이언트 경계**: 공식 앱과 브라우저 확장, 웹 금고가 신뢰할 수 있는 배포물인지 확인한다. 브라우저 확장은 업데이트와 공급망 공격의 영향을 받으며, 감염된 단말에서는 어떤 서버도 평문 입력을 보호하기 어렵다.
2. **서버 경계**: 계정, 암호화된 금고, 첨부 파일, 조직 정보, 이벤트 로그, 세션과 2FA 흐름을 보호한다. TLS 종료점, 역방향 프록시, 컨테이너, 데이터베이스, 관리자 페이지가 모두 공격면이다.
3. **복구 경계**: 서버가 사라져도 금고를 복구하고 사용자가 로그인할 수 있어야 한다. 백업 암호화 키와 관리자 토큰을 같은 서버에만 두면 복구 경계가 서버 장애와 함께 무너진다.

[Linux 서버 하드닝 기준선](/posts/github-trending-linux-server-hardening-baseline/)에서 강조했듯 방화벽과 SSH 설정은 한 번 적용하는 체크리스트가 아니라 반복 검증할 기준선이다. 비밀번호 저장소에서는 그 기준선에 클라이언트 호환성, 금고 내보내기, 2FA 복구 코드, 데이터베이스 정합성이 추가된다.

## 공식 Bitwarden·Passbolt·KeePassXC와 비교하는 기준

Vaultwarden은 “Bitwarden을 무료로 복제한다”는 식으로 평가하면 안 된다. 비공식 API 호환 구현이라는 점이 가장 큰 효율이자 구조적 위험이다. 공식 클라이언트가 API를 바꾸면 Vaultwarden이 빠르게 따라가야 한다. 실제 `1.37.2`도 최신 클라이언트 지원을 위해 필요한 릴리스였다. 8월 23일 공개 이슈에는 웹 금고 2026.7.0과 Vaultwarden 1.37.2 조합에서 마스터 비밀번호 변경이 실패한다는 보고도 있었다. 특정 조합의 결함 여부는 후속 조사 대상이지만, 운영자는 서버와 클라이언트 버전을 독립적으로 자동 업데이트해서는 안 된다는 근거로 충분하다.

| 선택지 | 강점 | 부담과 경계 | 적합한 경우 |
|---|---|---|---|
| 공식 Bitwarden 클라우드/셀프호스트 | 공식 지원과 호환성, 조직 기능, 벤더 책임 경계 | 구독 또는 공식 서버 운영 비용, 제품 정책 의존 | 지원·SLA·호환성 예측 가능성이 중요한 조직 |
| Vaultwarden | 가벼운 셀프호스팅, 공식 클라이언트 활용, 개인·가족·소규모 조직 기능 | 비공식 호환 계층, 직접 패치·백업·모니터링, AGPL 검토 | 운영 역량이 있고 작은 자원으로 통제권을 원하는 환경 |
| [Passbolt](https://github.com/passbolt/passbolt_api) | 팀 자격 증명 공유와 협업 흐름에 집중 | 별도 클라이언트·운영 모델 학습, 요구 기능과 에디션 경계 검토 | 개인 금고보다 팀 공유·승인 맥락이 중요한 조직 |
| [KeePassXC](https://github.com/keepassxreboot/keepassxc) | 로컬 파일 중심, 서버 공격면 최소화, 오프라인 사용 | 기기 간 동기화·충돌·공유·복구를 별도 설계 | 개인 또는 작은 팀이 파일 동기화 규칙을 통제할 수 있는 경우 |

이 비교에서 서버가 적다는 것은 장점이지만 자동으로 안전하다는 뜻은 아니다. KeePassXC의 데이터베이스를 무검증 동기화하면 충돌과 오래된 사본이 생길 수 있다. Vaultwarden을 한 대의 NAS에 띄우면 편리하지만 NAS 관리자 계정과 백업 저장소가 동시에 침해될 수 있다. 공식 SaaS는 운영 부담을 줄이지만 계정 복구 정책과 벤더 장애를 받아들여야 한다. 선택 기준은 기능표보다 **누가 패치하고, 누가 복구하며, 실패 시 어떤 독립 사본이 남는가**다.

## 최근 보안 공지가 말해주는 업그레이드 원칙

GitHub Security Advisory API에서 확인한 2026년 공개 공지에는 아이콘 엔드포인트 SSRF 우회, brute-force 보호 우회, 조직 간 그룹 바인딩 권한 문제, SSO 이메일 자동 연결, refresh token 무효화, WebAuthn 처리, CSRF 등 여러 high·medium 항목이 포함됐다. 이는 Vaultwarden이 안전하지 않다는 단순 결론이 아니다. 인증·조직·SSO·외부 URL 가져오기처럼 경계가 만나는 기능에서 결함이 생길 수 있고, 보안 저장소는 **공지 구독과 신속한 검증 업데이트가 제품 기능의 일부**라는 뜻이다.

[Trivy 공급망 보안 글](/posts/github-trending-trivy-supply-chain-security/)에서 이미지 스캔을 기본 게이트로 본 것처럼 Vaultwarden 이미지도 digest 고정, 출처 확인, 취약점 스캔을 적용할 수 있다. 그러나 컨테이너 스캔은 애플리케이션 권한 결함이나 클라이언트 API 호환성을 증명하지 못한다. 릴리스 노트와 보안 공지, 열린 호환성 이슈, 실제 로그인·동기화 회귀 테스트를 함께 봐야 한다.

업데이트 절차는 `latest`를 매일 재시작하는 방식보다 다음처럼 운영하는 편이 안전하다.

- 운영 이미지를 버전 또는 digest로 고정하고 새 릴리스를 스테이징에 먼저 배포한다.
- 웹, 데스크톱, 모바일, 브라우저 확장 중 조직이 실제 쓰는 조합으로 로그인·동기화·항목 수정·첨부·조직 공유를 시험한다.
- 데이터베이스 마이그레이션 전 일관된 백업을 만들고 별도 환경에서 복원 가능성을 확인한다.
- high severity 공지가 사용 중 기능에 영향을 주면 정기 창을 기다리지 않는 긴급 패치 절차를 사용한다.
- 롤백이 데이터 스키마를 되돌릴 수 있는지 확인하고, 불가능하면 이전 서버 이미지보다 복원 절차를 우선한다.

## 실패 모드: 편리한 단일 컨테이너가 단일 장애점이 되는 순간

가장 흔한 실패는 `/data` 볼륨이 있으니 백업됐다고 믿는 것이다. 영속 볼륨은 컨테이너 삭제를 견디게 할 뿐 호스트 디스크 고장, 랜섬웨어, 운영자 실수, 잘못된 동기화, 데이터베이스 손상까지 해결하지 않는다. README도 비밀번호와 첨부 파일의 데이터 손실 가능성을 경고하며 정기 백업을 강하게 권한다. 최근 [Immich 데이터 거버넌스 글](/posts/github-trending-immich-self-hosted-photo-governance/)에서 원본 파일과 DB를 함께 복구해야 한다고 본 것처럼, Vaultwarden도 데이터베이스·첨부·설정·키 재료의 일관된 복구 단위를 문서화해야 한다.

두 번째는 관리자 페이지 노출이다. 관리 기능은 일반 금고와 다른 고권한 표면이다. 인터넷에 직접 공개하지 말고 VPN이나 관리 네트워크로 제한하며, 긴 관리자 토큰을 애플리케이션 데이터와 분리해 보관한다. 역방향 프록시의 실제 클라이언트 IP 전달을 잘못 구성하면 brute-force 제한과 감사 로그가 프록시 주소만 보게 될 수 있다.

세 번째는 이메일과 2FA 의존성이다. SMTP 장애가 로그인·초대·복구 흐름에 어떤 영향을 주는지, TOTP 장치를 잃었을 때 누가 어떤 증거로 복구를 승인하는지 확인해야 한다. 비밀번호 관리자 안에 그 비밀번호 관리자의 2FA 복구 코드만 보관하면 잠금 순환이 생긴다. 복구 코드는 암호화한 오프라인 사본 또는 별도 신뢰 경계에 둔다.

네 번째는 메타데이터와 로그다. 금고 내용이 암호화돼도 계정 이메일, 로그인 시간, IP, 조직 멤버십, 이벤트 로그는 민감할 수 있다. 최신 커밋에는 성공 로그인 로그에 사용자 이메일을 포함하는 변경이 있다. 탐지에는 도움이 되지만 로그 수집 시스템으로 개인정보가 더 넓게 복제될 수 있으므로 보존 기간과 접근 권한을 정해야 한다.

## PoC는 설치 시간이 아니라 복구 시간으로 측정한다

작은 PoC에서도 다음 항목을 수치로 남겨야 한다.

- **호환성**: 실제 클라이언트 조합별 로그인·동기화 성공률, 서버 업데이트 후 회귀 건수, 클라이언트 강제 업데이트가 서버보다 앞설 때의 영향
- **복구**: 빈 호스트에서 서비스가 다시 열릴 때까지 걸린 RTO, 마지막 사용 가능한 항목의 시점인 RPO, 첨부·조직·2FA 설정의 복구 완전성
- **보안**: 관리자 표면의 네트워크 제한, MFA 적용률, 비정상 로그인 탐지 시간, 보안 공지에서 패치 완료까지의 시간
- **가용성**: DNS·TLS 인증서·SMTP·스토리지·데이터베이스 장애를 각각 주입했을 때 읽기와 동기화가 어떻게 실패하는지
- **운영 비용**: 월별 업데이트·백업 검증·사용자 지원 시간, 저장소 증가량, 로그와 모니터링 비용

PoC 순서는 정상 설치보다 실패 리허설을 먼저 두는 편이 좋다. 테스트 사용자와 조직을 만들고, 여러 클라이언트에서 항목과 첨부를 동기화한다. 백업한 뒤 서버와 볼륨을 제거하고 새 호스트에 복원한다. 오래된 클라이언트와 최신 클라이언트를 섞어 회귀를 확인한다. 프록시를 잘못 설정하거나 SMTP를 중단해 경보와 사용자 메시지를 본다. 마지막으로 관리자 토큰과 2FA 장치를 잃었다는 가정으로 복구 절차가 실제로 작동하는지 검증한다.

## 도입 판단: 통제권을 가져올 준비가 됐는가

Vaultwarden은 개인, 가족, 홈랩, 소규모 조직처럼 공식 Bitwarden 클라이언트 경험을 유지하면서 작은 자원으로 서버를 운영하려는 환경에 매력적이다. 특히 이미 컨테이너, TLS, 역방향 프록시, 오프사이트 백업, 모니터링을 안정적으로 운영하고 있다면 추가 부담을 예측하기 쉽다. AGPL-3.0인 수정 버전을 네트워크 서비스로 제공하거나 제품화하려는 조직은 법무 검토와 소스 제공 의무를 별도로 확인해야 한다.

반대로 전담 운영자가 없거나 복원 훈련을 할 수 없고, 고객 SLA와 공식 지원이 필요하며, 자동 업데이트 외의 릴리스 관리가 불가능하다면 공식 관리형 서비스를 우선하는 편이 안전하다. 셀프호스팅이 데이터 주권을 주는 것은 맞지만, 패치가 늦고 백업이 복원되지 않는 서버는 통제권이 아니라 집중된 위험이다.

결정 질문은 단순하다. “서버를 띄울 수 있는가”가 아니라 **클라이언트 호환성이 깨진 날, 보안 공지가 나온 날, 디스크와 2FA 장치를 함께 잃은 날에도 금고를 안전하게 되살릴 수 있는가**다. 그 질문에 절차와 측정값으로 답할 수 있을 때 Vaultwarden은 비용 절감 도구를 넘어 운영 가능한 자격 증명 인프라가 된다.

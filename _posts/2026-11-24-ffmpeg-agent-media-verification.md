AI에게 “이 영상을 세로 숏폼으로 바꾸고 자막과 음량을 맞춰 줘”라고 요청하면 편집 명령을 만드는 일보다 더 어려운 문제가 남는다. **출력 파일이 실제로 재생되는가, 요청한 코덱과 프레임 크기를 지켰는가, 오디오가 영상과 어긋나지 않았는가, 검증하지 못한 결과를 성공으로 오인하지 않았는가**를 판정해야 한다. 자연어 에이전트가 FFmpeg 명령을 즉석에서 조합하는 것만으로는 이 경계를 안정적으로 만들기 어렵다.

[kajisho5/ffmpeg-skill](https://github.com/kajisho5/ffmpeg-skill)은 이 문제를 “영상 편집 프롬프트”가 아니라 **기계 판독 가능한 실행 계약과 검증 결과**로 다룬다. 2026년 11월 24일 GitHub API 스냅샷 기준 저장소는 약 1.02만 stars, 892 forks, MIT 라이선스였고 최신 릴리스는 전날 공개된 `v4.7.1`이었다. 숫자는 변하는 인기도 지표일 뿐이다. 더 주목할 부분은 42개 도구의 입력 스키마, 안정성, 종료 코드, 결과 필드와 검증 정책을 약 950KB의 계약 문서로 생성한다는 설계다.

이미 [video-use 분석](/posts/github-trending-video-use-agent-video-editing/)에서 transcript와 EDL을 중심으로 “무엇을 편집할지”를 구조화하는 방식을 살펴봤다. 이번 글의 검색 의도는 다르다. 편집 판단 이후의 실행 계층에서 **어떻게 성공과 실패를 자동 판정할 것인가**가 중심이다.

## 핵심은 명령 생성이 아니라 증명 가능한 결과다

일반적인 에이전트 통합은 프롬프트에 FFmpeg 예시 몇 개를 넣고 셸 실행 권한을 준다. 빠르게 시작할 수 있지만 도구마다 옵션 이름과 출력 형식이 다르고, FFmpeg가 종료 코드 0을 반환했다는 사실을 결과물의 적합성으로 착각하기 쉽다. 파일은 만들어졌지만 음성 스트림이 없거나, 플랫폼 규격과 다른 크기이거나, 음량 측정이 실패한 상태도 “완료”로 전달될 수 있다.

ffmpeg-skill은 이 간극을 네 층으로 나눈다.

![FFmpeg 에이전트 실행 계약과 검증 파이프라인](https://heracles-jo.github.io/assets/img/posts/ffmpeg-agent-media-verification/architecture.svg)
_자연어 계획, 기계 판독 계약, 로컬 FFmpeg 실행, 산출물 검증을 분리해야 실패를 재현하고 정책으로 처리할 수 있다._

1. **계획 계층**은 사용자의 의도를 컷, 리프레임, 자막, 음량, 내보내기 단계로 바꾼다.
2. **계약 계층**은 도구별 필수 입력, 선택 옵션, 상호 배타 규칙, 출력 스키마와 안정성을 제공한다.
3. **실행 계층**은 셸 문자열을 임의 조합하지 않고 로컬 Python 도구가 FFmpeg·ffprobe를 호출한다.
4. **검증 계층**은 파일 존재만 보지 않고 스트림, 코덱, 크기, 프레임률, 길이, 음량과 콘텐츠 검사를 결과 문서에 남긴다.

저장소의 계약 문서는 코드 옆에 수동으로 복사해 둔 명세가 아니다. 각 스크립트의 `argparse` 정의에서 `input_schema`를 생성하고, 테스트가 실제 스크립트·MCP 서버·설치 프로그램의 도구 목록이 일치하는지 확인한다. 문서와 구현이 어긋나면 에이전트는 오래된 옵션을 계속 호출한다. 이 프로젝트는 그 드리프트를 CI 실패로 바꾸려 한다.

이는 [Modern Web Guidance의 에이전트 웹 검증 구조](/posts/modern-web-guidance-agent-web-validation/)와 같은 방향이다. 규칙을 자연어 조언으로만 남기지 않고, 실행 가능한 검사와 실패 코드로 만들어야 자동화가 반복될수록 품질이 올라간다.

## `status=completed`와 `verified=true`를 분리해야 한다

미디어 파이프라인에서 가장 위험한 모델은 성공 여부를 하나의 불리언으로 표현하는 것이다. 인코딩 프로세스가 끝난 것, 파일이 열리는 것, 플랫폼 사양을 만족한 것, 콘텐츠 품질이 허용 범위인 것은 서로 다른 사실이다.

ffmpeg-skill 결과는 실행 상태와 검증 상태를 분리한다. 쓰기 도구는 출력 파일이 존재하고 비어 있지 않으며 ffprobe가 스트림을 읽을 수 있는지 먼저 확인한다. 그 위에 도구별 `verification` 단계가 붙고, 모든 필수 검사가 통과해야 `verified: true`가 된다. `--dry-run`은 명령을 계획할 수 있지만 산출물을 검사하지 않았으므로 검증 성공으로 표시하지 않는다.

실무에서는 이 구분을 다음처럼 정책에 연결할 수 있다.

| 결과 상태 | 의미 | 자동화 정책 |
|---|---|---|
| 프로세스 실패 | FFmpeg 실행, 입력, 의존성 또는 시간 제한 실패 | 재시도 전 원인 분류, 결과 배포 금지 |
| 파일 생성·검증 실패 | 파일은 있으나 필수 스트림·코덱·크기·길이 규격 불충족 | 산출물 격리, 수정 가능한 단계만 재실행 |
| 완료·미검증 | 파일은 유효하지만 음량 등 일부 기준을 충족하지 못함 | 미리보기만 허용, 외부 게시 차단 |
| 완료·검증 성공 | 명시된 기계 검사가 모두 통과 | 사람 승인 또는 다음 자동 단계로 승격 |

여기서 `verified=true`도 “영상이 좋다”는 뜻은 아니다. 자막의 문맥, 컷의 리듬, 브랜드 표현, 초상권과 저작권은 기계 검사만으로 확정할 수 없다. 검증 필드는 **측정한 조건을 통과했다는 좁은 주장**이어야 한다. 무엇을 측정하지 않았는지 함께 보존해야 한다.

## 미디어 계약에서 반드시 잠가야 할 다섯 가지

### 1. 입력과 출력을 같은 파일로 취급하지 않는다

에이전트가 경로를 잘못 해석하면 원본을 덮어쓸 수 있다. ffmpeg-skill은 기본적으로 기존 출력을 거부하고 명시적 `--overwrite`를 요구하며, 입력과 출력이 같은 경로인지도 검사한다. 운영 환경에서는 여기에 작업별 격리 디렉터리, 읽기 전용 원본 마운트, 출력 용량 제한을 추가해야 한다.

### 2. 시간은 초가 아니라 프레임 규칙으로 해석한다

`1.902초에서 자르기` 같은 입력은 프레임률에 따라 실제 프레임 경계가 달라진다. 밀리초 반올림, VFR 소스, 키프레임 기반 stream copy가 섞이면 시작점이 한 프레임씩 이동한다. 최근 저장소 커밋도 밀리초 시간을 프레임에 맞춰 해석하는 결함을 수정했다. PoC에서는 단순 길이 비교보다 **첫 프레임, 마지막 프레임, 자막 cue, 오디오 onset을 함께 대조**해야 한다.

### 3. 코덱 이름만 보지 말고 컨테이너와 스트림 조합을 본다

`H.264로 만들었다`는 말만으로 납품 규격을 보장할 수 없다. 컨테이너가 코덱을 수용하는지, 비디오·오디오 스트림이 모두 있는지, 픽셀 포맷과 프로파일이 맞는지, 다중 오디오·자막·챕터가 보존됐는지 확인해야 한다. 소스에 있던 항목 중 무엇이 유지되고 삭제됐는지 `source_carry`처럼 별도 기록하는 방식이 유용하다.

### 4. 음량 정규화와 A/V 동기화를 한 문제로 본다

음량 필터는 소리만 바꾸는 것처럼 보이지만 타임스탬프의 빈 구간을 닫아 이후 오디오를 앞당길 수 있다. 프로젝트의 최근 변경 내역에는 짧은 오디오 gap을 채운 뒤 loudness 처리를 수행해 영상과 소리의 위치를 유지하는 수정이 포함됐다. 따라서 LUFS 목표 통과와 함께 플래시-비프 같은 기준 신호로 **처리 전후 동기화 오차**도 측정해야 한다.

### 5. 도구 계약 버전과 미디어 런타임을 함께 고정한다

계약 문서는 `contract_version`과 패키지 버전을 구분한다. 스키마 형태가 유지돼도 도구 동작은 결함 수정이나 FFmpeg 변경에 따라 달라질 수 있다. 실제 배포에서는 ffmpeg-skill 버전, Python, FFmpeg 빌드, 인코더 목록, 폰트와 모델 파일의 해시를 작업 기록에 남겨야 한다. [HyperFrames 영상 렌더링 파이프라인 분석](/posts/github-trending-hyperframes-html-video-rendering-pipeline/)에서 브라우저와 폰트를 잠그라고 한 이유와 같다.

## 보안 경계: 로컬 실행은 자동으로 안전하지 않다

이 프로젝트는 네트워크 API와 클라우드 키 없이 로컬에서 동작한다고 설명한다. 데이터가 외부 서비스로 전송되지 않는 장점은 분명하지만, “로컬”은 보안 속성이 아니라 배치 위치다. 코딩 에이전트가 파일 시스템과 프로세스 실행 권한을 가지면 다음 위험은 그대로 남는다.

- 사용자가 제공한 미디어 경로를 벗어난 파일 읽기
- 출력 경로, 심볼릭 링크, 하드 링크를 통한 원본 훼손
- 비정상적으로 큰 영상이나 필터 그래프로 인한 CPU·메모리·디스크 고갈
- 자막·메타데이터·첨부 파일에 포함된 비신뢰 입력 처리
- 선택적 음성 인식 모델 설치 과정의 공급망 및 네트워크 통제
- ffmpeg/ffprobe 빌드 차이로 인한 미지원 인코더와 예외 동작

계약의 `execution.shell: false`, 입력 비변경, 네트워크 비사용 같은 필드는 에이전트가 기대할 수 있는 경계를 명시한다. 그러나 최종 방어선은 별도 샌드박스여야 한다. 작업 컨테이너에 CPU·메모리·실행 시간을 제한하고, 원본은 읽기 전용으로 마운트하며, 출력은 작업 전용 경로만 허용하는 편이 안전하다. 외부 게시 권한은 편집 에이전트와 분리해야 한다.

## 실패 모드를 기준으로 도입 여부를 판단한다

![FFmpeg 에이전트 도입 결정을 위한 위험과 대응 매트릭스](https://heracles-jo.github.io/assets/img/posts/ffmpeg-agent-media-verification/risk-matrix.svg)
_명령 생성 정확도보다 검증 누락, 원본 보호, 런타임 드리프트와 사람 승인 경계를 먼저 측정해야 한다._

| 실패 모드 | 탐지 신호 | 완화책 | 중단 기준 |
|---|---|---|---|
| 옵션·스키마 드리프트 | 알 수 없는 인자, MCP 호출 실패 | 계약 버전 핀, CI 스냅샷 | 호환성 변경이 릴리스 노트 없이 발생 |
| 재생 가능하지만 규격 불일치 | `verified=false`, 코덱·크기·fps 실패 | 플랫폼 프리셋과 납품 검사 | 게시 단계가 미검증 결과를 허용 |
| A/V 동기화 손상 | 기준 신호 오차, packet timestamp 차이 | gap 포함 fixture, 전후 비교 | 허용 오차를 반복 초과 |
| 원본 또는 기존 출력 훼손 | 입력·출력 동일 경로, 링크 경로 | 읽기 전용 원본, overwrite 승인 | 원본 복구가 작업자 기억에 의존 |
| 자원 고갈 | wall time, peak RSS, 임시 파일 증가 | 제한된 워커, timeout, quota | 한 작업이 큐 전체를 막음 |
| 시각 품질 열화 | 과도한 crop·pad, 자막 가림 | contact sheet, 사람 검토 | 기계 통과가 곧 자동 게시로 연결 |

[Open Code Review의 하이브리드 검토 구조](/posts/open-code-review-hybrid-ai-code-review/)처럼 미디어 자동화도 “모델이 만든 결과를 다른 모델이 한 번 더 본다”로 끝내기보다, 결정적 검사와 사람 판단을 서로 다른 게이트로 구성하는 편이 낫다. 코덱·프레임률·음량은 기계가 차단하고, 컷의 의미와 표현 위험은 사람이 승인한다.

## PoC에서는 편집 기능보다 검증 커버리지를 측정하라

초기 실험에서 화려한 요청을 몇 개 성공시키는 것은 어렵지 않다. 운영 적합성을 보려면 정상 샘플보다 실패 fixture가 필요하다. 최소한 다음 세트를 준비할 만하다.

- CFR·VFR, 23.976·29.97·60fps와 비정상 시작 타임스탬프
- 무음, 짧은 gap, 다중 오디오, 5.1채널, AAC priming이 있는 소스
- HDR, BT.709, 10-bit, 세로·가로·비정사각 픽셀 영상
- 자막, 챕터, cover art, timecode, 언어 태그가 있는 컨테이너
- 0바이트, 손상된 `moov`, 확장자와 실제 포맷이 다른 입력
- 이미 존재하는 출력, 읽기 전용 경로, 심볼릭 링크·하드 링크 경계

측정표에는 성공률 하나만 적지 않는다. 첫 호출 성공률, 잘못된 옵션의 교정 가능성, 평균·최대 실행 시간, peak RSS, 임시 디스크, 검증 누락률, 사람 재작업 시간, 원본 보존 여부를 함께 기록한다. 특히 “검증할 수 없음”을 실패와 구분해 집계해야 한다. 미측정을 성공으로 채우는 순간 품질 게이트는 사라진다.

## 어떤 팀에 맞고, 어디까지 맡겨야 하는가

ffmpeg-skill 같은 계약형 도구는 반복 가능한 변환이 많은 팀에 잘 맞는다. 제품 데모를 여러 플랫폼 규격으로 내보내거나, 강의 영상에 정형 자막을 넣거나, 내부 미디어 파이프라인의 포맷 검사를 자동화하는 경우다. 반대로 서사 편집, 정교한 색보정, 복잡한 멀티캠, 프레임 단위 창작 판단이 핵심이라면 NLE를 대체하기보다 전처리·검사·납품 자동화에 제한하는 편이 현실적이다.

도입 순서는 다음이 안전하다.

1. `probe`, `check`, `look` 같은 읽기·검증 도구부터 연결한다.
2. 출력 전용 디렉터리에서 `cut`, `fit`, `loudness`, `export`를 실행한다.
3. 계약·런타임 버전과 fixture를 CI에 고정한다.
4. `verified=true`인 결과만 검토 큐로 보내되 자동 게시 권한은 주지 않는다.
5. 사람 승인 이후의 배포는 별도 서비스 계정과 감사 로그로 수행한다.

핵심 판단은 간단하다. FFmpeg 에이전트의 품질은 자연어를 얼마나 그럴듯한 명령으로 번역하느냐보다, **산출물이 요청한 조건을 충족했다는 사실을 얼마나 좁고 재현 가능하게 증명하느냐**에 달려 있다. ffmpeg-skill은 편집 기능의 수보다 계약, 실패 코드, 검증 단계와 호환성 테스트가 운영 자동화의 중심이어야 한다는 좋은 사례다.

## 왜 지금 C++ 기반 라이브러리인가

C++는 새롭지 않다. 그래서 오히려 실무에서 위험하다. 새 기술은 PoC 단계에서 과장되기 쉽지만, 오래된 C++ 코드는 이미 결제, 네트워크, 로봇, 차량, 보안 장비, 스토리지, 미디어 처리 파이프라인 안에서 오래 동작하고 있다. 이런 시스템은 한 번의 버전 변경, ABI 불일치, 빌드 옵션 차이, 예외 처리 정책 충돌, 스레드 모델 오해만으로도 장애 범위가 커질 수 있다.

최근 AI 인프라의 확산도 이 흐름을 강화한다. LLM 서빙, 벡터 검색, 영상 처리, 브라우저 자동화, 샌드박스 실행 환경은 겉으로는 Python이나 TypeScript API를 제공하더라도 내부에는 C/C++/Rust 네이티브 계층이 많다. 운영자는 “모델이 좋은가”만이 아니라 “토큰이 들어오기 전후의 네트워크 I/O, 설정, 캐시, 로그, 테스트가 재현 가능한가”를 봐야 한다. Abseil, Catch2, yaml-cpp, Asio 같은 라이브러리가 Trending에 오른 것은 단순한 향수라기보다, 고성능·저지연·장기 운영 시스템의 기초 체력을 다시 보자는 신호로 읽을 수 있다.

## 네 가지 라이브러리가 담당하는 아키텍처 계층

### 1. Abseil: 공통 유틸리티와 API 규율

[Abseil](https://abseil.io/)은 Google에서 공개한 C++ 공통 라이브러리다. 문자열, 시간, 컨테이너, 동기화, 로그, 상태 표현 등 애플리케이션 전반에서 반복되는 유틸리티를 제공한다. 실무적으로 중요한 점은 기능의 양이 아니라 “팀이 직접 만든 사내 유틸리티가 무분별하게 늘어나는 현상”을 제어할 수 있다는 데 있다.

대규모 C++ 코드베이스에서는 `utils`, `common`, `base`라는 이름의 디렉터리가 빠르게 커진다. 처음에는 편의 함수였지만, 시간이 지나면 예외 정책, 문자열 인코딩, 시간대 처리, 에러 전달 방식, 로깅 포맷이 각 팀마다 달라진다. Abseil은 이런 영역에 대해 비교적 명확한 API와 릴리스 정책을 제공한다. 다만 Abseil은 C++ 표준 라이브러리의 대체품이라기보다 표준화 전후의 갭을 메우는 계층에 가깝다. 이미 C++20/23 기능을 적극적으로 쓰는 조직이라면 Abseil 기능 중 일부가 중복될 수 있고, 반대로 오래된 컴파일러를 유지해야 하는 조직에는 호환성 레이어로 가치가 크다.

확인 시점 Abseil 저장소는 17,505 stars, Apache-2.0 라이선스, 2026-06-01에 `20260526.0` 릴리스를 게시했고, 2026-07-10에도 커밋이 있었다. 활발한 유지보수 신호는 긍정적이지만, “Google이 쓰니까 안전하다”는 식의 단정은 피해야 한다. 내부 코드 스타일, 빌드 시스템, 릴리스 주기와 맞는지 별도 검토해야 한다.

### 2. Catch2: 테스트 프레임워크는 개발자 편의가 아니라 릴리스 안전장치

[Catch2](https://github.com/catchorg/Catch2)는 C++ 테스트 프레임워크다. 확인 시점 20,605 stars, BSL-1.0 라이선스, 2026-07-07에 `v3.15.2` 릴리스가 게시되어 있었다. 최근 커밋에는 `catch_discover_tests()`의 JSON 파싱 최적화처럼 CI와 테스트 발견 성능에 영향을 주는 변경도 보인다.

C++에서 테스트 프레임워크 선택은 문법 취향 문제가 아니다. 빌드 시간, 테스트 디스커버리, 병렬 실행, CMake 통합, sanitizer와의 조합, Windows/Linux/macOS 매트릭스, 예외 비활성화 빌드 지원 여부까지 운영 조건이 달라진다. Catch2는 단일 헤더 시대의 간편함으로 유명했지만, v3 계열에서는 패키징과 빌드 통합 방식을 더 신중하게 봐야 한다.

대체 도구로는 [GoogleTest](https://github.com/google/googletest)와 [doctest](https://github.com/doctest/doctest)가 자주 비교된다. GoogleTest는 대기업·장기 프로젝트에서 표준처럼 쓰이며 생태계가 넓다. doctest는 컴파일 시간과 경량성을 중시하는 프로젝트에 매력적이다. Catch2는 표현력과 사용성, CMake 연동 사이에서 균형을 제공한다. 따라서 이미 GoogleTest 기반의 대규모 테스트 자산이 있다면 전환보다 공존 전략이 현실적이고, 새 모듈이나 라이브러리 단위 테스트부터 Catch2를 적용하는 방식이 더 안전하다.

### 3. yaml-cpp: 설정 파일은 작은 기능이 아니라 운영 인터페이스다

[yaml-cpp](https://github.com/jbeder/yaml-cpp)는 C++용 YAML 파서와 emitter다. 확인 시점 6,072 stars, MIT 라이선스, 2026-02-04에 `yaml-cpp-0.9.0` 릴리스가 있었고, 2026-07-07에도 문서와 기능 관련 커밋이 있었다. YAML 파서는 화려한 기술처럼 보이지 않지만, 운영 시스템에서는 설정 파일이 곧 제품의 외부 인터페이스다.

문제는 YAML 자체가 사람이 읽기 쉬운 만큼 모호성도 많다는 점이다. 들여쓰기, 앵커, 암시적 타입 변환, 큰 파일 처리, 잘못된 스키마, 보안상 위험한 입력 처리 등이 장애 원인이 된다. yaml-cpp를 도입한다는 것은 “YAML을 읽을 수 있다”에서 끝나지 않는다. 스키마 검증, 기본값 정책, deprecated 필드 처리, 에러 메시지 품질, 설정 변경의 롤백, 민감정보 마스킹, 런타임 reload 정책을 함께 설계해야 한다.

대체 접근은 JSON, TOML, protobuf text format, 자체 DSL 등이다. JSON은 도구 지원이 넓지만 주석과 사람이 관리하는 설정 측면에서 불편하다. TOML은 설정 파일로 깔끔하지만 복잡한 계층 구조에는 한계가 있다. protobuf는 스키마와 호환성에는 강하지만 운영자가 직접 편집하는 경험은 떨어질 수 있다. YAML을 선택한다면 yaml-cpp 자체보다 “운영자가 실수했을 때 시스템이 어떻게 실패하는가”가 핵심 판단 기준이다.

### 4. Asio: 비동기 I/O의 실제 비용

[Asio](https://github.com/chriskohlhoff/asio)는 C++ 비동기 I/O 라이브러리다. Boost.Asio와 독립 Asio 양쪽 맥락에서 오랫동안 사용되어 왔다. 확인 시점 6,064 stars, 최근 커밋은 2026-07-06이며 MSVC와 채널 컴파일 관련 수정이 보였다. Asio의 의미는 “네트워크 코드를 짧게 작성한다”가 아니라 이벤트 루프, 타이머, 소켓, 코루틴, 스레드 풀, cancellation, backpressure 같은 운영 난제를 한 모델 안에서 다루는 데 있다.

비동기 I/O는 성능 개선의 만능키가 아니다. 잘못 설계하면 콜백/코루틴의 생명주기, 객체 소유권, 타임아웃 누락, 에러 전파, graceful shutdown이 더 어려워진다. 특히 C++에서는 dangling reference, strand 사용 오해, executor 정책 불일치, 예외 경계 누락이 장애로 이어진다. Asio 도입은 라이브러리 선택보다 팀의 비동기 프로그래밍 규율을 요구한다.

대체 도구로는 libuv, folly, Seastar, Rust의 Tokio 같은 런타임이 있다. libuv는 C 기반 이벤트 루프로 이식성이 강하고 Node.js 생태계와도 연결된다. folly는 Meta 내부 규모의 C++ 유틸리티와 결합되어 강력하지만 도입 표면적이 크다. Seastar는 shard-per-core 모델로 고성능 서버에 강하지만 설계 제약이 크다. Tokio는 Rust 프로젝트라면 가장 강력한 선택지 중 하나지만, 기존 C++ 코드베이스를 즉시 대체하기는 어렵다. Asio는 기존 C++ 시스템 안에서 점진적으로 비동기 모델을 정리할 때 현실적인 선택지가 된다.

## 기존 방식과 비교: “사내 common”의 비용

많은 조직은 처음부터 Abseil, Catch2, yaml-cpp, Asio를 도입하지 않는다. 작은 프로젝트에서는 표준 라이브러리, 직접 만든 파서, 간단한 테스트 매크로, blocking socket만으로 충분하다. 문제는 제품이 커지고 운영 기간이 길어질 때 나타난다.

| 영역 | 사내 구현 중심 접근 | 검증된 오픈소스 기반 접근 |
|---|---|---|
| 공통 유틸리티 | 빠르게 시작하지만 팀별 관용구가 분산된다. | API 규율과 문서화된 동작을 공유할 수 있다. |
| 테스트 | 초기 비용은 낮지만 리포팅·디스커버리·CI 통합이 약해진다. | 회귀 방지와 빌드 매트릭스 운영이 쉬워진다. |
| 설정 파싱 | 제품 요구에 딱 맞출 수 있지만 예외 케이스가 누적된다. | 널리 검증된 파서를 쓰되 스키마와 정책은 별도 설계해야 한다. |
| 비동기 I/O | 단순 서버에는 충분하지만 확장 시 생명주기 관리가 어려워진다. | 이벤트 루프 모델을 표준화할 수 있으나 학습 비용이 있다. |

오픈소스 기반 접근의 장점은 “남이 만들어서 공짜”가 아니다. 더 중요한 가치는 장애를 설명할 언어가 생긴다는 점이다. 예를 들어 테스트 실패가 Catch2 리포트로 남고, 설정 파싱 오류가 yaml-cpp 예외와 내부 스키마 검증 메시지로 분리되며, 네트워크 타임아웃이 Asio 타이머 정책으로 추적된다면, 운영팀과 개발팀이 같은 단어로 문제를 논의할 수 있다.

## 실무 도입 장점과 한계

장점은 명확하다. 첫째, 장기 운영 코드베이스의 반복 문제를 표준화한다. 둘째, 신규 인력 온보딩이 쉬워진다. C++ 프로젝트에서 가장 큰 비용 중 하나는 “이 팀만의 방식”을 이해하는 시간이다. 널리 쓰이는 라이브러리는 문서, 예제, 검색 가능한 이슈가 있어 학습 경로가 짧다. 셋째, CI/CD 품질을 끌어올릴 수 있다. Catch2와 sanitizer, coverage, benchmark를 조합하면 성능 회귀와 메모리 오류를 더 일찍 발견한다. 넷째, 플랫폼 이식성을 개선할 가능성이 있다. Asio나 Abseil처럼 다양한 플랫폼을 고려한 라이브러리는 Windows/MSVC, Linux/GCC, macOS/Clang 차이를 직접 감당하는 부담을 줄여준다.

하지만 한계도 작지 않다. Abseil은 내부 API 사용 방식과 릴리스 정책을 이해하지 않으면 표준 라이브러리와 중복 계층이 될 수 있다. Catch2는 테스트가 많아질수록 빌드 시간과 discovery 비용을 관리해야 한다. yaml-cpp는 YAML의 표현력을 그대로 열어두면 운영자가 예측하기 어려운 설정을 만들 수 있다. Asio는 비동기 모델이 팀 전체에 정착하지 않으면 일부 모듈만 복잡해지고 디버깅 난도가 올라간다.

또 하나의 한계는 패키지 관리다. C++은 npm이나 Cargo처럼 사실상의 단일 패키지 관리 경험이 약하다. [vcpkg](https://github.com/microsoft/vcpkg), [Conan](https://github.com/conan-io/conan), 시스템 패키지, Git submodule, FetchContent, 내부 미러가 혼재한다. 따라서 라이브러리 채택 결정은 반드시 빌드·패키징 전략과 함께 내려야 한다. “README에 설치 명령이 있다”는 이유만으로 프로덕션 채택을 결정하면, 6개월 뒤 CI 캐시, 사내 프록시, 크로스 컴파일, 보안 스캔에서 비용을 치르게 된다.

## 보안, 운영, 성능 리스크

가장 먼저 볼 리스크는 공급망이다. C++ 라이브러리는 빌드 단계에서 소스, 컴파일러, 링커, 플랫폼 SDK와 강하게 결합한다. 단순히 GitHub stars가 많다고 안전한 것이 아니다. 릴리스 태그 서명 여부, 패키지 매니저 레시피의 출처, 의존성 잠금, 내부 아티팩트 저장소, SBOM 생성, 취약점 스캔 대상 포함 여부를 확인해야 한다.

두 번째는 ABI와 링크 정책이다. 정적 링크는 배포 단순성을 높이지만 보안 패치 반영과 바이너리 크기에 영향을 준다. 동적 링크는 패치 교체가 쉬울 수 있지만 런타임 환경 차이와 ABI 충돌을 부른다. 특히 C++ 표준 라이브러리, 컴파일러 버전, `_GLIBCXX_USE_CXX11_ABI` 같은 옵션은 장애 원인이 되기 쉽다.

세 번째는 성능 회귀다. Abseil 컨테이너나 Asio 비동기 I/O는 성능을 개선할 가능성이 있지만, 잘못 사용하면 반대로 메모리 사용량과 tail latency가 증가한다. yaml-cpp로 큰 설정 파일을 자주 파싱하거나, Catch2 테스트를 무거운 통합 테스트처럼 남용하는 경우도 마찬가지다. 도입 전후 benchmark와 프로파일링 기준선을 만들어야 한다.

네 번째는 유지보수 경계다. 오픈소스 라이브러리의 이슈 수가 많다는 것은 활발함의 신호일 수도 있고, 오래된 요구와 플랫폼 조합이 누적되었다는 뜻일 수도 있다. 확인 시점 Asio는 open issues가 1,071개, Catch2는 433개, Abseil은 234개, yaml-cpp는 213개였다. 숫자 자체로 품질을 판단해서는 안 되지만, 우리 조직이 의존할 기능과 관련된 이슈가 열려 있는지는 반드시 확인해야 한다.

## PoC 체크리스트

C++ 기반 라이브러리 도입은 “샘플이 빌드된다”에서 끝나면 실패하기 쉽다. 아래 체크리스트를 PoC 종료 조건으로 삼는 편이 안전하다.

- [ ] 지원 컴파일러와 표준 버전(C++17/20/23)을 명확히 정한다.
- [ ] CMake, Bazel, vcpkg, Conan 중 공식 빌드 경로를 하나 이상 고정한다.
- [ ] 정적 링크와 동적 링크 중 기본 정책을 정하고 예외 조건을 문서화한다.
- [ ] Linux, macOS, Windows 또는 타깃 임베디드 환경의 CI matrix를 만든다.
- [ ] Catch2 또는 기존 테스트 프레임워크와 sanitizer를 함께 실행한다.
- [ ] yaml-cpp 사용 시 스키마 검증, 기본값, deprecated 필드, 에러 메시지 정책을 구현한다.
- [ ] Asio 사용 시 timeout, cancellation, shutdown, backpressure, executor/strand 규칙을 코드 리뷰 체크리스트에 넣는다.
- [ ] Abseil 사용 시 표준 라이브러리와 중복되는 API의 사용 기준을 정한다.
- [ ] SBOM, 라이선스, CVE 모니터링, 내부 미러링 절차를 만든다.
- [ ] 성능 기준선과 롤백 절차를 배포 문서에 포함한다.

## 어떤 팀에 적합하고, 어떤 경우 피해야 하는가

이 흐름은 네이티브 성능, 장기 호환성, 플랫폼 이식성을 동시에 요구하는 팀에 적합하다. 예를 들어 네트워크 장비, 게임 서버, 영상 처리, 로봇/제조 제어, 브라우저 기반 엔진, 고성능 데이터 처리, 온프레미스 에이전트, 보안 제품을 운영하는 팀이라면 C++ 기반 라이브러리 스택 정비가 실질적인 효과를 낼 수 있다.

반대로 제품의 핵심 병목이 C++ 계층이 아니거나, 팀 내 C++ 유지보수 역량이 약하거나, 배포 대상이 단일 플랫폼이고 성능 요구가 높지 않다면 도입 범위를 줄이는 편이 낫다. 특히 단순 설정 파일을 위해 YAML의 복잡성을 감수하거나, 작은 CLI 도구에 무거운 비동기 I/O 구조를 넣는 것은 과한 설계가 될 수 있다. 좋은 엔지니어링은 더 많은 라이브러리를 넣는 것이 아니라, 장애를 줄이는 방향으로 의존성을 제한하는 것이다.

## 향후 관찰해야 할 지표

앞으로는 세 가지 지표를 보면 좋다. 첫째, 릴리스 주기와 컴파일러 지원 정책이다. C++ 생태계는 C++20/23 도입 속도가 빨라지고 있어, 라이브러리가 어떤 표준을 기본으로 삼는지가 중요해진다. 둘째, 패키지 매니저 생태계의 안정성이다. vcpkg와 Conan 레시피가 얼마나 빠르게 업데이트되고, 조직 내부 캐시와 보안 스캔에 잘 붙는지 확인해야 한다. 셋째, AI 인프라와 네이티브 계층의 접점이다. LLM serving, agent sandbox, browser automation, multimodal processing이 커질수록 C++ 기반 라이브러리의 운영 품질이 상위 애플리케이션의 안정성을 좌우할 가능성이 크다.

GitHub Trending은 장기 기술 전략을 결정하는 절대 지표가 아니다. 그러나 어느 날 어떤 저장소들이 함께 떠오르는지는 현장의 관심사가 어디로 이동하는지 보여주는 유용한 온도계다. 오늘의 C++ 기반 라이브러리 동시 부상은 “새 프레임워크를 쫓아가라”는 신호가 아니라, 오래 운영되는 시스템의 공통 부품, 테스트, 설정, 비동기 I/O를 다시 정리하라는 신호에 가깝다. 실무 의사결정자에게 중요한 질문은 하나다. 우리 팀의 C++ 코드는 지금도 제품의 핵심 경로에 있는가? 그렇다면 다음 장애를 줄이는 가장 현실적인 투자는 새로운 기능이 아니라, 기반 라이브러리 스택의 표준화와 운영 검증일 수 있다.

AI 코딩 에이전트 한 개가 빨라졌다면 다음 질문은 자연스럽다. 같은 문제를 여러 에이전트에게 동시에 맡기면 개발 속도도 그만큼 빨라질까? 답은 조건부다. 구현 대안을 탐색하거나 재현하기 어려운 버그를 여러 각도에서 조사할 때는 효과가 크다. 반면 같은 작업 디렉터리에서 여러 에이전트가 파일을 덮어쓰거나, 결과를 비교할 자동 검증이 없거나, 사람이 다섯 개의 거대한 diff를 읽어야 한다면 병렬화는 속도가 아니라 혼란을 늘린다.

[stablyai/orca](https://github.com/stablyai/orca)는 이 문제를 모델 API의 오케스트레이션보다 **개발 작업 공간의 오케스트레이션**으로 접근한다. Claude Code, Codex를 비롯한 터미널 기반 에이전트를 실행하고, 각 작업을 독립된 Git worktree에 배치하며, 터미널·diff·브라우저·원격 호스트·모바일 상태를 한 화면에서 관리하는 도구다. 핵심은 “에이전트 다섯 개”가 아니라 “서로 오염시키지 않는 변경 후보 다섯 개”다.

2026년 7월 16일 07:51 KST 공개 스냅샷에서 Orca 저장소는 약 19.8k stars, 1.5k forks, 1,485개의 열린 이슈·PR을 표시했고, 주 언어는 TypeScript였다. 최신 릴리스는 7월 16일 KST에 게시된 [v1.4.142](https://github.com/stablyai/orca/releases/tag/v1.4.142)였으며, 같은 날 worktree·터미널 수명주기와 원격 relay 관련 수정이 계속 반영됐다. 이 수치는 확인 시점의 상태이며 이후 바뀔 수 있다. 활발한 개발은 긍정적 신호지만, 높은 변경 속도와 큰 이슈 큐는 안정성 검증을 생략해도 된다는 뜻이 아니다.

Search Console과 Analytics의 쿼리·순위 데이터에는 이번 실행 환경에서 접근할 수 없었다. 따라서 노출이나 CTR을 봤다고 가정하지 않고, 기존 68개 글의 제목·설명·태그·내부 주제와 실시간 저장소 자료를 대조해 주제를 정했다.

## Git worktree가 해결하는 것과 해결하지 못하는 것

Git worktree는 하나의 저장소 객체 데이터베이스를 공유하면서 서로 다른 브랜치를 별도 디렉터리에 체크아웃한다. 전체 저장소를 여러 번 clone하는 방식보다 객체 중복을 줄이고, 각 디렉터리의 파일 상태와 인덱스는 분리할 수 있다. 에이전트 A가 인증 오류를 최소 수정하고, 에이전트 B가 인증 계층을 리팩터링하며, 에이전트 C가 실패 재현 테스트만 만드는 식의 실험에 잘 맞는다.

Orca의 [공식 한국어 README](https://github.com/stablyai/orca/blob/main/docs/readme/README.ko.md)는 하나의 프롬프트를 여러 에이전트에 보내되 각 에이전트를 자체 worktree에서 실행하고 결과를 비교해 가장 좋은 것을 병합하는 흐름을 전면에 둔다. GitHub·Linear 작업에서 worktree를 열고, diff에 줄 단위 코멘트를 남겨 에이전트에게 돌려보내며, SSH 호스트에서도 같은 작업 모델을 쓰는 기능도 제공한다. 모델을 직접 통합하는 폐쇄형 IDE라기보다 여러 CLI 에이전트와 Git 작업 공간을 묶는 제어면에 가깝다.

하지만 worktree의 “격리”를 컨테이너 격리와 혼동하면 안 된다. 디렉터리와 브랜치는 나뉘어도 프로세스는 같은 사용자 권한으로 실행될 수 있다. 홈 디렉터리의 자격증명, Docker socket, 클라우드 CLI 설정, 네트워크, 공용 캐시와 데이터베이스는 그대로 공유할 수 있다. 코드 충돌을 줄이는 장치이지 보안 샌드박스가 아니다. 신뢰할 수 없는 저장소나 적대적 프롬프트를 실행한다면 [CubeSandbox의 MicroVM 격리](/posts/github-trending-cubesandbox-microvm-ai-sandbox/)처럼 실행 결과의 영향 범위를 운영체제 경계에서 줄이는 계층이 별도로 필요하다.

![병렬 AI 코딩 에이전트의 worktree 아키텍처](https://heracles-jo.github.io/assets/img/posts/orca-parallel-ai-coding-agents/architecture.svg)

또한 worktree가 자동으로 병합 가능한 결과를 만들지는 않는다. 세 에이전트가 같은 API를 서로 다른 방식으로 바꾸면 각 브랜치는 깨끗해도 최종 선택은 여전히 어렵다. 따라서 병렬 실행 전에 다음 네 가지를 고정해야 한다.

1. **같은 기준점**: 모든 후보는 동일한 base commit과 동일한 의존성 잠금 파일에서 시작한다.
2. **분리된 가설**: “알아서 고쳐라”를 복제하지 말고 최소 수정, 구조 개선, 재현 테스트처럼 후보의 역할을 구분한다.
3. **공통 성공 조건**: 같은 테스트, 린트, 성능 예산, 보안 규칙을 통과해야 비교할 수 있다.
4. **병합 소유자**: 우승 브랜치를 통째로 합칠지, 여러 후보의 일부를 사람이 재구성할지 미리 정한다.

## 다섯 에이전트가 한 에이전트보다 나쁜 경우

병렬화의 가장 흔한 실패는 일을 잘게 나누지 않고 프롬프트만 복제하는 것이다. 에이전트 다섯 개가 같은 결론에 도달하면 모델 비용과 CI 시간만 다섯 배가 된다. 서로 다른 결론을 내면 검증 기준이 없는 팀은 더 많은 리뷰 시간을 쓴다. 특히 요구사항이 모호한 UI 조정, 도메인 정책 변경, 데이터 마이그레이션처럼 정답을 자동 판정하기 어려운 작업은 후보 수가 늘수록 의사결정 부채가 커진다.

두 번째 실패는 공유 자원의 경합이다. worktree 디렉터리는 달라도 동일한 로컬 포트, 테스트 데이터베이스, Docker Compose 프로젝트명, 브라우저 프로필, 캐시 디렉터리, 개발 클라우드 계정을 사용할 수 있다. 두 에이전트가 동시에 스키마를 초기화하거나 같은 포트에서 서버를 띄우면 한쪽 테스트가 다른 쪽 상태에 의존한다. 브랜치 이름이나 worktree ID를 포트·데이터베이스·임시 디렉터리 namespace에 포함하고, 외부 서비스에는 실행별 idempotency key와 비용 상한을 둬야 한다.

세 번째는 숨은 기준점 이동이다. 한 후보가 작업 중 base branch의 새 커밋을 가져오고 다른 후보는 오래된 상태에 머물면 테스트 결과를 공정하게 비교할 수 없다. 평가 중에는 기준 SHA를 고정하고, 최신 main 반영은 후보 선정 후 한 번만 수행하는 편이 낫다. Git worktree 내부에서 임의 rebase나 force push를 허용하지 않고, 변경 근거와 테스트 결과를 후보별 artifact로 남겨야 한다.

마지막은 결과의 출처 상실이다. 여러 에이전트의 코드를 복사해 하나의 브랜치로 만들면 어떤 모델·프롬프트·테스트에서 나온 변경인지 추적하기 어렵다. [코드베이스 기억 계층](/posts/github-trending-codebase-memory-mcp-code-intelligence-layer/)이 관련 맥락을 찾는 비용을 줄여도, 변경 provenance와 승인 책임까지 대신해 주지는 않는다. 후보 ID, 시작 SHA, 에이전트·버전, 입력 제약, 생성 commit, 검증 결과를 하나의 run record로 묶는 편이 좋다.

## Orca 저장소가 보여주는 실제 운영 난점

Orca는 매력적인 데모뿐 아니라 다중 에이전트 IDE가 떠안는 운영 복잡성도 공개적으로 보여준다. 저장소의 [Git 호환성 정책](https://github.com/stablyai/orca/blob/main/docs/reference/git-compatibility.md)은 로컬·WSL·SSH 호스트마다 Git 버전이 다를 수 있으므로 기능 탐지와 fallback을 호스트별로 관리한다고 설명한다. core workflow 기준선은 Git 2.25이며, `worktree list -z` 같은 새 기능은 지원 여부를 실제 동작으로 확인해 구버전 파서로 내려간다. 단순히 `git --version` 문자열만 믿지 않는 이유는 벤더 백포트와 래퍼가 실제 실행 바이너리의 능력을 정확히 나타내지 않을 수 있기 때문이다.

확인 시점 최신 커밋에는 디렉터리가 삭제됐지만 Git 등록에는 남은 `prunable` worktree가 정상 workspace처럼 표시되어 ENOENT와 빈 pane을 반복하던 문제의 수정이 포함됐다. 최신 릴리스에는 터미널 replay, Windows 붙여넣기, renderer 메모리 누수, SSH relay, 모바일 복구와 관련된 변경도 다수 들어갔다. 공개 이슈에는 앱이 관리하는 훅의 설정 위치, Codex 업데이트 후 훅 실패, macOS renderer white screen 같은 사례가 남아 있었다.

이것은 Orca만의 결함 목록이라기보다 **병렬 에이전트 제어면이 관리해야 할 상태의 수**를 보여준다. 브랜치와 디렉터리뿐 아니라 PTY 프로세스, 에이전트 세션, 원격 연결, diff, 브라우저, 알림, 모바일 재접속, Git provider 상태가 함께 움직인다. 팀이 도입할 때 “화면에서 에이전트가 여러 개 열린다”만 검증하면 안 된다. 재시작·네트워크 단절·삭제된 worktree·오래된 Git·중단된 에이전트·실패한 hook에서 상태가 어떻게 복구되는지 시험해야 한다.

## 도구 비교: 오케스트레이터가 필요한 시점

| 방식 | 적합한 상황 | 장점 | 주요 비용 |
|---|---|---|---|
| 에이전트 1개를 직렬 실행 | 요구사항이 순차적으로 좁혀지는 일반 작업 | 가장 단순하고 리뷰 맥락이 이어짐 | 한 접근에 고착될 수 있음 |
| 수동 `git worktree` + 여러 터미널 | 소수의 독립 실험, CLI에 익숙한 개인·소규모 팀 | 추가 플랫폼 없이 투명하게 구성 | 세션·상태·diff 비교를 직접 관리 |
| Orca 같은 통합 제어면 | 여러 CLI 에이전트, 원격 호스트, 반복적인 후보 비교 | worktree·터미널·리뷰·상태를 한곳에서 관찰 | 빠른 릴리스, 복잡한 상태, 도구 자체 운영 리스크 |
| CI에서 후보를 생성하는 자동 파이프라인 | 재현 가능한 대량 실험과 중앙 통제가 필요한 팀 | 권한·예산·검증을 서버에서 강제 | 상호작용성이 낮고 구축 비용이 큼 |
| 컨테이너·MicroVM 기반 agent runner | 비신뢰 코드, 강한 격리, 다중 사용자 서비스 | 파일·프로세스·네트워크 침해 반경 축소 | 시작 지연, 이미지·스토리지·관측성 비용 |

Orca가 모든 팀의 출발점은 아니다. 독립 후보를 주 1~2회 비교한다면 셸 스크립트와 `git worktree add`만으로 충분할 수 있다. 반대로 여러 모델과 원격 개발 머신을 매일 오가며, 세션 재개와 diff 피드백이 병목이라면 통합 UI의 가치가 커진다. [DeerFlow의 장기 실행 에이전트 운영](/posts/github-trending-deer-flow-long-horizon-agent-workflow/)에서 다룬 체크포인트·관찰성 문제가 코딩 영역에서는 worktree와 commit, test artifact라는 더 구체적인 형태로 나타나는 셈이다.

## 2주 PoC는 “생성량”이 아니라 채택 가능한 변경을 측정한다

PoC에서는 에이전트가 작성한 줄 수나 동시에 열린 세션 수를 성과로 삼지 말아야 한다. 실제 backlog에서 서로 다른 접근이 가치 있는 작업 5~10개를 골라 직렬 방식과 병렬 worktree 방식을 비교한다. 좋은 후보는 회귀 테스트를 먼저 만들 수 있는 버그, 성능 구현 대안, API 호환성을 유지하는 리팩터링, 의존성 교체처럼 성공 조건이 명확한 작업이다.

측정 항목은 다음 정도면 충분하다.

- **후보 채택률**: 생성된 후보 중 실제 PR에 들어간 비율과 폐기 사유를 기록한다.
- **검증 통과율**: 첫 시도에서 테스트·린트·타입·보안 게이트를 통과한 비율을 비교한다.
- **사람의 리뷰 시간**: 후보 생성 시간보다 전체 diff를 이해하고 하나를 고르는 시간이 줄었는지 본다.
- **충돌·재작업 시간**: 후보 조각을 결합하면서 생긴 충돌과 다시 실행한 테스트 시간을 합산한다.
- **후보당 총비용**: 모델 사용량, CI 분, 원격 머신, 저장공간, 실패 재실행을 포함한다.
- **복구 가능성**: 앱·네트워크·에이전트를 강제로 중단한 뒤 worktree, 세션, 미커밋 변경을 찾을 수 있는지 확인한다.

안전 장치도 병렬 수에 맞춰 강화해야 한다. 각 worktree는 최소 권한의 자격증명을 사용하고 프로덕션 배포 권한을 갖지 않게 한다. 셸 명령 훅은 우발적 파괴를 줄일 수 있지만, [dcg 글에서 살펴본 fail-open 경계](/posts/ai-agent-destructive-command-guard/)처럼 IAM과 샌드박스를 대체하지 않는다. 원격 호스트는 개발 전용 계정과 짧은 수명의 키를 사용하고, 모바일 원격 제어는 분실 기기·페어링 해제·알림 내용 노출까지 위협 모델에 넣어야 한다.

실행 전 체크리스트는 짧고 강제 가능해야 한다.

- 기준 SHA와 작업별 성공 조건을 run manifest에 고정한다.
- worktree마다 브랜치, 포트, DB schema, 임시 디렉터리 namespace를 분리한다.
- 한 후보가 수정할 수 있는 경로와 실행 가능한 외부 작업을 제한한다.
- 모든 후보에 동일한 테스트·성능·보안 게이트를 적용한다.
- 자동 병합보다 diff 비교와 사람 승인을 기본값으로 둔다.
- 폐기한 worktree도 필요한 로그와 commit을 보존한 뒤 명시적으로 prune한다.
- Orca를 사용한다면 telemetry 수집 범위와 opt-out, 업데이트 정책, MIT 라이선스 고지를 조직 기준으로 검토한다.

## 병렬화의 목표는 더 많은 코드가 아니다

Orca가 보여주는 중요한 변화는 AI 코딩 도구의 경쟁이 모델 선택에서 작업 공간 운영으로 확장됐다는 점이다. 여러 에이전트를 띄우는 일 자체는 어렵지 않다. 어려운 부분은 동일한 기준에서 시작시키고, 서로의 상태를 오염시키지 않으며, 결과를 같은 잣대로 검증하고, 하나의 일관된 변경으로 끝내는 것이다.

따라서 병렬 AI 코딩의 성패는 에이전트 수보다 **작업 분해와 선택 규칙**에 달려 있다. 독립적인 가설이 있고 자동 검증이 가능하며 후보 다양성의 가치가 리뷰 비용보다 큰 작업에는 Git worktree 오케스트레이션이 유용하다. 반대로 요구사항이 계속 변하고 공유 상태가 많으며 사람이 결과를 판정하기 어려운 작업은 숙련된 에이전트 하나와 짧은 피드백 루프가 낫다.

도입 여부를 결정할 때는 “다섯 배 빠른가”를 묻기보다 “채택 가능한 변경 하나를 만드는 총 리드타임과 위험이 줄었는가”를 측정해야 한다. 그 질문에 재현 가능한 수치로 답할 수 있을 때, Orca 같은 병렬 제어면은 화려한 터미널 대시보드를 넘어 실제 개발 인프라가 된다.

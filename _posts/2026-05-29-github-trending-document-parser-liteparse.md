## RAG에서 자주 망가지는 곳은 모델이 아니다

2026년 5월 29일 GitHub Trending daily에서 [run-llama/liteparse](https://github.com/run-llama/liteparse)가 눈에 들어왔다. 확인 시점 기준 약 7,821 stars, 462 forks, daily 약 929 stars today로 노출되었고, GitHub API 기준 주요 언어는 Rust, 라이선스는 Apache-2.0이었다. 최신 릴리스는 2026년 5월 30일 공개된 `node-v2.0.4`로 확인했고, 최근 커밋도 2026년 5월 30일 기준으로 확인됐다. open issue는 약 15개 수준이었다.

문서 파서는 겉으로 보기에는 지루하다. 새로운 LLM 모델이나 에이전트 프레임워크처럼 화려하지 않다. 그런데 RAG를 실제로 만들어 보면 가장 자주 발목을 잡는 곳이 바로 이 앞단이다. PDF에서 문단 순서가 뒤섞이고, 표가 깨지고, 각주가 사라지고, 페이지 번호와 본문이 섞이면 검색 품질은 바로 무너진다. 그 상태에서 임베딩 모델이나 프롬프트를 바꿔 봐야 효과가 제한적이다.

LiteParse가 흥미로운 이유는 이 문제를 꽤 좁고 실용적인 범위에서 다룬다는 점이다. README 기준으로는 빠르고 가벼운 오픈소스 PDF parsing tool이며, PDFium 기반 spatial text parsing, bounding box, Markdown 출력, Rust·Node·WASM·Python 패키지 배포를 내세운다. 공식 문서도 `developers.llamaindex.ai/liteparse/`로 연결되어 있다.

## LiteParse가 맡는 위치

문서 AI 파이프라인을 단순하게 그리면 원본 문서, 파싱, 정제, 청크 생성, 임베딩, 검색, 답변 생성으로 이어진다. LiteParse는 이 중 파싱과 구조화에 집중한다. 이 위치가 별것 아닌 것처럼 보일 수 있지만, 실제로는 뒤쪽 품질을 결정하는 데이터 계약에 가깝다.

![LiteParse 문서 처리 파이프라인](https://heracles-jo.github.io/assets/img/posts/github-trending-document-parser-liteparse/architecture.svg)

문서를 단순 문자열로 뽑는 것과 LLM이 읽을 수 있는 구조로 바꾸는 것은 다르다. 페이지 안에서 텍스트가 어디에 있었는지, 어떤 순서로 읽어야 하는지, 표와 본문을 어떻게 분리할지, 원문 근거를 어떻게 다시 보여줄지까지 생각해야 한다. bounding box가 의미 있는 이유도 여기에 있다. 나중에 사용자가 “이 답변의 근거가 어디냐”고 물었을 때 원문 페이지와 영역을 보여줄 수 있기 때문이다.

Rust 기반 코어와 다중 런타임 지원도 꽤 중요하다. Python 배치 파이프라인에서만 쓰는 도구라면 선택지가 많다. 그런데 Node 백엔드, WASM 기반 브라우저 미리보기, Python 데이터 처리, Rust CLI를 같이 고려해야 하는 팀이라면 같은 파싱 계층을 여러 위치에서 재사용할 수 있다는 점이 장점이 된다.

## 문서 파싱은 “조용한 실패”가 가장 무섭다

LiteParse를 검토할 때 가장 먼저 봐야 할 것은 잘 되는 예제가 아니다. 실패하는 문서다. 텍스트 기반 PDF는 대부분의 도구가 어느 정도 처리한다. 문제는 스캔 문서, 다단 컬럼, 복잡한 표, 도장 이미지, 수식, 혼합 언어, 페이지 머리말과 꼬리말이 많은 문서다.

운영 환경에서 가장 위험한 실패는 파싱 에러가 크게 나는 경우가 아니다. 오히려 일부 내용이 조용히 빠지는 경우가 더 위험하다. RAG 시스템은 누락된 내용을 모른 채 답을 만든다. 사용자는 “모델이 멍청하다”고 느끼지만, 원인은 12페이지의 표가 파싱되지 않은 것일 수 있다.

그래서 문서 파서는 반드시 관측 가능해야 한다. 문서별 페이지 수, 파싱 시간, 추출된 텍스트 길이, 빈 페이지 비율, 표 보존율, 청크 수, 인덱싱 실패 여부를 남겨야 한다. 나중에 답변 품질 문제가 생겼을 때 “LLM이 틀렸다”에서 멈추지 않고 “원문 어느 영역이 빠졌다”까지 내려갈 수 있어야 한다.

## 기존 도구들과 비교하면 LiteParse의 성격이 보인다

비교 대상은 PyMuPDF, pdfplumber, Apache Tika, unstructured, Docling, 그리고 LlamaParse 같은 상용 또는 클라우드 문서 AI 서비스다. 이 도구들은 같은 문제를 풀지만 성격이 조금씩 다르다.

PyMuPDF와 pdfplumber는 Python 생태계에서 문서 처리와 데이터 분석을 붙이기 좋다. Apache Tika는 PDF뿐 아니라 여러 파일 포맷을 범용적으로 다룰 때 강점이 있다. unstructured와 Docling은 문서 AI 전처리 관점에서 더 넓은 기능을 제공한다. 클라우드 문서 AI 서비스는 복잡한 레이아웃, OCR, 표, 이미지 기반 문서에서 더 나은 결과를 줄 수 있지만 데이터 반출과 비용을 검토해야 한다.

LiteParse를 고를 이유는 비교적 분명하다. 텍스트 중심 PDF를 빠르게 로컬에서 처리하고 싶고, Markdown과 좌표 정보를 활용하고 싶으며, Node/WASM/Python/Rust 같은 여러 실행 환경을 고려한다면 좋은 후보가 된다. 반대로 스캔 문서와 복잡한 양식이 핵심이라면 LiteParse 단독으로 끝내겠다는 접근은 위험하다. OCR fallback이나 LlamaParse 같은 대안을 같이 놓고 봐야 한다.

![LiteParse 대안 비교 매트릭스](https://heracles-jo.github.io/assets/img/posts/github-trending-document-parser-liteparse/comparison.svg)

## 실제 적용 시나리오

가장 직접적인 사용처는 사내 PDF를 Markdown으로 바꿔 검색 인덱스에 넣는 일이다. 정책 문서, 기술 문서, RFC, 보고서, 제품 매뉴얼처럼 텍스트가 중심인 문서가 좋다. 민감 문서를 외부 API로 보내기 어려운 조직이라면 로컬 파서의 의미가 더 커진다.

개인 개발자라면 논문이나 기술 문서를 로컬 지식 베이스로 옮기는 데 쓸 수 있다. 소규모 팀은 고객 문서나 내부 운영 문서를 검색 가능한 형태로 바꾸는 배치 파이프라인을 만들 수 있다. 엔터프라이즈 환경에서는 여기서 한 단계 더 나아가야 한다. 문서 등급, 접근 권한, 원문 링크, 감사 로그, 보존 기간 정책을 함께 붙여야 한다.

특히 사내 검색에서는 “읽을 수 있는 문서”와 “검색해도 되는 문서”가 다르다. 파서가 권한 모델을 대신해 주지는 않는다. 원본 문서의 권한을 인덱스와 검색 결과까지 전달해야 한다. 이 부분을 놓치면 기술적으로는 멋진 RAG 시스템이지만 보안적으로는 위험한 문서 유출 경로가 된다.

## PoC는 예쁜 데모보다 샘플 문서 세트가 중요하다

LiteParse를 검증하려면 대표 문서 50~100개 정도를 먼저 모아야 한다. 잘 정리된 PDF만 넣으면 거의 모든 파서가 좋아 보인다. 실제 조직에서 쓰는 문서는 다르다. 오래된 스캔본, 복잡한 표가 있는 보고서, 페이지마다 머리말이 반복되는 계약서, 한글과 영어가 섞인 매뉴얼, 이미지가 많은 제안서가 들어온다.

측정 항목은 단순히 성공/실패가 아니어야 한다. 텍스트 추출률, 문단 순서, 표 보존율, 페이지별 누락량, 처리 시간, 메모리 사용량, 실패 유형을 봐야 한다. 파서 버전이 바뀌었을 때 청크 결과가 얼마나 달라지는지도 중요하다. 청크가 바뀌면 임베딩도 바뀌고, 검색 결과도 바뀐다. 운영 중인 RAG에서는 이것이 꽤 큰 변경이다.

OCR fallback 기준도 미리 정해 두는 편이 좋다. 예를 들어 페이지별 텍스트 추출량이 비정상적으로 낮거나, 이미지 기반 페이지 비율이 높으면 LiteParse 결과를 그대로 쓰지 않고 OCR 파이프라인으로 넘기는 식이다. 실패를 없애려 하기보다 실패를 분류하고 다른 경로로 보내는 구조가 더 현실적이다.

## LiteParse를 도입할 만한 팀

RAG나 문서 검색을 이미 만들고 있거나, 만들 계획이 있는 팀에게 LiteParse는 검토할 만하다. 특히 “LLM은 붙였는데 답변 품질이 들쭉날쭉하다”는 문제를 겪는 팀이라면 모델보다 파싱 결과를 먼저 들여다봐야 한다. 문서 AI에서 입력 품질은 생각보다 자주 과소평가된다.

제품팀 관점에서는 WASM이나 Node 지원이 흥미롭다. 서버에서만 문서를 처리하는 것이 아니라, 브라우저 미리보기나 사용자 업로드 검증 단계에서 일부 기능을 붙일 수 있기 때문이다. 플랫폼팀 관점에서는 Rust 기반 코어와 로컬 실행이 장점이다. 민감 문서를 외부로 보내지 않고도 대량 처리 파이프라인을 만들 수 있다.

다만 모든 문서 문제를 LiteParse 하나로 해결하려는 접근은 피해야 한다. README에서도 복잡한 문서, 조밀한 표, 다단 레이아웃, 차트, 손글씨, 스캔 PDF의 경우 클라우드 기반 LlamaParse가 더 좋은 결과를 줄 수 있다고 설명한다. 이 문장은 오히려 신뢰할 만하다. 좋은 도구는 자신이 잘 못하는 영역도 알려준다.

## 아키텍처 판단: LiteParse는 RAG의 “수집 계층” 품질을 책임진다

RAG 시스템을 설계할 때 많은 팀이 벡터 DB, 임베딩 모델, 리랭커, 프롬프트에 먼저 관심을 둔다. 하지만 운영에서 더 자주 문제를 만드는 것은 수집 계층이다. 원문 문서를 어떤 순서로 읽었는지, 표를 어떻게 분해했는지, 페이지 머리말을 본문으로 오인했는지, 각주와 캡션이 어디에 붙었는지가 검색 품질을 좌우한다. LiteParse는 바로 이 수집 계층의 앞부분을 맡는다. 그래서 단순 유틸리티가 아니라 데이터 품질 계약의 일부로 봐야 한다.

문서 파싱 결과는 뒤쪽 파이프라인으로 계속 전파된다. 파서가 문단 순서를 잘못 잡으면 청크가 잘못 만들어지고, 청크가 잘못 만들어지면 임베딩이 왜곡되며, 검색 결과가 흔들리고, 결국 LLM은 그럴듯하지만 근거가 약한 답변을 만든다. 운영자가 마지막 답변만 보면 원인을 찾기 어렵다. 따라서 LiteParse 같은 파서는 “문자열을 뽑아내는 도구”가 아니라 “원문과 검색 가능한 지식 사이의 변환 레이어”로 취급해야 한다.

이 관점에서 bounding box와 spatial text parsing은 단순 부가 기능이 아니다. RAG 답변에서 근거를 보여주려면 원문 페이지와 위치를 다시 연결할 수 있어야 한다. 사용자가 답변을 신뢰하려면 “이 내용은 12페이지 왼쪽 하단 표에서 왔다”는 식의 추적 가능성이 필요하다. 규제 산업이나 내부 감사가 필요한 조직에서는 이 추적성이 모델 성능만큼 중요하다. LiteParse를 PoC할 때도 Markdown 출력만 보지 말고 좌표 정보가 후속 UI와 감사 로그에 어떻게 연결될 수 있는지 확인해야 한다.

## 실패를 분류하는 파이프라인이 필요하다

문서 AI에서 좋은 설계는 모든 문서를 한 도구로 완벽히 처리하는 것이 아니다. 현실적인 설계는 문서를 분류하고, 각 유형에 맞는 처리 경로를 태우는 것이다. 텍스트 중심 PDF는 LiteParse 같은 경량 파서로 빠르게 처리할 수 있다. 스캔 문서나 이미지 중심 문서는 OCR 경로로 넘겨야 한다. 복잡한 표와 다단 레이아웃, 도장과 손글씨가 섞인 계약서는 클라우드 문서 AI나 사람이 검수하는 경로가 필요할 수 있다.

이를 위해서는 파싱 결과의 품질 신호를 남겨야 한다. 페이지별 추출 텍스트 길이, 빈 페이지 비율, 표 후보 수, 이미지 비율, 문단 순서 이상 징후, 처리 시간, 오류 유형을 기록한다. 예를 들어 20페이지 PDF인데 17페이지에서 텍스트가 거의 추출되지 않았다면 성공으로 처리하면 안 된다. “파싱은 성공했지만 품질 경고가 있음”이라는 상태가 필요하다. 이 상태를 기준으로 OCR fallback, 수동 검수, 또는 인덱싱 제외를 결정한다.

조용한 실패를 줄이는 장치도 중요하다. 파서가 에러를 내면 운영자는 알 수 있다. 하지만 일부 표만 빠지거나 페이지 순서가 섞이는 문제는 사용자가 잘못된 답변을 받기 전까지 드러나지 않는다. 따라서 샘플 문서 세트에 대한 회귀 테스트가 필요하다. 파서 버전을 올릴 때 주요 문서의 청크 수, 텍스트 길이, 핵심 키워드 포함 여부, 페이지별 누락률이 크게 변하지 않았는지 자동으로 비교해야 한다.

## RAG 운영에서 LiteParse를 넣을 때의 데이터 계약

LiteParse 결과를 바로 벡터 DB에 넣는 것은 빠르지만, 운영 시스템으로는 부족하다. 중간에 정규화 계층이 있어야 한다. 이 계층은 문서 ID, 버전, 페이지 번호, 좌표, 섹션 제목, 원문 파일 해시, 접근 권한, 파싱 도구 버전, 처리 시각을 메타데이터로 붙인다. 나중에 같은 문서가 업데이트되었을 때 어떤 청크를 폐기하고 어떤 청크를 유지할지 판단하려면 이 정보가 필요하다.

접근 권한 전파도 놓치기 쉽다. 원본 문서가 특정 부서만 볼 수 있는 자료라면, 파싱된 텍스트와 임베딩도 같은 제한을 가져야 한다. 벡터 DB에 들어간 순간 권한 모델이 사라지면 RAG는 내부 정보 유출 경로가 된다. LiteParse는 파서이지 권한 시스템이 아니다. 따라서 문서 수집 파이프라인이 원본 저장소의 ACL을 읽고, 검색 시점에도 사용자 권한을 필터로 적용해야 한다.

문서 버전 관리도 중요하다. 계약서, 정책 문서, 제품 매뉴얼은 시간이 지나며 바뀐다. 사용자가 오래된 버전의 내용을 근거로 답변을 받으면 업무 사고가 난다. 파싱 결과에는 원본 문서 버전과 유효 기간, 폐기 여부를 저장해야 한다. 인덱스 재생성 작업은 단순 overwrite가 아니라 어떤 버전이 언제부터 검색 대상인지 관리하는 배포 작업에 가깝다.

## 실무 PoC 설계안

LiteParse PoC는 “README 예제가 동작한다”에서 끝나면 안 된다. 첫 주에는 대표 문서 세트를 만드는 것이 더 중요하다. 정책 문서, 제품 매뉴얼, 계약서, 보고서, 프레젠테이션에서 변환한 PDF, 스캔 PDF, 표가 많은 PDF, 한영 혼합 PDF를 섞어 50~100개 정도를 준비한다. 각 문서에는 기대 결과를 간단히 적어 둔다. 예를 들어 “3페이지 가격표가 추출되어야 함”, “5페이지 표의 첫 번째 열 순서가 보존되어야 함”, “머리말은 청크에서 제외되어야 함” 같은 기준이다.

두 번째 단계에서는 LiteParse와 대안 도구를 같은 세트에 돌린다. PyMuPDF, pdfplumber, unstructured, Docling, 클라우드 문서 AI를 일부 비교군으로 놓고 처리 시간, 텍스트 추출량, 표 보존, 좌표 정보, 설치·운영 복잡도를 비교한다. 이때 단일 승자를 찾기보다 문서 유형별 라우팅 기준을 찾는 것이 좋다. 텍스트 중심 문서는 LiteParse, 스캔 문서는 OCR, 복잡한 재무 표는 별도 서비스처럼 나누는 식이다.

세 번째 단계에서는 RAG까지 연결해 본다. 같은 문서를 파서별로 청크화하고, 동일한 질문 세트로 검색 정확도와 근거 표시 품질을 비교한다. 답변 정확도만 보지 말고 “정확한 페이지를 찾았는가”, “누락된 표 때문에 답변이 틀렸는가”, “근거 UI에 표시할 좌표가 충분한가”를 확인한다. 이 과정을 거쳐야 LiteParse가 단순히 빠른 파서인지, 실제 RAG 품질을 개선하는 수집 계층인지 판단할 수 있다.

## 운영 체크리스트

- 대표 문서 세트를 만들고 문서 유형별 기대 결과를 기록한다.
- 파싱 결과에 문서 ID, 원본 해시, 페이지, 좌표, 파서 버전, 처리 시각을 붙인다.
- 텍스트 추출량이 낮은 페이지는 OCR fallback으로 보내는 기준을 만든다.
- 원본 문서 권한을 인덱스와 검색 결과까지 전파한다.
- 파서 버전 변경 시 청크 수, 텍스트 길이, 핵심 키워드, 검색 결과를 회귀 테스트한다.
- 스캔 문서와 복잡한 표를 LiteParse 단독으로 처리하려 하지 않는다.
- RAG 답변 UI에서 원문 페이지와 영역을 다시 보여줄 수 있는지 확인한다.
- 파싱 실패와 품질 경고를 대시보드로 관측한다.

## 개인적인 결론: RAG 품질은 파서에서 시작된다

LiteParse가 GitHub Trending에서 주목받은 것은 우연한 신호가 아니다. 많은 팀이 RAG를 시도하면서 이제 “문서를 잘 읽는 문제”로 돌아오고 있다. 벡터 DB와 LLM 모델을 바꿔도 답변 품질이 안정되지 않는다면, 원문이 어떻게 파싱되고 있는지부터 확인해야 한다.

LiteParse는 가볍고 로컬에서 돌릴 수 있는 PDF 파서가 필요한 팀에게 좋은 후보로 보인다. 특히 텍스트 중심 PDF, Markdown 변환, 좌표 정보, 다중 런타임 지원이 필요하다면 PoC 가치가 있다. 다만 스캔 문서와 복잡한 레이아웃까지 한 번에 해결해 줄 만능 도구는 아니다.

문서 AI의 운영 품질은 “답변이 그럴듯한가”가 아니라 “원문에서 근거를 추적할 수 있는가”로 판단해야 한다. LiteParse는 그 추적 가능성을 만드는 앞단 도구다. 그래서 더 중요하다. 화려하지 않아도, 여기서 틀리면 뒤쪽은 대부분 같이 틀어진다.

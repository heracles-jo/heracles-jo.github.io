GitHub Trending에서 [penpot/penpot](https://github.com/penpot/penpot)이 다시 주목받는 것은 단순히 “Figma 대체재가 있다”는 뉴스로 소비하기에는 아깝다. Penpot은 오픈소스 디자인 툴이라는 표면적 설명보다 더 근본적인 질문을 던진다. 디자인 협업 인프라는 반드시 특정 SaaS 벤더 안에 있어야 하는가. 제품 설계의 원본 파일, 디자인 토큰, 컴포넌트 의사결정, 개발 핸드오프 데이터는 조직이 직접 통제할 수 있어야 하는가.

Penpot의 메시지는 디자인 협업을 웹에서 하되, 필요하면 자체 서버에 배포하고, 데이터와 워크플로를 조직이 통제하며, 결과물을 웹 표준에 가깝게 유지하자는 것이다. “무료 Figma”라는 표현은 이 프로젝트의 의미를 축소한다. 더 정확히는 디자인 인프라의 소유권과 거버넌스 문제다. 특히 AI 코딩 도구와 디자인 토큰, 프론트엔드 플랫폼 팀이 결합되는 흐름에서는 디자인 파일이 더 이상 디자이너만의 산출물이 아니다.

![Penpot 협업 구조](https://heracles-jo.github.io/assets/img/posts/github-trending-penpot-open-source-design-collaboration/architecture.svg)

## 후보 비교: 디자인 협업 도구의 기준이 바뀐다

| 후보 | 강점 | 한계 | 이번 글의 관점 |
|---|---|---|---|
| [penpot/penpot](https://github.com/penpot/penpot) | 오픈소스, 셀프호스팅, 웹 표준 기반, 디자인-개발 협업 지향 | SaaS형 성숙도·플러그인 생태계·운영 부담 검토 필요 | 디자인 인프라의 소유권과 거버넌스 관점에서 선택 |
| Figma | 강력한 협업 UX, 방대한 생태계, 업계 표준에 가까운 채택 | 벤더 종속, 데이터 통제, 비용, 규제 환경 이슈 | 기능 기준의 비교 대상이지만 오픈 인프라 논점과는 다름 |
| Excalidraw | 빠른 스케치와 저마찰 협업 | 정교한 디자인 시스템·프로토타입에는 제한 | 아이디어 발산 도구로 적합 |
| Storybook | 구현 컴포넌트 문서화와 테스트에 강함 | 디자인 원본 제작 도구는 아님 | Penpot 이후 개발 측 검증 계층 |

Penpot을 평가할 때 “Figma보다 기능이 많은가”로 시작하면 핵심을 놓친다. 실무 질문은 “우리 조직이 디자인 협업 데이터를 어디에 둘 것인가”, “디자인 시스템과 개발 파이프라인을 얼마나 직접 연결할 것인가”, “감사·규제·보안 요구사항을 누가 책임질 것인가”다.

## 디자인 도구가 아니라 협업 백엔드다

Penpot을 도입 후보로 볼 때는 화면 편집기만 보면 안 된다. 실무 도입 여부는 대개 편집 UX보다 계정, 권한, 저장소, 백업, 배포, 감사, 외부 연동에서 갈린다. 셀프호스팅 가능한 플랫폼이라는 말은 자유를 의미하는 동시에 책임을 의미한다. 서버를 운영해야 하고, 업그레이드를 계획해야 하며, 장애와 백업을 관리해야 하고, 사내 인증 체계와의 연결도 검토해야 한다.

디자인 협업 플랫폼의 흐름은 대략 이렇다. 디자이너는 브라우저에서 파일과 컴포넌트를 편집한다. 팀원은 실시간으로 코멘트와 리뷰를 남긴다. 디자인 시스템 담당자는 토큰과 라이브러리를 관리한다. 개발자는 SVG, CSS, 레이아웃 정보, 에셋, 토큰을 확인해 구현에 반영한다. 제품 관리자는 프로토타입을 통해 의사결정을 정리한다. 이 모든 이벤트는 권한 모델과 저장소 모델 위에서 움직인다.

Penpot이 웹 표준을 강조하는 것도 이 맥락에서 중요하다. SVG, CSS, HTML, JSON 같은 표현은 개발자에게 익숙하고 자동화와도 잘 맞는다. 디자인 산출물이 독점 포맷의 블랙박스에 가까울수록 자동화는 어려워진다. 반대로 웹 표준에 가까울수록 디자인-개발 간 변환, 테스트, 검색, diff, 내보내기, 에이전트 활용 가능성이 커진다.

## 디자인 토큰과 개발자 경험

Penpot이 특히 흥미로운 부분은 디자인 토큰과 개발자 친화성을 전면에 둔다는 점이다. 제품 조직에서 디자인 토큰은 더 이상 색상표 문서가 아니다. 다크 모드, 브랜드 테마, 플랫폼별 UI, 접근성 대비, 컴포넌트 상태, 반응형 레이아웃을 통제하는 운영 단위다. 토큰이 잘 관리되면 디자이너와 개발자는 “primary blue가 무엇인가”를 매번 다시 논의하지 않아도 된다.

Penpot을 디자인 시스템 운영에 연결할 때 핵심은 source of truth를 명확히 하는 것이다. 토큰의 원천이 Penpot인지, 코드 저장소의 JSON인지, Style Dictionary인지, 별도 토큰 플랫폼인지 정해야 한다. Penpot을 도입한다고 자동으로 디자인 시스템이 정리되지는 않는다. 기존에 중복된 색상, 임의 spacing, 페이지별 예외 컴포넌트가 많다면 Penpot은 그 혼란을 더 잘 보여줄 뿐이다.

## 장점과 리스크

첫 번째 장점은 데이터 통제권이다. 디자인 파일과 협업 데이터를 자체 인프라에 둘 수 있다는 것은 보안·규제·조달 측면에서 강력하다. 금융, 공공, 국방, 헬스케어, 대기업 내부 플랫폼처럼 데이터 위치와 접근 감사가 중요한 조직에서는 SaaS만으로 해결하기 어려운 요구가 있다.

두 번째 장점은 비용 구조의 예측 가능성이다. 오픈소스라고 해서 운영 비용이 0이 되는 것은 아니지만, 사용자 수 증가에 따른 SaaS 라이선스 비용 압박을 다른 방식으로 관리할 수 있다. 세 번째 장점은 개발 조직과의 접점이다. 디자인 토큰, 컴포넌트 라이브러리, Storybook, Playwright 시각 회귀 테스트, 접근성 검사와 연결하는 전략을 세우기 좋다.

반대로 가장 큰 리스크는 운영 역량이다. 셀프호스팅은 매력적이지만, 장애가 나면 누군가 고쳐야 한다. 업그레이드가 실패하면 누군가 롤백해야 한다. 디자인 팀이 사용하는 도구는 업무 중단의 영향이 크다. 또 Figma의 플러그인, 템플릿, 교육 자료, 외부 협업자 숙련도와 비교하면 생태계 차이가 생길 수 있다. 도구의 조작감도 중요하다. 디자이너는 단축키, 레이아웃, 컴포넌트 variant, 프로토타입 전환의 미묘한 차이에 민감하다.

## PoC 체크리스트

- 셀프호스팅 배포와 업그레이드를 누가 책임지는지 정한다.
- 계정과 권한을 사내 인증 체계와 어떻게 연결할지 확인한다.
- 백업, 복구, 감사 로그 요구사항을 문서화한다.
- 디자이너가 실제 작업에서 불편함을 느끼는 지점을 기록한다.
- 디자인 토큰을 어떤 시스템과 동기화할지 결정한다.
- 개발자 핸드오프가 기존보다 빨라지는지 측정한다.
- 기존 Figma 파일과 디자인 시스템을 어디까지 이전할지 경계를 정한다.
- 장애 발생 시 업무 우회 경로를 마련한다.

## 도입 순서: 전환 프로젝트가 아니라 학습 프로젝트로 시작하라

Penpot을 검토하는 팀에게 가장 현실적인 출발점은 전면 전환이 아니다. 신규 제품 전체를 옮기는 것도, 기존 디자인 시스템을 한 번에 마이그레이션하는 것도 위험하다. 더 좋은 접근은 경계가 분명한 학습 프로젝트다. 예를 들어 내부 관리자 화면, 신규 실험 서비스, 디자인 시스템 v2의 일부 컴포넌트, 외부 공유가 제한된 보안 민감 프로젝트처럼 실패해도 복구 가능한 범위를 고른다.

이때 평가는 기능표가 아니라 흐름표로 해야 한다. 디자이너가 컴포넌트를 만들고, PM이 코멘트를 남기고, 개발자가 토큰과 SVG를 확인하고, QA가 구현 화면을 비교하는 실제 한 사이클을 돌려봐야 한다. 도구의 장점은 데모에서 보이지만, 조직의 마찰은 이 사이클에서 드러난다. 특히 사내 인증, 백업, 파일 export, 외주사 권한, 토큰 동기화, 디자인 리뷰 기록은 PoC 초기에 확인해야 한다.

## 결론: 핵심은 무료가 아니라 주권이다

Penpot을 “무료 Figma”라고 부르는 순간 가장 중요한 의미가 흐려진다. Penpot의 핵심은 가격표가 아니라 디자인 인프라의 주권이다. 디자인 파일, 협업 기록, 토큰, 핸드오프 데이터, 프로토타입이 모두 제품 개발의 핵심 자산이 되었다면 조직은 그 자산을 어디에 두고 누가 통제할지 결정해야 한다.

물론 모든 팀의 정답은 아니다. Figma 생태계는 강력하고, Penpot 도입은 운영 책임을 수반한다. 그러나 GitHub Trending에서 Penpot이 주목받는 흐름은 분명하다. 디자인 협업 도구 시장은 이제 단순한 UX 경쟁을 넘어 데이터 소유권, 거버넌스, 자동화, 개발 파이프라인 통합의 문제로 이동하고 있다. 디자인은 더 이상 그림 파일이 아니다. 운영해야 할 시스템이다.

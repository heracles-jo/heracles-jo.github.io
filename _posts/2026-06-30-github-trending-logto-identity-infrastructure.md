GitHub Trending daily에서 [logto-io/logto](https://github.com/logto-io/logto)가 다시 눈에 띈 것은 “Auth0 대안이 하나 더 올라왔다”는 정도로만 볼 일이 아니다. 2026년 6월 30일 KST 오전 확인 시점의 공개 스냅샷 기준으로 Logto 저장소는 약 1.26만 개의 스타, 860개 이상의 포크, 183개 수준의 공개 이슈, 2026년 5월 29일 공개된 [v1.40.1 릴리스](https://github.com/logto-io/logto/releases/tag/v1.40.1), 그리고 6월 29일까지 이어진 커밋 활동을 보였다. README는 Logto를 “SaaS and AI apps”를 위한 오픈소스 인증·인가 인프라로 설명하며, OIDC와 OAuth 2.1, 멀티테넌시, 엔터프라이즈 SSO, RBAC를 전면에 둔다. 이 표현은 마케팅 문구처럼 보일 수 있지만, 최근 제품팀과 플랫폼팀이 실제로 겪는 문제를 정확히 건드린다. 인증은 더 이상 로그인 화면 하나가 아니라, 고객 조직·에이전트·API·내부 운영자·감사 로그가 얽힌 **ID 운영 평면(identity plane)** 이 되고 있다.

이번 글의 논지는 명확하다. 오늘의 기술 흐름은 “오픈소스 인증 제품의 인기”가 아니라 **SaaS와 AI 애플리케이션이 인증·인가를 애플리케이션 내부 기능에서 독립 인프라 계층으로 분리하는 움직임**이다. Logto는 이 흐름을 비교적 현대적인 제품 언어로 포장한다. Keycloak처럼 오래된 엔터프라이즈 IAM의 무게를 모두 떠안기보다, 제품 개발자가 다루기 쉬운 콘솔과 SDK, 멀티테넌시, OIDC/OAuth 2.1 기반 통합을 앞세운다. 동시에 Authentik, Ory Kratos 같은 대안과 비교하면 운영 모델과 확장 지점이 다르다. 따라서 의사결정자는 “스타가 늘었다”가 아니라 “우리 조직에서 ID를 제품 코드 안에 계속 넣을 것인가, 아니면 별도 운영 평면으로 분리할 것인가”를 질문해야 한다.

모든 수치와 저장소 상태는 위 확인 시점의 스냅샷이다. GitHub Trending 순위, 스타 증가, 이슈 수, 릴리스 상태는 시간에 따라 바뀔 수 있으며, 이 글은 특정 제품의 성능이나 보안 수준을 보장하지 않는다.

## 왜 지금 인증·인가 인프라가 다시 주목받는가

인증 시스템은 오래된 문제다. 로그인, 회원가입, 비밀번호 재설정, 소셜 로그인, SSO, MFA는 새로운 개념이 아니다. 그런데도 Logto 같은 프로젝트가 Trending에 오르는 이유는 세 가지 변화가 동시에 진행되기 때문이다.

첫째, **B2B SaaS의 기본 요구 수준이 올라갔다.** 초기 제품은 이메일 로그인과 소셜 로그인을 붙이는 것으로 충분할 수 있다. 하지만 유료 고객이 늘면 조직 단위 테넌트, 도메인 기반 초대, SAML/OIDC SSO, SCIM 프로비저닝, 역할 기반 접근 제어, 감사 로그, 데이터 격리, 관리자 위임이 요구된다. 이 기능들은 제품의 본질적 차별화가 아니지만, 없으면 엔터프라이즈 계약이 막힌다. 내부에서 직접 만들면 단기간에는 빨라 보여도, 시간이 지나면서 예외 처리와 보안 패치가 제품 개발 속도를 잡아먹는다.

둘째, **AI 앱은 권한 모델을 더 복잡하게 만든다.** 전통적인 웹 앱은 사용자가 버튼을 누르고 서버가 요청을 처리한다. AI 에이전트 앱은 사용자를 대신해 문서를 읽고, 캘린더를 조회하고, CRM을 수정하고, 코드를 실행하고, 외부 API를 호출한다. 이때 “로그인한 사용자”와 “행동하는 에이전트”의 경계가 흐려진다. 사용자 동의, 토큰 위임, 세션 수명, 권한 축소, 감사 추적이 핵심 설계 요소가 된다. README가 Logto를 SaaS와 AI 앱용 인증 인프라라고 부르는 배경도 여기에 있다.

셋째, **클라우드 IDaaS 비용과 종속성에 대한 재평가**가 진행 중이다. Auth0, Okta, Firebase Authentication, Cognito 같은 관리형 서비스는 빠른 출시와 안정성에서 강점이 크다. 그러나 월간 활성 사용자, 기업용 SSO, 머신 투 머신 토큰, 커스텀 도메인, 감사 로그, 고급 MFA가 붙을수록 비용 구조가 급격히 달라질 수 있다. 규제 산업이나 데이터 주권 요구가 있는 조직은 사용자 계정과 인증 로그를 어디에 둘지 더 엄격하게 본다. 오픈소스 대안은 무료라는 이유만으로 선택할 수는 없지만, 배포 위치와 데이터 경계를 직접 통제할 수 있다는 점에서 의사결정 테이블에 다시 올라온다.

## Logto의 핵심 구조: 제품 코드 밖에 인증 평면을 둔다

Logto의 기능 목록을 단순히 나열하면 OIDC, OAuth 2.1, SAML, SSO, RBAC, 멀티테넌시, SDK, 사전 구축 로그인 플로우 정도가 된다. 하지만 실무적으로 더 중요한 점은 **제품 코드가 직접 인증 상태와 권한 정책을 모두 소유하지 않도록 만드는 경계**다. 애플리케이션은 사용자를 Logto의 인증 플로우로 보내고, 표준 프로토콜을 통해 토큰을 받으며, 토큰의 클레임과 권한을 해석해 기능 접근을 제어한다. 관리자는 별도 콘솔에서 애플리케이션, 조직, 역할, 연결된 IdP, 로그인 경험을 다룬다.

이 구조의 장점은 관심사의 분리다. 제품팀은 매번 로그인 폼, OAuth 콜백, 토큰 갱신, 소셜 로그인 제공자별 예외, 기업 SSO 설정 화면을 직접 만들 필요가 줄어든다. 플랫폼팀은 인증 정책을 한곳에서 관리하고, 여러 앱이 같은 정책과 IdP 연결을 재사용하도록 만들 수 있다. 보안팀은 감사 로그, 세션 정책, MFA 요구, 역할 변경 이력을 제품별로 따로 뒤지지 않아도 된다. 물론 이 이상적인 그림은 실제 배포와 운영이 제대로 되었을 때만 성립한다.

OIDC와 OAuth 2.1을 중심으로 한다는 점도 중요하다. OIDC는 사용자가 누구인지에 대한 인증 계층이고, OAuth는 리소스 접근 위임과 토큰 발급의 표준 흐름이다. OAuth 2.1은 오래된 implicit flow 같은 위험한 패턴을 정리하고, Authorization Code with PKCE 같은 더 안전한 흐름을 기본으로 가져가려는 방향을 반영한다. AI 앱에서는 사용자의 클라우드 문서, 메일, 티켓 시스템, 코드 저장소에 접근하는 위임 권한이 자주 필요하므로, 표준 흐름을 얼마나 정확히 구현하고 운영하는지가 단순 로그인보다 중요해진다.

멀티테넌시는 또 다른 핵심이다. B2B SaaS에서 테넌트는 단순히 `organization_id` 컬럼 하나가 아니다. 테넌트마다 로그인 도메인, SSO 제공자, 역할 체계, 관리자 권한, 사용자 초대 정책, 데이터 보존 정책이 다를 수 있다. 인증 인프라가 이 모델을 일급 개념으로 제공하면 제품 코드는 상대적으로 단순해진다. 반대로 테넌트 모델이 제품 도메인과 맞지 않으면, 인증 제품의 기능을 우회하는 커스텀 코드가 늘어나고 결국 운영 복잡도가 되돌아온다.

## Keycloak·Authentik·Ory와 비교한 선택 기준

Logto를 판단하려면 오래된 강자인 [Keycloak](https://github.com/keycloak/keycloak), 자체 호스팅 SSO에서 인기가 높은 [Authentik](https://github.com/goauthentik/authentik), API 우선의 [Ory Kratos](https://github.com/ory/kratos)와 비교해야 한다. 같은 “오픈소스 인증” 범주에 묶이지만 실제로는 제품 철학이 다르다.

Keycloak은 가장 성숙한 엔터프라이즈 IAM 선택지 중 하나다. 확인 시점 기준 GitHub 저장소는 약 3.54만 stars, Apache-2.0 라이선스, 2026년 6월 26일 26.6.4 릴리스, 6월 29일까지의 커밋 활동을 보였다. 장점은 표준 지원, 확장성, 대규모 레퍼런스, 커뮤니티, 운영 경험의 축적이다. 하지만 JVM 기반 운영, 설정의 폭, 클러스터링, 업그레이드, 테마 커스터마이징, 플러그인 개발은 가벼운 제품팀에 부담이 될 수 있다. 이미 플랫폼팀과 IAM 전문성이 있는 조직에는 강력하지만, 스타트업이 제품 출시 속도를 위해 바로 쓰기에는 과한 경우가 있다.

Authentik은 “authentication glue”라는 설명처럼 내부 서비스, 프록시, SSO, 홈랩에서 기업 환경까지 폭넓은 인증 접착제로 인식된다. 확인 시점 기준 약 2.21만 stars와 활발한 커밋 활동을 보였고, 자체 호스팅 친화적인 UI와 여러 프로바이더 통합이 강점이다. 다만 라이선스, 엔터프라이즈 기능 경계, 업그레이드 전략, 고가용성 운영 모델은 조직 요구사항에 맞춰 별도로 검토해야 한다. 내부 도구와 SSO 프록시 통합에는 매력적이지만, 제품에 내장되는 고객용 멀티테넌트 인증의 UX까지 어느 정도 책임질지는 팀마다 평가가 갈릴 수 있다.

Ory Kratos는 headless identity API에 가깝다. 확인 시점 기준 약 1.37만 stars, Apache-2.0, 2026년 3월 v26.2.0 릴리스가 있었다. UI와 플로우를 직접 조합할 자유가 큰 대신, 제품팀이 인증 경험을 더 많이 설계해야 한다. API 우선 조직이나 복잡한 사용자 경험을 직접 통제하려는 팀에는 강력하지만, “관리 콘솔과 기본 로그인 경험까지 빠르게 얻고 싶다”는 팀에는 초기 진입 장벽이 있다.

Logto는 이 세 선택지 사이에서 제품 개발자 친화적인 위치를 잡는다. Keycloak보다 가볍고 현대적 UX를 강조하며, Ory보다 완성된 로그인 경험과 콘솔을 제공하려 하고, Authentik보다 SaaS 고객용 멀티테넌시와 애플리케이션 통합 메시지를 전면에 둔다. 이 포지셔닝이 GitHub Trending에서 관심을 받는 이유다. 다만 성숙도, 대규모 레퍼런스, 장기 업그레이드 안정성에서는 오래된 프로젝트와 동일하다고 가정하면 안 된다.

## 실무 도입 시 장점: 출시 속도보다 운영 경계가 더 중요하다

Logto 같은 ID 인프라를 검토할 때 가장 쉽게 보이는 장점은 출시 속도다. SDK와 사전 구축 로그인 플로우를 쓰면 이메일 로그인, 소셜 로그인, OIDC 앱 등록, 토큰 발급, 사용자 관리 콘솔을 직접 만드는 시간을 줄일 수 있다. 그러나 실무에서 더 큰 가치는 출시 속도보다 **운영 경계의 명확화**다.

첫 번째 장점은 보안 책임의 집중이다. 인증 로직이 여러 마이크로서비스와 프론트엔드에 흩어져 있으면 패치와 감사가 어렵다. 인증 평면을 분리하면 토큰 수명, 세션 폐기, MFA 요구, 비밀번호 정책, SSO 연결 같은 민감 정책을 한곳에서 통제할 수 있다. 물론 이 말은 Logto만이 가능하다는 뜻이 아니라, ID를 독립 계층으로 운영하는 방식 자체의 장점이다.

두 번째 장점은 B2B 확장성이다. 초기에는 개인 사용자만 받다가 기업 고객이 들어오면 “이 회사 도메인 사용자는 이 IdP로만 로그인해야 한다”, “관리자는 팀원을 초대하고 역할을 부여해야 한다”, “감사 로그를 보관해야 한다”는 요구가 생긴다. 제품 코드 안에 하드코딩된 권한 모델은 이런 요구를 감당하기 어렵다. 멀티테넌시와 RBAC가 인증 인프라에 내장되어 있으면, 제품 도메인 권한과 인증 권한을 분리해 설계할 여지가 생긴다.

세 번째 장점은 AI 에이전트 권한의 기반을 마련한다는 점이다. AI 앱이 외부 SaaS API를 호출하거나 조직 내부 데이터를 읽을 때, 사용자의 모든 권한을 그대로 넘기는 방식은 위험하다. 최소 권한, 시간 제한 토큰, 동의 범위, 서비스 계정, 감사 가능한 에이전트 액션이 필요하다. Logto가 이 모든 문제를 자동으로 해결한다고 말할 수는 없지만, OIDC/OAuth 기반 ID 평면을 갖추는 것은 에이전트 권한을 설계하기 위한 전제 조건에 가깝다.

## 한계와 리스크: 인증은 “설치하면 끝”이 아니다

오픈소스 ID 인프라의 가장 큰 함정은 제품을 띄우는 데 성공한 것을 도입 완료로 착각하는 것이다. 인증 시스템은 장애가 나면 모든 제품이 멈추고, 보안 사고가 나면 고객 신뢰가 직접 훼손된다. Logto를 포함한 어떤 도구든 다음 리스크를 반드시 검토해야 한다.

**보안 리스크**부터 보자. OIDC/OAuth 구현에서는 redirect URI 검증, PKCE 적용, 토큰 저장 위치, refresh token rotation, JWT 서명 키 관리, JWKS 캐싱, clock skew, logout semantics, CORS 설정 같은 세부 항목이 사고 지점이 된다. 관리 콘솔이 인터넷에 노출된다면 관리자 MFA와 접근 제어가 필수다. 소셜 로그인과 기업 IdP를 연결할 때는 계정 연결 정책과 이메일 검증 정책도 중요하다. 잘못 설계하면 공격자가 동일 이메일을 가진 다른 제공자를 통해 계정을 탈취하는 계정 혼동(account linking) 문제가 생길 수 있다.

**운영 리스크**도 크다. ID 시스템은 데이터베이스, 캐시, 이메일/SMS 제공자, 외부 IdP, DNS, TLS 인증서, 백업, 키 회전이 모두 얽힌다. 로그인이 느려지거나 콜백이 실패하면 사용자는 제품 자체가 망가졌다고 느낀다. 고가용성을 위해 여러 인스턴스를 띄운다면 세션과 키, 캐시 일관성을 검토해야 한다. 백업 복원 테스트를 하지 않은 상태에서 사용자 계정 데이터베이스만 믿는 것은 위험하다.

**성능 리스크**는 트래픽 패턴에 따라 다르다. 인증 요청은 일반 API 요청보다 빈도가 낮아 보이지만, 장애 복구 후 재로그인, 토큰 갱신 폭주, 대규모 고객사의 출근 시간, 모바일 앱 업데이트 후 재인증처럼 순간 피크가 발생한다. AI 앱에서는 백엔드 작업자와 에이전트가 토큰을 자주 갱신하거나 여러 리소스 서버에 접근할 수 있다. 토큰 검증을 매번 원격 introspection으로 처리할지, 로컬 JWT 검증과 짧은 TTL을 조합할지에 따라 지연과 폐기 가능성이 달라진다.

**유지보수 리스크**는 프로젝트 성숙도와 라이선스에서 온다. Logto는 MPL-2.0 라이선스를 사용한다. Apache-2.0인 Keycloak·Ory와 다르므로, 소스 수정과 배포, SaaS 제공 모델에서 법무 검토가 필요하다. 또한 상대적으로 젊은 프로젝트인 만큼 특정 기능의 API 안정성, 마이그레이션 품질, 장기 지원 정책, 클라우드 서비스와 오픈소스 버전의 기능 경계를 확인해야 한다. 오픈소스라는 사실은 비용과 통제권의 장점이지만, 운영 책임이 사라지는 것은 아니다.

## PoC 체크리스트: 로그인 데모가 아니라 실패 조건을 검증하라

PoC는 “로그인 버튼이 동작한다”에서 끝나면 안 된다. 특히 인증 시스템은 실패 시나리오를 먼저 검증해야 한다. 다음 체크리스트를 기준으로 1~2주짜리 짧은 PoC를 설계하는 것이 현실적이다.

### 1. 프로토콜과 앱 통합

- Authorization Code with PKCE 흐름이 웹, 모바일, SPA, 서버 사이드 렌더링 앱에서 각각 안전하게 구성되는가?
- redirect URI, post logout redirect URI, CORS, cookie SameSite 정책이 환경별로 명확히 관리되는가?
- access token, ID token, refresh token의 수명과 저장 위치가 보안 정책과 맞는가?
- 백엔드 API가 JWT를 로컬 검증할지, introspection을 사용할지, 권한 변경 반영 지연을 어떻게 허용할지 결정했는가?

### 2. 멀티테넌시와 권한 모델

- 고객 조직, 워크스페이스, 프로젝트, 팀 같은 제품 도메인 모델이 Logto의 조직·역할 모델과 자연스럽게 매핑되는가?
- 테넌트별 SSO, 도메인 제한, 관리자 위임, 사용자 초대, 멤버 퇴사 처리 흐름을 구현할 수 있는가?
- RBAC만으로 충분한가, 아니면 리소스별 ABAC나 정책 엔진이 추가로 필요한가?
- 제품 데이터 권한과 인증 권한의 책임 경계가 문서화되어 있는가?

### 3. 운영과 장애 대응

- 데이터베이스 백업과 복원 절차를 실제로 테스트했는가?
- 서명 키 회전, 비밀값 교체, 관리자 계정 복구 절차가 준비되어 있는가?
- 외부 IdP 장애, 이메일 발송 장애, DNS 장애, 인증 서버 과부하 시 사용자 경험은 어떻게 되는가?
- 로그인 성공률, 콜백 오류율, 토큰 발급 지연, MFA 실패율, SSO 설정 변경 같은 지표를 수집하는가?

### 4. 보안과 감사

- 관리자 콘솔 접근에 MFA와 네트워크 제한을 적용했는가?
- 역할 변경, SSO 설정 변경, 앱 secret 발급, 사용자 삭제가 감사 로그에 남는가?
- 계정 연결, 이메일 검증, 비밀번호 재설정, 초대 링크 만료 정책을 검토했는가?
- 침해 사고 시 특정 사용자·테넌트·애플리케이션의 세션과 토큰을 폐기할 수 있는가?

### 5. 라이선스와 공급망

- MPL-2.0 라이선스 의무와 회사의 배포 방식이 충돌하지 않는지 확인했는가?
- 컨테이너 이미지, npm 패키지, 데이터베이스 마이그레이션, Helm/Compose 구성의 공급망 검증 절차가 있는가?
- 업그레이드 전 스테이징에서 마이그레이션과 롤백을 검증하는가?

## 어떤 팀에 적합하고, 어떤 경우 피해야 하나

Logto는 다음과 같은 팀에 특히 검토 가치가 있다. 첫째, B2B SaaS를 만들고 있으며 가까운 시점에 고객별 SSO, 조직 관리, RBAC, 다중 애플리케이션 인증 통합이 필요한 팀이다. 둘째, Auth0·Okta 같은 IDaaS를 쓰고 있지만 비용·데이터 위치·커스터마이징 한계 때문에 대안을 검토하는 팀이다. 셋째, AI 앱을 만들면서 사용자와 에이전트, API 권한을 표준 프로토콜 기반으로 정리하려는 팀이다. 넷째, IAM 전문 플랫폼팀은 없지만 인증 코드를 제품마다 복제하는 방식은 더 이상 지속 가능하지 않다고 판단한 조직이다.

반대로 피하거나 보류해야 할 상황도 있다. 이미 Keycloak을 안정적으로 운영하고 있고, 조직의 IAM 요구가 복잡하며, 전담 팀이 있는 경우 Logto로 옮길 이유는 제한적이다. 규제 산업에서 매우 구체적인 인증 보증, 장기 지원, 공식 인증, 벤더 책임 계약이 필요한 경우에는 오픈소스 자체 호스팅보다 상용 IDaaS나 검증된 엔터프라이즈 배포판이 더 적합할 수 있다. 또한 인증 도메인 지식이 전혀 없는 팀이 “오픈소스라 싸다”는 이유만으로 자체 운영을 선택하는 것은 위험하다. ID 시스템은 클라우드 비용보다 사고 비용이 훨씬 크다.

제품 도메인의 권한 모델이 매우 특수한 경우에도 주의해야 한다. 예를 들어 의료, 금융, 공공 영역에서는 리소스별 동의, 세밀한 위임, 정책 기반 접근 제어, 데이터 주권, 감사 보존 기간, 법적 삭제 요구가 복잡하다. Logto의 RBAC와 조직 모델이 출발점은 될 수 있지만, 외부 정책 엔진이나 자체 권한 서비스가 필요할 수 있다. 이때 인증은 Logto가 맡고, 권한 결정은 별도 서비스가 맡는 하이브리드 구조가 더 적합할 수 있다.

## 향후 관찰해야 할 지표와 전망

Logto를 계속 관찰한다면 단순 스타 수보다 더 중요한 지표가 있다. 첫째, 릴리스 주기와 마이그레이션 품질이다. ID 인프라는 빠른 기능 추가보다 안정적인 업그레이드가 중요하다. 릴리스 노트에서 breaking change, 데이터베이스 마이그레이션, 보안 패치, 롤백 가능성을 봐야 한다. 둘째, 엔터프라이즈 기능과 오픈소스 기능의 경계다. SSO, 감사 로그, 조직 관리, 고급 보안 기능이 어떤 라이선스와 플랜에 속하는지 확인해야 한다. 셋째, 보안 취약점 대응 속도와 공개 정책이다. 인증 제품은 CVE 대응, 의존성 패치, 보안 공지의 투명성이 신뢰의 핵심이다.

넷째, AI 앱 권한 모델의 진화다. 지금은 “SaaS and AI apps”라는 표현이 넓게 쓰이지만, 앞으로는 에이전트 권한 위임, 도구 호출 감사, 사용자 동의 범위, MCP와 같은 도구 연결의 인증 표준, 서비스 계정 수명 관리가 더 구체적인 기능 요구로 내려올 가능성이 크다. Logto가 이 영역을 단순 마케팅이 아니라 실제 제품 기능으로 확장하는지 봐야 한다.

마지막으로 커뮤니티와 생태계를 봐야 한다. SDK가 30개 이상의 프레임워크를 지원한다는 README의 메시지는 매력적이지만, 실무에서는 각 SDK의 유지보수 속도, 예제 품질, 프레임워크 버전 대응, 보안 기본값이 중요하다. 인증 SDK는 애플리케이션의 가장 민감한 코드 경로에 들어간다. “예제가 동작한다”보다 “업그레이드해도 안전하다”가 더 중요하다.

## 결론: 인증을 기능이 아니라 플랫폼 계약으로 다뤄야 한다

Logto의 GitHub Trending 등장은 오픈소스 인증 도구 하나의 인기를 넘어, SaaS와 AI 앱 개발 방식이 바뀌고 있음을 보여준다. 제품이 커질수록 인증은 로그인 화면이 아니라 테넌트, 조직, 역할, SSO, 토큰, 감사, 에이전트 권한을 묶는 플랫폼 계약이 된다. 이 계약을 제품 코드 안에 흩어 놓으면 초기 속도는 빠를 수 있지만, 엔터프라이즈 고객과 보안 요구가 늘어날수록 기술 부채가 된다.

Logto는 Keycloak의 성숙도와 Ory의 headless 철학 사이에서, 현대적인 제품팀이 빠르게 도입할 수 있는 ID 운영 평면을 제안한다. 다만 이것이 곧 무조건적인 정답은 아니다. 인증은 실패 비용이 큰 인프라다. PoC에서는 기능 데모보다 장애, 키 회전, SSO 오작동, 테넌트 권한 충돌, 감사 로그, 업그레이드 실패를 검증해야 한다. 자체 호스팅을 선택한다면 운영 책임까지 가져오는 것이고, 관리형 서비스를 선택한다면 비용과 종속성을 받아들이는 것이다.

오늘의 실무적 결론은 단순하다. 새로운 SaaS나 AI 제품을 만드는 팀이라면, 인증을 “나중에 리팩터링할 회원 기능”으로 보지 말고 처음부터 독립된 ID 평면으로 설계하라. Logto는 그 선택지 중 하나이며, GitHub Trending은 이 문제가 더 많은 팀의 공통 고민이 되고 있다는 신호다. 앞으로 몇 달 동안은 Logto의 릴리스 안정성, AI 앱 권한 모델 확장, 엔터프라이즈 기능 경계, 보안 대응 투명성을 함께 관찰할 필요가 있다.

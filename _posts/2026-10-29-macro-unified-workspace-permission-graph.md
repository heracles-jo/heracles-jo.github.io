업무 도구를 통합하려는 이유는 탭을 줄이기 위해서만이 아니다. 고객 요청은 이메일에 도착하고, 우선순위 결정은 채팅에서 이뤄지며, 실행 항목은 이슈 트래커에 생기고, 최종 근거는 문서와 통화 기록에 흩어진다. 사람이 이 연결을 기억하지 못하면 CRM과 프로젝트 관리 도구는 곧 현실보다 늦어진다. AI 에이전트에 여러 SaaS의 MCP를 붙여도 문제가 자동으로 사라지지는 않는다. 검색 대상이 늘어난 만큼 어느 기록이 최신인지, 서로 충돌하는 권한을 어떻게 해석할지, 행동 결과를 어디에 남길지가 새 병목이 된다.

[macro-inc/macro](https://github.com/macro-inc/macro)는 이메일, 메시지, 문서, 업무, 통화, 파일, CRM, 에이전트를 하나의 워크스페이스와 권한 체계로 묶는다. 각 기능을 범용 문서 데이터베이스의 변형으로 만들기보다 목적별 블록으로 유지하되, 블록 사이 참조를 양방향 그래프로 저장한다. 여기에 팀 활동을 매일 종합하는 AI 메모리와 UI 작업 대부분을 다루는 MCP 표면을 결합한다. 핵심 질문은 “Slack·Notion·Linear를 한 화면으로 바꿀 수 있는가”가 아니다. **협업 맥락을 한 그래프에 모았을 때 권한 확산, 기억의 최신성, 장애와 복구 책임까지 감당할 수 있는가**다.

2026년 10월 29일 08시 48분 KST 전후 GitHub Trending daily에서 Macro는 `106 stars today`로 표시됐다. GitHub API 기준 저장소는 5,406 stars, 517 forks, 열린 이슈와 PR을 합쳐 346개였고, AGPL-3.0 라이선스를 사용했다. 최신 릴리스는 10월 29일 KST에 게시된 `v2026.10.28.0`이며 같은 시점까지 커밋이 이어졌다. 수치와 활동은 확인 당시의 공개 스냅샷이고 이후 달라질 수 있다. 이번 실행 환경에서는 Search Console이나 Analytics의 실제 쿼리·노출 데이터에 접근하지 못했으므로 선정 근거로 사용하지 않았다.

오늘 후보에는 더 큰 일일 증가 폭을 보인 프로젝트가 많았다. 하지만 이미 다룬 AI 코딩 에이전트, 스킬, 장기 메모리 검색 의도와 겹치는지를 먼저 봤다.

Macro를 단순한 오픈소스 Notion 대안으로 설명하면 중요한 차이가 빠진다. 기존 [Twenty CRM 분석](/posts/github-trending-open-source-crm-twenty/)에서 다룬 중심 문제는 고객 데이터 모델과 셀프호스팅 CRM 운영이었다. Macro의 더 큰 실험은 CRM, 채팅, 문서, 업무를 따로 동기화하지 않고 **하나의 참조·검색·권한 모델 안에 배치하는 것**이다. 통합이 성공하면 맥락 이동과 데이터 동기화가 줄지만, 실패하면 한 번의 공유와 한 에이전트 연결이 더 넓은 데이터에 영향을 준다.

기존 [Block Buzz의 주권형 협업 릴레이](/posts/github-trending-buzz-sovereign-collaboration-relay/)는 Nostr 서명 이벤트와 자체 호스팅 협업 로그를 중심으로 봤다. 이번 글은 프로토콜 주권보다 **채널 멤버십이 문서·업무·고객 데이터의 접근권으로 전파되고, 그 결과가 팀 AI 메모리에 다시 들어가는 권한 수렴 문제**에 초점을 둔다. 협업 플랫폼이라는 제품 범주는 같아도 검색 의도와 검증 지표는 다르다.

## 블록 그래프는 동기화를 줄이지만 결합 범위를 넓힌다

Macro의 첫 번째 설계 축은 `block`이다. 공식 문서가 열거하는 블록에는 문서, 이메일, 채널, 채팅, 에이전트, 루틴, 스킬, 업무, 프로젝트, 스프레드시트, 연락처, 회사, 통화, 캔버스, 코드, 이미지, 영상, PDF가 포함된다. 각 화면은 해당 업무에 맞춘 UI를 가지지만, 참조와 공유, 검색은 공통 기반을 사용한다. 메시지에서 고객사를 언급하고 그 메시지로 업무를 만들면 고객사, 대화, 업무의 연결이 양방향으로 남는다.

문서 협업은 Loro CRDT와 Cloudflare Durable Objects를 사용한다. 문서마다 Durable Object room을 두고 WebSocket으로 동기화해 오프라인 편집과 실시간 협업을 제공한다. 호스팅 제품의 데이터는 공식 보안 문서 기준으로 Postgres에 블록과 관계, S3에 파일과 통화 녹음, OpenSearch에 검색 색인을 둔다. 공개 저장소는 42개 배포 서비스와 167개 Rust 라이브러리, SolidJS 클라이언트, Pulumi 인프라를 포함하는 대형 모노레포다.

![Macro의 블록·참조·권한·AI 메모리 계층을 분리한 아키텍처](https://heracles-jo.github.io/assets/img/posts/macro-unified-workspace-permission-graph/architecture.svg)

이 구조의 장점은 “복사”보다 “참조”가 늘어난다는 점이다. 고객 이메일을 Slack에 붙여 넣고, 다시 Linear 이슈에 요약하고, Notion 회의록에 링크하는 과정이 줄어든다. 에이전트도 각 SaaS를 순서대로 검색하기보다 연결된 블록과 통합 검색을 따라갈 수 있다. 최신 상태를 찾는 데 드는 도구 호출과 사람이 맥락을 재구성하는 시간이 함께 줄어들 가능성이 있다.

대신 장애 범위가 넓어진다. 독립된 도구 조합에서는 채팅 장애가 CRM 검색을 곧바로 막지 않을 수 있다. 통합 그래프에서는 참조 저장, 권한 계산, 검색 색인, 문서 동기화, 이메일 수집 중 하나가 뒤처지면 여러 화면이 서로 다른 현실을 보여 줄 수 있다. 원본 블록은 갱신됐는데 OpenSearch가 지연되거나, 채널 멤버십은 제거됐지만 파생 메모리와 캐시에 이전 내용이 남는 식이다. 운영자는 서비스별 uptime보다 **하나의 변경이 참조·권한·검색·메모리에 언제 수렴하는지**를 관측해야 한다.

따라서 “통합 검색에서 나온다”만으로 최신성을 판정하면 안 된다. 각 결과에는 원본 블록 ID, 수정 시각, 권한 판정 시각, 색인 버전, 삭제·보관 상태가 필요하다. 에이전트가 답을 만들 때도 요약 메모리만 인용하지 말고 중요한 판단은 원본 이메일, 업무, 문서, 통화 transcript로 다시 내려가야 한다.

## 채널 기반 공유는 편리함과 권한 증폭을 같은 동작에 담는다

Macro의 권한 모델에서 가장 독특한 규칙은 채널 기반 공유다. 블록을 채널에서 `@mention`하면 채널 멤버 모두에게 그 블록이 공유된다. 새 멤버가 들어오면 과거 메시지 전체와 그 채널에서 공유된 블록에 접근하고, 채널에서 제거되면 해당 경로의 접근을 잃는다. 문서·업무마다 별도 공유 대화상자를 반복하는 비용을 줄이는 대신, **대화 참여자 변경이 데이터 접근 변경이 된다.**

이 모델은 협업 속도에는 유리하다. 새 프로젝트 구성원이 채널에 합류하자마자 결정 기록, 관련 업무, 고객 문서에 접근할 수 있다. 반면 세 가지 위험을 함께 만든다.

첫째, 언급은 설명 행위처럼 보이지만 실제로는 권한 부여다. 민감한 계약서나 고객 이메일을 잘못된 채널에서 언급하면 단순 링크 노출이 아니라 접근 경로가 생긴다. 사용자는 메시지를 쓰는 순간 ACL을 바꾸고 있다는 사실을 인지하기 어렵다.

둘째, 신규 멤버는 합류 이후 기록만 보는 것이 아니라 전체 과거와 과거에 연결된 블록까지 볼 수 있다. 외부 협력자, 인턴, 인수인계 인력이 들어오는 채널은 초대 전에 역사 전체를 검토해야 한다. 팀 채널은 검색과 가입이 가능하고 자동 가입도 설정할 수 있으므로, 채널 유형과 도메인 자동 가입 정책을 민감도와 맞춰야 한다.

셋째, 공유 철회가 모든 파생물의 삭제를 뜻하지 않는다. 공식 문서는 에이전트가 사용자의 권한을 상속한다고 설명하지만, 이미 만들어진 에이전트 답변, 개인 메모, 통화 요약, export, 외부 MCP 서버로 전달된 데이터까지 동일한 시점에 회수되는지는 별도 문제다. 접근 판정과 정보 수명주기를 혼동하면 “채널에서 뺐으니 끝났다”는 잘못된 확신을 만든다.

안전한 운영에는 채널을 협업 UI가 아니라 권한 그룹으로 다루는 정책이 필요하다. 민감 블록의 채널 공유는 경고와 추가 확인을 요구하고, 외부 사용자가 있는 채널은 명확히 표시하며, 신규 멤버 초대 전에 과거 공유 블록 목록을 미리 보여 줘야 한다. 구성원 제거 후에는 검색 결과, 캐시, 메모리, 외부 connector 세션에서 canary 데이터가 다시 나타나는지 검증해야 한다.

## 팀 AI 메모리는 검색 캐시가 아니라 새로운 기록 체계다

Macro는 개인 채팅 기록만이 아니라 이메일, 메시지, 업무, 문서, 통화, MCP 연결 활동을 바탕으로 개인·팀 메모리를 만든다. 공식 문서에 따르면 매일 밤 활동을 종합해 메모리를 갱신한다. 업무는 기본적으로 팀 메모리에 들어가고, 통화 녹음과 transcript도 기본값이 팀 메모리 공유이며 통화별 opt-out이 가능하다. 설정 가능 범위는 현재 제한적이라고 문서가 직접 밝힌다.

이 방식은 [claude-mem의 세션 기억 운영](/posts/claude-mem-agent-session-memory/)보다 입력 범위가 훨씬 넓다. 코딩 세션의 관찰 기록이 아니라 회사의 의사결정과 고객 접점이 요약 대상이다. 따라서 메모리 품질 문제도 “어제 수정한 파일을 기억했는가”에서 끝나지 않는다.

- **최신성**: 야간 갱신 전의 긴급 결정과 방금 취소된 업무가 답변에 반영되는가.
- **충돌 해석**: 이메일과 채팅, 문서가 다른 상태를 말할 때 무엇을 우선하는가.
- **권한 변화**: 팀에서 제외된 사용자의 과거 정보가 새 메모리에서 제거되거나 접근 불가해지는가.
- **옵트아웃**: 통화의 팀 공유를 끄면 transcript, 요약, 파생 업무와 이전 메모리 반영분도 기대한 범위에서 분리되는가.
- **증거 추적**: “프로젝트 상태가 지연”이라는 메모리 문장에서 원본 메시지와 결정자를 찾을 수 있는가.

메모리는 편의 기능이지만 조직 안에서는 사실상 2차 기록 시스템이 된다. 원본의 삭제·보존 정책과 다른 수명주기를 가지면 법적 보존, 개인정보 요청, 내부 조사에서 문제가 생긴다. 요약에 날짜와 출처가 없으면 오래된 판단이 현재 사실처럼 재사용된다. 팀 메모리는 최소한 생성 시각, 포함된 source 범위, 마지막 검증 시각, 근거 링크를 노출하고, 중요한 행동 전에는 원본을 재조회해야 한다.

Context Mode에서 큰 출력을 줄여도 행동 근거는 원문으로 재확인해야 한다고 본 원칙이 여기에도 적용된다. 통합 메모리는 검색 비용을 낮추는 색인이지, 회사의 최종 진실 원장을 자동으로 대체하는 판정기가 아니다.

## MCP가 붙는 순간 통합 UI는 통합 쓰기 권한이 된다

Macro MCP는 원격 HTTP endpoint와 OAuth로 연결된다. README는 UI에서 할 수 있는 작업에 가까운 넓은 MCP 표면을 제공한다고 설명하고, 공개 문서 트리에는 문서·채널·업무·회사·연락처 생성과 수정, 에이전트 dispatch, 검색 같은 다수의 도구가 존재한다. 사용자의 관점에서는 여러 SaaS connector를 따로 관리하지 않고 하나의 인증으로 업무를 처리할 수 있다는 장점이 있다.

그러나 읽기 맥락이 통합됐다는 이유로 쓰기 권한까지 통합하는 것은 다른 결정이다. “고객 A의 최신 상황을 알려 줘”와 “고객 A의 deal stage를 바꾸고 담당자에게 업무를 만들어”는 같은 검색 문맥을 사용하지만 실패 비용은 다르다. 에이전트가 사용자의 권한을 상속하더라도, 그 권한 전체를 모든 프롬프트와 외부 MCP client가 항상 사용해야 하는 것은 아니다.

[AWS Agent Toolkit의 MCP·IAM 거버넌스](/posts/aws-agent-toolkit-mcp-iam-governance/)에서 도구 발견과 실제 실행 권한을 분리했듯, Macro에서도 다음 경계를 두는 편이 안전하다.

1. 검색·요약은 기본 허용하되 public link 생성, 외부 초대, 이메일 전송, 고객·업무 상태 변경은 별도 승인한다.
2. 에이전트별로 허용 블록 유형과 채널을 제한하고, 사용자 계정의 최대 권한을 그대로 복제하지 않는다.
3. 실행 전 대상 블록, 변경 전후 값, 새로 공유될 사람, 외부 전송 내용을 결정론적으로 표시한다.
4. MCP OAuth token의 발급 client, 사용자, scope, 만료, 마지막 사용, 폐기를 감사할 수 있어야 한다.
5. 외부 MCP server로 보낸 데이터에는 Macro의 철회 정책이 적용되지 않으므로 connector별 전송 로그와 보존 계약을 관리한다.

도구 통합의 가치는 인증 창을 줄이는 데 있지만, 보안 목표는 인증을 한 번만 하는 것이 아니다. 행동별 최소 권한과 되돌릴 수 있는 변경 기록을 유지하는 것이다.

## AGPL 셀프호스팅은 가능하지만 아직 제품화된 운영 경로와 다르다

Macro는 2026년 5월 31일 AGPLv3로 전환했고 저장소는 전체 제품 코드를 공개한다. 그러나 “소스가 공개됐다”와 “일반 조직이 안정적으로 자체 운영할 수 있다”는 같은 뜻이 아니다. 공식 FAQ는 2026년 6월 기준 셀프호스팅이 주된 초점이 아니며, 호스팅 버전은 iOS, Apple·Google Mail·GitHub 승인과 SOC 2 Type II 운영을 제공한다고 설명한다. LiveKit, FusionAuth, PostHog 등의 라이선스와 서비스를 직접 유지하거나 비활성화해야 할 수 있다.

개발용 local stack만 봐도 Postgres, Redis, LocalStack, OpenSearch, Kafka, FusionAuth와 여러 Rust service, 동기화 worker가 필요하다. 실제 Google OAuth가 없으면 일부 Gmail·MCP 경로가 동작하지 않는다. 공개 이슈에는 공식 self-hosting용 pre-built Docker image 요청과 개발 Dockerfile의 빌드 의존성 문제가 남아 있다. 이는 셀프호스팅이 불가능하다는 뜻이 아니라, 현재는 “Compose 파일 하나로 관리형 제품을 대체”하는 단계로 가정하면 안 된다는 신호다.

또한 AGPL은 네트워크로 수정 버전을 제공할 때 소스 제공 의무가 생길 수 있다. 내부 사용, 고객 제공, 폐쇄형 확장, 별도 서비스 결합 범위에 따라 법무 검토가 필요하다. 직접 운영한다면 [Coolify 셀프호스팅 PaaS 운영](/posts/coolify-self-hosted-paas-operations/)에서 강조한 제어면 복구 원칙처럼 데이터베이스만 백업해서는 부족하다. Postgres 관계, S3 객체, OpenSearch 재색인, CRDT/Durable Object 상태, 인증 설정, OAuth 승인, 메모리 산출물의 조합을 복구해야 한다.

## 3주 PoC는 기능 수보다 권한 수렴과 맥락 정확도를 측정한다

Macro 같은 통합 워크스페이스를 평가할 때 “몇 개 도구를 없앴는가”만 세면 마이그레이션 비용과 위험을 놓친다. 실제 프로젝트 하나와 제한된 고객 계정, 테스트 이메일 도메인을 사용해 읽기·협업·에이전트 행동을 단계적으로 연다.

![Macro 도입에서 통합 가치와 권한·메모리·복구 위험을 함께 판정하는 의사결정 흐름](https://heracles-jo.github.io/assets/img/posts/macro-unified-workspace-permission-graph/decision.svg)

| 검증 영역 | 수집할 증거 | 중단 조건 예시 |
|---|---|---|
| 맥락 연결 | 이메일→채널→업무→문서→고객 레코드의 backlink와 수정 시각 | 최신 결정을 찾기 위해 결국 기존 도구 전체를 수동 검색해야 함 |
| 권한 수렴 | 채널 합류·탈퇴 전후 block access, 검색, cache, public link 결과 | 제거한 사용자가 과거 공유 블록이나 검색 snippet에 계속 접근 가능 |
| 메모리 정확도 | 팀 메모리 답변의 source 링크, 최신성, 충돌·취소 반영 | 근거 없는 요약으로 고객·프로젝트 상태를 잘못 단정함 |
| 에이전트 행동 | MCP 호출별 actor, 대상, before/after, 승인, rollback 기록 | 자연어 한 문장으로 외부 초대·전송·상태 변경을 연속 실행 가능 |
| 통합 장애 | 색인 지연, CRDT 재접속, 이메일 수집 실패, 부분 서비스 중단 | 원본과 검색·메모리의 불일치를 탐지하거나 복구할 수 없음 |
| 데이터 수명 | trash, account deletion, retention, Gmail disconnect, export 확인 | 삭제·철회 후 파생 메모리와 외부 connector 전송분의 위치를 알 수 없음 |
| 셀프호스팅 | image·서비스 버전, 백업·복원, OAuth, secret rotation, AGPL 검토 | 인증·검색·파일·동기화 중 하나를 포함한 복구 훈련을 완료하지 못함 |

성과 지표는 화면 전환 횟수만이 아니다. 프로젝트 상태 질문에 답하기까지의 시간, 잘못된 최신 정보 선택률, 중복 입력 횟수, 권한 요청·오공유 건수, 에이전트 행동의 사람 수정률을 기존 도구 조합과 비교해야 한다. 통합 이후 검색은 빨라졌지만 권한 검토와 데이터 정정이 더 오래 걸린다면 순효과는 음수다.

Macro가 제시하는 방향은 설득력이 있다. 협업 데이터가 이미 서로 연결돼 있는데 제품 경계 때문에 매번 복사와 동기화를 반복하는 것은 비효율적이다. 양방향 참조와 통합 검색, 팀 메모리는 사람과 에이전트가 같은 업무 맥락에서 출발하게 할 수 있다.

다만 통합의 반대편에는 권한과 장애의 집중이 있다. 채널 언급이 ACL 변경이 되고, 통화가 기본적으로 팀 메모리에 들어가며, 하나의 OAuth 연결이 여러 블록에 쓰기 작업을 수행한다. 셀프호스팅은 AGPL 코드 접근보다 인증·검색·동기화·스토리지·외부 승인 운영 능력에 의해 결정된다.

도입 기준은 “기존 SaaS를 몇 개 대체하는가”보다 명확해야 한다. **연결된 맥락이 실제 의사결정 시간을 줄이는가, 권한 변경이 모든 파생 계층에 예측 가능하게 수렴하는가, AI 메모리의 결론을 원본까지 추적할 수 있는가, 잘못된 에이전트 행동을 승인 전에 멈추고 이후 되돌릴 수 있는가.** 이 네 질문에 반복 가능한 증거로 답할 수 있을 때 통합 워크스페이스는 도구 묶음을 넘어 운영 체계가 된다.

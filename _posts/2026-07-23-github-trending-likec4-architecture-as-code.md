GitHub Trending daily에서 [LikeC4](https://github.com/likec4/likec4)가 눈에 띈 이유는 단순히 다이어그램 도구 하나가 더 등장했기 때문이 아니다. 2026년 7월 23일 오전 KST 확인 시점의 스냅샷 기준으로 LikeC4는 약 4.2천 개의 스타, 300여 개의 포크, 160개대의 오픈 이슈를 보유했고, 같은 날 daily Trending에서는 약 172개의 신규 스타를 얻고 있었다. 최신 릴리스도 [v1.59.2](https://github.com/likec4/likec4/releases/tag/v1.59.2)로 2026년 7월 22일에 배포되었으며, 저장소의 최근 커밋은 의존성 업데이트와 릴리스 작업까지 매우 활발했다. 이 숫자만 보면 세계적 메가 프로젝트라고 부르기는 어렵지만, 실무 아키텍처 문서화 관점에서는 중요한 신호다. 개발 조직이 다시 “아키텍처를 어떻게 최신 상태로 유지할 것인가”라는 오래된 문제를 코드 저장소와 CI/CD의 언어로 풀기 시작했다는 뜻이기 때문이다.

최근 Trending에는 AI 에이전트, 로컬 LLM, 음성·영상 생성 도구처럼 즉각적인 화제성을 가진 프로젝트가 많다. 그러나 실제 엔터프라이즈와 플랫폼 팀의 병목은 종종 더 지루한 곳에서 발생한다. 시스템은 점점 더 잘게 나뉘고, 팀은 분산되며, 서비스 의존성은 런타임에서만 드러난다. 장애가 발생했을 때 최신 다이어그램을 찾지 못하거나, 보안 검토에서 데이터 흐름을 설명하지 못하거나, 신규 입사자가 “문서는 있는데 현재 구조와 다르다”고 느끼는 상황은 여전히 흔하다. LikeC4의 부상은 이 문제를 그림 도구의 UX가 아니라 **Architecture as Code**, 즉 아키텍처 모델을 소스 코드처럼 버전 관리하고 리뷰하며 자동 생성하는 방식으로 다루려는 흐름을 보여준다.

선택 기준은 “가장 스타가 많은 저장소”가 아니었다. 이미 이 블로그에서는 에이전트 네이티브 소프트웨어, 토큰 절감형 AI 코딩 도구, 로컬 AI, 운영 자동화, 보안 거버넌스 등 여러 흐름을 다뤘다. 오늘의 차별화된 논지는 **AI 시대일수록 시스템 지식의 정규화된 표현, 즉 아키텍처 모델이 더 중요해진다**는 점이다. AI 코딩 도구가 코드를 빠르게 바꿀수록, 사람이 합의한 시스템 경계와 데이터 흐름은 더 쉽게 낡는다. LikeC4는 이 간극을 줄이기 위한 실용적 도구로 볼 수 있다.

## LikeC4란 무엇인가: 다이어그램 도구보다 모델링 언어에 가깝다

LikeC4의 README는 자신을 “software architecture를 설명하는 모델링 언어와 그 모델로부터 다이어그램을 생성하는 도구”라고 설명한다. 이름에서 드러나듯 [C4 Model](https://c4model.com/)과 [Structurizr](https://structurizr.com/) DSL에서 영감을 받았지만, 자체 표기법과 유연한 중첩 수준, 커스텀 요소 타입, 스타일링을 제공한다. 사용자는 `npx likec4 start` 같은 CLI로 미리보기 서버를 띄우고, VS Code 확장이나 정적 내보내기를 통해 문서 포털에 통합할 수 있다. 공식 문서는 [likec4.dev](https://likec4.dev/)와 [playground](https://playground.likec4.dev/)에서 확인할 수 있다.

핵심은 PNG나 SVG 파일을 수동으로 그리는 것이 아니다. 서비스, 시스템, 외부 의존성, 관계, 관점을 텍스트 모델로 작성하고, 이를 기반으로 여러 뷰를 만든다. 예를 들어 결제 도메인 전체를 보여주는 context view, API gateway와 내부 서비스 관계를 보여주는 container view, 특정 서비스 내부 컴포넌트를 보여주는 component view를 한 모델에서 파생할 수 있다. 모델이 변경되면 다이어그램도 함께 바뀌므로, 리뷰 대상은 “그림 파일”이 아니라 “관계 선언”이 된다.

이 차이는 실무에서 크다. 기존 문서화는 대개 Confluence, Notion, draw.io, Figma, Miro, Markdown 이미지가 뒤섞인 형태로 남는다. 처음에는 보기 좋지만, 릴리스가 몇 번 지나면 실제 코드와 다이어그램이 벌어진다. 반면 Architecture as Code 접근은 아키텍처 정보를 코드 저장소 안에 두고 pull request로 검토하게 만든다. 변경 이력, 소유자, 리뷰, CI 검증, 정적 사이트 배포라는 개발 조직의 기존 운영 장치를 그대로 사용할 수 있다.

## 왜 지금 Architecture as Code가 다시 중요해졌나

첫 번째 배경은 시스템 복잡도의 증가다. 마이크로서비스, 이벤트 스트리밍, SaaS 통합, 데이터 파이프라인, AI API 호출이 섞인 구조에서는 “서비스 목록”만으로는 전체 리스크를 설명할 수 없다. 어떤 서비스가 어떤 데이터를 받아 어디로 전달하는지, 어떤 외부 API가 장애 격리 경계인지, 어떤 큐가 backpressure를 흡수하는지를 시각적으로 설명해야 한다. 보안 심사와 장애 대응에서는 이 정보가 문서 장식이 아니라 운영 자산이다.

두 번째 배경은 AI 코딩 도구의 확산이다. AI가 테스트를 고치고 모듈을 추가하는 속도는 빨라졌지만, 시스템 설계 의도까지 자동으로 유지해 주지는 않는다. 오히려 더 많은 코드 변경이 더 작은 단위로 발생하면서, 아키텍처 결정의 추적 가능성이 약해질 수 있다. 이때 LikeC4 같은 모델 기반 문서는 AI 도구에도 유용한 컨텍스트가 된다. 사람이 읽는 다이어그램일 뿐 아니라, 저장소 내부의 구조화된 시스템 지식으로 활용될 수 있기 때문이다.

세 번째 배경은 플랫폼 엔지니어링과 내부 개발자 포털의 확산이다. Backstage 같은 포털, 서비스 카탈로그, 소유권 메타데이터, runbook, SLO 문서가 조직 내 표준으로 자리 잡을수록 아키텍처 다이어그램도 “문서 페이지의 그림”이 아니라 카탈로그와 연결된 산출물이 되어야 한다. LikeC4의 정적 내보내기와 IDE 중심 경험은 이런 내부 포털 흐름과 잘 맞는다.

## 핵심 아키텍처: 모델, 뷰, 도구 체인의 분리

LikeC4를 실무적으로 이해하려면 세 계층으로 나누는 것이 좋다.

1. **모델 계층**: 시스템, 컨테이너, 컴포넌트, 외부 actor, 관계를 선언한다. 이는 코드의 클래스 다이어그램이 아니라 팀이 합의한 아키텍처 경계를 표현한다.
2. **뷰 계층**: 같은 모델에서 독자별 관점을 만든다. 임원 보고용 context view, 개발자 온보딩용 container view, 보안 검토용 데이터 흐름 view는 같은 모델을 다르게 투영한 결과일 수 있다.
3. **도구 계층**: CLI, VS Code 확장, 정적 export, CI 검증, 문서 사이트 배포가 여기에 해당한다. 개발자는 로컬에서 바로 미리 보고, 리뷰어는 PR diff에서 관계 변경을 확인한다.

이 구조는 특히 “다이어그램이 너무 많아서 관리가 안 된다”는 문제를 완화한다. 같은 관계를 여러 그림에 중복해서 그리지 않고, 하나의 관계 모델에서 필요한 뷰를 만든다. 물론 완벽한 자동화는 아니다. 어떤 수준까지 모델링할지, 관계를 얼마나 자세히 쓸지, 이벤트 토픽과 데이터 저장소를 별도 요소로 둘지 같은 결정은 여전히 팀이 해야 한다. 그러나 결정이 코드 리뷰와 이력 관리 안으로 들어온다는 점이 중요하다.

## Mermaid, C4-PlantUML, Structurizr와 비교

![Mermaid, C4-PlantUML, Structurizr, LikeC4를 실무 기준으로 비교한 매트릭스](https://heracles-jo.github.io/assets/img/posts/github-trending-likec4-architecture-as-code/comparison-matrix.svg)

아키텍처 다이어그램 생태계는 이미 풍부하다. LikeC4를 도입할 이유가 있는지 판단하려면 대체 도구와의 경계를 명확히 해야 한다.

| 도구 | 적합한 경우 | 장점 | 한계 |
| --- | --- | --- | --- |
| [Mermaid](https://github.com/mermaid-js/mermaid) | README, ADR, 간단한 흐름도 | Markdown 친화적이고 학습 비용이 낮음 | 아키텍처 의미론과 재사용 모델은 약함 |
| [C4-PlantUML](https://github.com/plantuml-stdlib/C4-PlantUML) | PlantUML 기반 C4 다이어그램 표준화 | C4 표현이 익숙하고 렌더러 생태계가 넓음 | 스타일·렌더링·모델 재사용을 팀 규칙으로 보완해야 함 |
| [Structurizr](https://structurizr.com/) / [Structurizr Java](https://github.com/structurizr/java) | C4 모델을 엄격하게 운영하고 싶은 조직 | C4 원저자 생태계와 모델 중심 접근 | 운영 방식, 호스팅, 라이선스, 조직 표준 검토 필요 |
| LikeC4 | 코드 저장소 중심의 유연한 Architecture as Code | DSL 유연성, IDE 경험, 정적 문서화에 강점 | 모델 거버넌스가 없으면 또 다른 문서 부채가 됨 |

Mermaid는 “문서에 빠르게 그림을 넣는 도구”로 훌륭하다. 개발자가 README나 이슈에서 시퀀스 다이어그램을 그리기에는 가장 가볍다. 그러나 여러 뷰에서 같은 시스템 관계를 재사용하고, 변경 리뷰의 대상으로 삼고, 조직의 아키텍처 카탈로그와 연결하려면 표현력이 부족해질 수 있다.

C4-PlantUML은 C4 모델을 이미 이해한 팀에 매력적이다. PlantUML 렌더링 파이프라인을 갖춘 조직이라면 도입 장벽도 낮다. 다만 PlantUML 파일이 많아질수록 공통 모델과 뷰 분리, 스타일 일관성, 렌더링 환경을 관리하는 별도 규칙이 필요하다.

Structurizr는 C4 모델 중심 접근의 대표 격이다. 엄격한 구조와 C4 방법론을 중시하는 조직에는 여전히 강력한 선택지다. LikeC4는 이 계보를 더 개발자 도구 친화적이고 유연한 DSL 경험으로 풀어내려는 시도로 볼 수 있다. 따라서 선택은 “어느 도구가 더 유명한가”보다 “우리 조직이 아키텍처 모델을 어떤 개발 흐름에 붙일 것인가”에 달려 있다.

## 실무 도입 시 장점

가장 큰 장점은 온보딩 속도다. 신규 개발자는 레포지토리의 README와 소스 트리만 보고 시스템 구조를 파악하기 어렵다. 특히 여러 팀이 만든 서비스가 이벤트나 API로 얽힌 경우, 코드 검색만으로는 전체 경계를 이해하기 힘들다. LikeC4 모델이 있으면 “이 서비스가 어떤 bounded context에 속하는지”, “외부 결제 사업자와의 호출 경계가 어디인지”, “사용자 데이터가 어느 저장소를 거치는지”를 빠르게 설명할 수 있다.

두 번째 장점은 변경 리뷰 품질이다. PR에서 새로운 서비스가 추가되거나 외부 의존성이 생겼는데 아키텍처 모델이 업데이트되지 않았다면 리뷰어가 이를 지적할 수 있다. 반대로 모델 변경이 포함되어 있으면 코드 변경의 의도를 더 잘 이해할 수 있다. 이는 ADR(Architecture Decision Record)과도 잘 결합된다. ADR은 “왜 이 결정을 했는가”를 남기고, LikeC4는 “그 결정이 현재 구조에서 어떻게 보이는가”를 표현한다.

세 번째 장점은 보안과 컴플라이언스 대응이다. 데이터 흐름, 신뢰 경계, 외부 SaaS 의존성, 인증·인가 경로를 뷰로 만들면 보안 리뷰의 시작점이 명확해진다. 물론 LikeC4 자체가 보안 도구는 아니다. 그러나 보안팀과 개발팀이 같은 구조 모델을 놓고 대화하게 만드는 기반이 된다. 감사 대응에서도 “현행 구조를 설명하는 최신 문서”가 있다는 것은 비용을 크게 줄인다.

네 번째 장점은 내부 포털과의 통합 가능성이다. 정적 export 결과를 GitHub Pages, Backstage TechDocs, 사내 문서 포털에 배포하면 서비스 카탈로그와 아키텍처 뷰를 함께 제공할 수 있다. 플랫폼 팀이 서비스 템플릿에 기본 LikeC4 모델을 포함시키면, 새 서비스가 생성될 때부터 문서화 습관을 심을 수 있다.

## 한계와 운영 리스크: 모델도 결국 코드처럼 관리해야 한다

LikeC4 도입의 가장 흔한 실패 패턴은 “처음 한 번 예쁘게 그린 뒤 방치”다. Architecture as Code라고 해서 자동으로 최신성이 보장되는 것은 아니다. 모델 파일을 누가 소유하는지, 어떤 변경에서 업데이트가 필수인지, 리뷰어가 무엇을 검토해야 하는지 정하지 않으면 텍스트 파일로 된 낡은 그림이 하나 더 생길 뿐이다.

두 번째 리스크는 모델링 과잉이다. 모든 함수, 모든 클래스, 모든 테이블을 아키텍처 모델에 넣으려 하면 유지보수 비용이 폭증한다. C4 접근의 장점은 추상화 수준을 조절하는 데 있다. 실무에서는 서비스 경계, 외부 시스템, 데이터 저장소, 핵심 이벤트, 보안 경계처럼 의사결정에 필요한 요소부터 모델링해야 한다. 코드 구조를 완전히 반영하려는 욕심은 피해야 한다.

세 번째 리스크는 진실의 원천(source of truth) 충돌이다. 이미 서비스 카탈로그, Terraform, Kubernetes manifests, OpenAPI, AsyncAPI, DB schema, observability metadata가 존재한다면 LikeC4 모델은 이들과 어떻게 관계를 맺을지 정해야 한다. 모든 정보를 LikeC4에 복사하면 중복이 생긴다. 반대로 너무 적게 쓰면 의미가 없다. 권장되는 방식은 LikeC4를 “아키텍처 관점의 설명 모델”로 두고, 상세 설정은 기존 도구에 링크하는 것이다.

네 번째 리스크는 렌더링과 배포 파이프라인의 안정성이다. 문서 사이트 빌드가 개발 빌드와 같은 CI에서 돌면, 다이어그램 렌더링 실패가 릴리스를 막을 수 있다. 이는 장점이자 위험이다. 초기에는 warning 수준으로 시작하고, 핵심 시스템에 한해 점진적으로 gate를 강화하는 편이 현실적이다.

보안 관점에서도 주의가 필요하다. 아키텍처 다이어그램에는 내부 네트워크 구조, 민감한 외부 연동, 데이터 이동 경로가 포함될 수 있다. 공개 저장소에서 운영하는 경우 정보 노출 위험이 있다. 사내 저장소라도 벤더명, 내부 호스트명, 인증 경로를 어디까지 드러낼지 기준을 세워야 한다.

## PoC 체크리스트: 한 주 안에 검증할 수 있는 범위

LikeC4는 조직 전체 표준으로 바로 도입하기보다 작은 PoC로 검증하는 것이 좋다. 다음 범위를 권한다.

- **대상 선택**: 서비스 3~7개가 얽힌 실제 도메인 하나를 고른다. 너무 단순한 서비스는 효과를 보여주기 어렵고, 너무 복잡한 플랫폼 전체는 첫 PoC로 부적합하다.
- **모델 범위 정의**: 시스템, 외부 actor, 주요 서비스, 데이터 저장소, 핵심 이벤트 또는 API 관계만 포함한다.
- **뷰 3종 생성**: 비즈니스/임원용 context view, 개발자용 container view, 보안 검토용 데이터 흐름 view를 만든다.
- **PR 규칙 설정**: 외부 의존성, 신규 서비스, 데이터 저장소, 인증 경계가 바뀌는 PR에는 모델 업데이트 여부를 체크한다.
- **문서 배포**: 정적 결과물을 사내 문서 포털이나 GitHub Pages preview에 올려 리뷰어가 쉽게 볼 수 있게 한다.
- **ADR 연결**: 중요한 관계 변경에는 ADR 링크를 붙여 “구조”와 “결정 이유”를 연결한다.
- **성공 기준 측정**: 신규 온보딩 설명 시간, 보안 리뷰 질문 수, 장애 대응 시 참조 여부, 모델 업데이트 PR 비율을 관찰한다.

PoC의 목표는 예쁜 다이어그램을 만드는 것이 아니다. 팀이 실제 변경 흐름 안에서 아키텍처 모델을 유지할 수 있는지 확인하는 것이다. 만약 한 달 뒤 모델이 업데이트되지 않는다면 도구 문제가 아니라 운영 설계 문제일 가능성이 높다.

## 어떤 팀에 적합한가

LikeC4는 다음 조건의 팀에 특히 적합하다.

- 여러 서비스와 외부 SaaS가 얽혀 있어 신규 구성원이 전체 구조를 파악하기 어려운 팀
- 보안·개인정보·컴플라이언스 리뷰에서 데이터 흐름 설명이 반복적으로 필요한 팀
- ADR, 서비스 카탈로그, 내부 개발자 포털을 이미 운영하거나 도입하려는 플랫폼 팀
- Git 기반 리뷰 문화가 강하고, 문서 변경도 PR로 관리하는 조직
- AI 코딩 도구 도입 이후 시스템 지식의 정합성을 더 엄격히 관리하려는 팀

반대로 피해야 할 경우도 있다. 단일 서비스 또는 작은 모놀리스에서 팀원이 모두 구조를 잘 알고 있다면 Mermaid 몇 줄이나 README 그림으로 충분할 수 있다. 문서 리뷰 문화가 없는 조직에서 LikeC4만 도입하면 유지보수 부담이 늘어난다. 또한 아키텍처 결정권이 불명확하고 서비스 ownership이 흐릿한 조직에서는 모델 파일이 책임 소재 논쟁의 장이 될 수 있다. 도구 도입 전에 소유권과 리뷰 책임을 먼저 정해야 한다.

## 운영 설계: CI, 리뷰, 소유권을 어떻게 붙일 것인가

실무에서 추천하는 운영 모델은 다음과 같다.

1. 각 도메인 또는 플랫폼 영역별로 `architecture/` 또는 `docs/architecture/` 디렉터리를 둔다.
2. CODEOWNERS로 아키텍처 모델 리뷰어를 지정한다. 단, 중앙 아키텍트만 병목이 되지 않도록 도메인 리드를 함께 넣는다.
3. CI에서는 초기에 문법 검증과 정적 export만 수행한다. 필수 gate는 핵심 서비스부터 단계적으로 확대한다.
4. PR 템플릿에 “아키텍처 모델 업데이트 필요 여부” 체크박스를 추가한다.
5. 매 분기 또는 주요 릴리스 후 아키텍처 모델 리뷰 세션을 열어 드리프트를 제거한다.
6. 내부 포털에서는 모델만 보여주지 말고 runbook, SLO, 대시보드, ADR, 담당 팀 링크를 함께 제공한다.

이 정도의 운영 장치가 있어야 LikeC4가 문서화 도구가 아니라 변경 거버넌스 도구가 된다. 특히 서비스 카탈로그와 연결할 때는 중복 입력을 최소화해야 한다. 예를 들어 ownership은 Backstage catalog에서 관리하고, LikeC4에서는 해당 카탈로그 항목에 링크하는 방식이 낫다. 데이터 계약은 OpenAPI나 AsyncAPI를 원천으로 두고, LikeC4에서는 상위 관계와 신뢰 경계만 표현하는 식이다.

## 성능과 유지보수 관점

다이어그램 도구는 종종 성능 문제가 과소평가된다. 소규모 모델에서는 어떤 도구든 빠르지만, 수백 개 요소와 수천 개 관계가 생기면 렌더링 시간, 레이아웃 안정성, diff 가독성이 중요해진다. LikeC4를 대규모로 쓰려면 모델을 도메인별로 나누고, 하나의 거대한 “전사 아키텍처 다이어그램”을 만들려는 욕심을 줄여야 한다. 전사 맵은 탐색용 인덱스 정도로 두고, 실제 검토는 도메인별 뷰에서 수행하는 편이 낫다.

유지보수 측면에서는 버전 고정이 중요하다. npm 패키지와 VS Code 확장, 정적 export 결과가 버전에 따라 조금씩 달라질 수 있으므로 CI에서는 lockfile을 사용하고, 문서 사이트 빌드 이미지도 고정하는 것이 좋다. 또한 렌더링 결과를 커밋할지, 빌드 산출물로만 둘지도 결정해야 한다. 일반적으로 모델 소스만 커밋하고 결과물은 CI에서 생성하는 방식이 깔끔하지만, 폐쇄망이나 감사 목적에서는 특정 시점의 export 결과를 아카이브할 필요가 있다.

## 향후 관찰해야 할 지표

LikeC4의 향후 가치를 판단하려면 단순 스타 수보다 다음 지표를 보는 편이 낫다.

- 릴리스 주기와 breaking change 관리가 안정적인가
- VS Code 확장, CLI, 정적 export가 일관된 경험을 제공하는가
- 대규모 모델에서 성능과 레이아웃 품질이 유지되는가
- Structurizr, C4-PlantUML, Mermaid 사용자와 비교해 생태계가 확장되는가
- 문서, 예제, 템플릿, 마이그레이션 가이드가 충분히 쌓이는가
- 이슈 응답과 PR 병합이 특정 개인에게 과도하게 의존하지 않는가
- 내부 포털, ADR, 서비스 카탈로그와 연결하는 사례가 늘어나는가

현재 LikeC4는 빠르게 움직이는 개발자 도구에 가깝다. 따라서 장기 표준으로 채택하려는 조직은 기능 매력도뿐 아니라 프로젝트 지속성과 마이그레이션 비용도 함께 봐야 한다. MIT 라이선스라는 점은 도입 장벽을 낮추지만, 운영 책임은 결국 사용자 조직에 있다.

## 결론: 아키텍처 문서의 가치는 ‘최신성’에서 결정된다

LikeC4가 GitHub Trending에 오른 현상은 다이어그램 도구 시장의 작은 이벤트로 볼 수도 있다. 그러나 더 넓게 보면 소프트웨어 조직이 다시 아키텍처 지식을 코드 가까이에 두려는 흐름이다. AI가 코드를 더 빠르게 생성하고, 플랫폼 팀이 더 많은 자동화를 제공하며, 보안과 컴플라이언스 요구가 더 촘촘해질수록 “현재 시스템을 설명할 수 있는가”라는 질문은 더 중요해진다.

LikeC4는 이 질문에 대한 하나의 실용적 답이다. Mermaid처럼 가볍지는 않고, Structurizr처럼 정통 C4 생태계의 중심이라고 말하기도 이르다. 대신 코드 저장소 중심의 유연한 모델링, IDE 친화적 경험, 정적 문서화 흐름을 결합해 실무 팀이 Architecture as Code를 시도하기 좋은 위치에 있다. 도입의 핵심은 도구 선택보다 운영 설계다. 모델 소유자, 리뷰 규칙, CI 검증, 내부 포털 연결, 보안 정보 노출 기준을 함께 정하지 않으면 어떤 도구도 오래가지 못한다.

오늘의 기술 흐름을 한 문장으로 정리하면 이렇다. **앞으로의 아키텍처 문서는 사람이 그린 그림이 아니라, 코드와 함께 리뷰되고 배포되는 시스템 지식 모델에 가까워질 것이다.** LikeC4의 Trending 진입은 그 변화가 화려한 AI 데모가 아닌 개발 조직의 일상적인 문서화 문제에서도 진행되고 있음을 보여준다.
